# Conditions and mechanisms

A condition is the saved `agents.run` request plus its declared intervention. Change only the intended treatment where possible; keep runner, model, tools, task inputs, and state comparable unless the contrast explicitly studies them.

Check selected capabilities before scored assignment. Admission depends on behavior, not runtime version labels. The fixed guest supports `pi`, `claude`, and `veda` requests and validates selected settings. Recursive Pi requests omit custom cwd; a requested hard descendant cap is unsupported unless the runtime can enforce it.

Mechanism evidence answers whether the intended treatment was actually exposed. Use task-output evidence or returned settings when available. Do not trust a model's self-report that a skill, prompt, or tool was used. If exposure cannot be verified and the outcome definition requires it, retain `treatment-unverified` or a declared limitation rather than manufacturing compliance.

Task state is scoped to the benchmark task. Text tasks need a fresh session and frozen inputs. Coding tasks may use a declared fixture checkout/reset. Browser or application tasks use concrete task-specific reset and verification. Do not require a generic environment inventory, protected-root scan, account framework, database layer, or sandbox.
