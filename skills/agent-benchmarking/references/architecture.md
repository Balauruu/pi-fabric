# Architecture

This reference maps the public benchmark workflow to the installed Pi and Pi Fabric contracts. Methodology belongs in the other references. Machine request fields belong in the [workflow-request schema](../schemas/workflow-request.schema.json), route behavior belongs in [the fixed runner](../workflows/benchmark.ts), and deterministic mechanics belong in the directly indexed helpers in `SKILL.md`.

## Version scope

This map is verified only for:

- Pi coding agent 0.84.4;
- Pi Fabric 0.75.0;
- the Fabric guest TypeScript declarations generated by that installed runtime.

The installed package manifests cited as PI1 and PF1 below establish those package versions. Do not infer a later runtime contract from this document. Recheck guest declarations, public package exports, lifecycle behavior, limits, and canaries after either version changes. The current fixed runner and request schema expose `execute`, `judge`, `adjudicate`, and `finalize` stages, bind runtime capability and call-plan artifacts by digest, cap requests at 100 calls, and support recursive measured parents by omitting custom cwd and passing an absolute workspace in the prompt. If any of those installed capabilities or bindings is absent or fails its exact-path canary, return `unsupported` before mutation. Pi Fabric's supported npm export boundary is `pi-fabric` and `pi-fabric/protocol` (PF1). Declarations under `pi-fabric/dist` are installed implementation evidence, not supported imports for the workflow.

## Public routes and one-program rule

The request selects exactly one public route from the `workflow-request` schema:

| Route | Behavior | Scored calls |
| --- | --- | --- |
| Design | Frame the decision, inventory bounded evidence, freeze design-owned contracts and schedule, build and certify graders, and report blockers. | Forbidden |
| Execute | Verify seals and canaries, run only eligible sealed schedule rows, checkpoint waves, reconcile, and freeze raw output. | Allowed only after the launch gate |
| Audit | Inspect an existing packet read-only, classify defects, and recommend the smallest valid repair. Never rerun an existing benchmark merely to complete the audit. | Forbidden |
| Analyze | Advance one preplanned `judge` batch, `adjudicate` batch, or zero-call `finalize` stage. Preparation occurs before the first judge call in the sealed judge-stage transaction. Every stage is independently reconciled and checkpointed. | Only calls preassigned to the selected judge/adjudication call plan |

Each bounded route or preplanned stage invocation is one type-checked `fabric_exec` program. Read `workflows/benchmark.ts`, provide its exact bytes as the guest TypeScript program, and let it obtain and validate one request through `π.request`. Do not split a stage into ad hoc host calls and never author a session-specific replacement. The installed execution service type-checks the complete guest program and returns before host-call setup when diagnostics exist (PF3). One program therefore gives the checker a complete argument surface before side effects, keeps phase and result values in one execution context, and produces one bounded Fabric execution trace and one checkpoint boundary.

A long Execute route uses sealed resumable wave invocations. Analyze uses zero-call preparation within the first judge transaction, bounded `judge` batches, bounded `adjudicate` batches, then zero-call `finalize`; no invocation may exceed the capability-bound call plan. Each invocation is still the same complete type-checked fixed runner. It verifies the same frozen revisions, processes only selected sealed waves and eligible missing rows, and returns an immutable checkpoint receipt. A valid terminal row is skipped. A never-assigned row may run. An assigned row without a terminal is ambiguous and must not be replayed under the same ID. A retry runs only under a new ID already present in the frozen schedule.

Static or type-check failure must occur before attempt assignment. Runtime argument validation remains authoritative after alias normalization even when guest checking succeeds.

## Visible phases

Use `workflow.phase` for applicable phase transitions and `workflow.item` for stable row-level progress. The canonical phase vocabulary is:

1. Frame
2. Inventory
3. Freeze design
4. Build graders
5. Certify graders
6. Preflight conditions
7. Verify mechanisms
8. Test scheduler and supervisor
9. Seal execution
10. Execute waves
11. Freeze raw outputs
12. Blind grade
13. Aggregate telemetry
14. Analyze
15. Reconcile
16. Report
17. Cleanup

Routes omit phases that do not apply, but they do not reorder validity dependencies. In particular, design and graders precede scored output; preflight precedes assignment; execution reconciliation precedes raw freeze; raw freeze and reconciliation precede blind-map creation; grading completes before unblinding and analysis; exact final reconciliation precedes a completion claim. Audit treats Cleanup as a recommendation or verified observation, not permission to mutate the audited packet.

`workflow.configure` changes the activity display but does not create a phase. Repeated `workflow.phase` calls create repeated occurrences. Live item labels, event messages, descriptions, and arbitrary data are not all retained in Fabric's functional trace. Durable benchmark state therefore lives in write-once artifacts, not the activity UI or terminal prose.

## Ownership and data flow

```text
workflow request
  -> route validation
  -> design-owned contracts and design seal
  -> condition, grader, scheduler, supervisor, and resume canaries
  -> execution-owned code and execution seal
  -> sealed schedule rows
  -> assignment artifact
  -> direct agents.run request
  -> full FabricAgentResult plus logs/session/native evidence
  -> started projection when supported
  -> terminal artifact published last
  -> exact lifecycle reconciliation
  -> raw freeze
  -> condition-private blind map
  -> separate direct agents.run grader records
  -> telemetry projection and paired analysis
  -> audit/report completion gate
```

Ownership is intentionally narrow:

| Owner | Data it may create |
| --- | --- |
| Coordinator | Requests, assignments, checkpoints, freezes, seals, timestamps, IDs, hashes, terminal projections, and reconciliation receipts |
| Measured agent | Returned response and task-side effects inside its isolated attempt state |
| Fabric runtime | Agent ID, resolved runner/model metadata, statuses, runtime timestamps, usage, tool-call count, session/log pointers, and raw lifecycle evidence |
| Grader | Immutable criterion result under a blinded grader ID |
| Deterministic helpers | Create-only derived records whose inputs, versions, and source digests are retained |

No model-authored timestamp, ID, retrieval date, or provenance field is coordinator evidence. One artifact has one owner. Derived projections never replace raw bytes.

## `workflow.agent` and `agents.run`

`workflow.agent(prompt, options)` is a convenience projection. On success it returns `result.value` when defined, otherwise `result.text`. It throws on a non-completed child and hides the child ID, full status, runner, transport, model, session fields, timestamps, turns, tool calls, usage, errors, logs, nested tree, and budget summary. It participates in workflow token-budget observation (PF2, PF4).

Use `workflow.agent` only for bounded design inventory, semantic audit, or report review where returned text or value is sufficient and no measured metadata is needed.

`agents.run(request)` blocks until its one-shot child is terminal and returns the full guest `FabricAgentResult` (PF2, PF6). Use it for every measured attempt and every model grader. Preserve the exact request and complete result before deriving projections. A rejected prelaunch/configuration call is different from a returned terminal `failed`, `stopped`, or `timed_out` result.

Direct `agents.run` bypasses `workflow.budget` token accounting because only helper-mediated runs pass through the installed usage recorder (PF4). The coordinator must therefore enforce and record agent-count and concurrency ceilings and aggregate returned usage separately. Model graders use distinct IDs, sessions, artifacts, and traffic totals and start only after scored outputs are frozen.

## Request, model, and session caveats

An agent request may select runner `pi`, `claude`, or `veda` and may provide a model selector. Runner resolution uses call override, configuration, then the runner default. Model selectors may pass through aliases, exact matching, or fuzzy/recency resolution. Retain three layers for parent and nested nodes:

- requested: exact sealed request and selector;
- resolved: runner/model/settings Fabric selected and returned;
- observed: independent process or provider attribution, when exposed.

`FabricAgentResult.model` is resolved metadata. It is not independent proof of the provider-observed model. Preserve raw provider attribution where available and use `unknown` where it is not. Package paths, defaults, and model catalogs do not prove runtime identity.

Keep these IDs distinct:

- `id`: Fabric run identity;
- `sessionId`: transport/session identity when present;
- `runnerSessionId`: runner conversation identity when present.

Never synthesize an absent ID. Pi one-shot children normally use `--no-session`; Veda uses an isolated run name. Fresh one-shot process/session state does not isolate the workspace, home/config, credentials, caches, browser/account state, network services, or mutable tool servers. `worktree: true` isolates Git files only. The condition contract must prove every task-relevant reset independently.

Pi expands `/skill:name` on documented prompt and RPC paths (PI1, PI2). Historical packet evidence showed literal preservation on one one-shot path, while the current installed `agents.run` process canary captured expansion. Treat neither observation as portable. Prove loading through the exact headless runner, transport, version, and prompt position used by the condition. Otherwise use a sealed inline instruction bundle, name it as such, and limit the claim.

## Telemetry and audit caveats

The full result provides a terminal status, aggregate turns and tool-call count, normalized usage, runtime timestamps, and optional session/log evidence. Detailed tool records remain runner-dependent raw JSONL whose parsed payload has no stable normalized public schema. Preserve native logs and declare blind spots.

Pi Fabric 0.75.0 normalizes result usage to `input`, `output`, `cacheRead`, `cacheWrite`, and `cost`. Parent usage is direct for that worker; recursive descendants have separate usage records. Compute subtree totals only from uniquely owned direct records. Never add an inclusive or unknown-scope parent to child usage. The public cost unit is documented inconsistently, so retain the raw value and source and do not present it as independently billed currency without provider evidence.

The outer `fabric_exec` usage field, when present, concerns Fabric auto-approval classifier calls, not child-agent traffic. Rich Fabric audits may contain sensitive arguments and results. Functional traces omit or project some nested content and external/MCP details and can trim under byte bounds. Preserve authorized attempt evidence separately from the trace.

Use coordinator monotonic time for intervals in one process. Runtime `startedAt` and `finishedAt` are source-qualified wall-clock metadata. The blocking `agents.run` API may reveal `startedAt` only on return, so a post-return started projection is not proof of crash-safe in-flight publication or live chronology.

## Limits and controls

| Control | Current contract |
| --- | --- |
| `agents.maxPerExecution` and invocation `agentBudget` | Race-free call-count ceiling, normalized by runtime limits; attempts to call `run`, `spawn`, `handoff`, or `create` consume the count (PF3, PF5). The public `fabric_exec` schema accepts `agentBudget >= 1`, so zero is not a supported API input. The installed service's internal `Math.max(1, ...)` clamp is implementation evidence only, not a public zero-call policy. Prove a zero-call route by omitting agent calls and verifying observed call count zero. |
| `agents.maxConcurrent` | Per-manager semaphore, default 4, range 1 to 32 (PF5). Recursive processes construct separate managers/semaphores, so this is not a recursion-tree global ceiling. |
| `agents.maxDepth` | Runtime spawn-depth guard; normalized zero disables recursive spawning (PF5). |
| Agent timeout | Per-call value can raise but not lower the configured floor. Current configurable maximum is 24 hours (PF5). |
| Executor deadline | Host-enforced. The configured default maximum is 15 minutes and can be raised only to the 24-hour implementation maximum. Orchestration calls can raise the enclosing deadline to the agent timeout (PF5). |
| `tokenBudget` | Observational for workflow helpers, excludes cache tokens, checks before launch, and may overshoot. Direct `agents.run` is excluded (PF3, PF4). |
| Recursive USD budget | Append-only observational ledger that may overshoot under concurrency (PF7). |
| Per-child token guard | Stops only after observed usage crosses the limit and may overshoot by an event (PF5, PF7). |
| Output and trace bounds | Nested result default 2,000,000 characters; successful model-visible output default 50,000; failed output 20,000; persisted details and functional trace each have 512 KiB bounds (PF5, PF8). Oversized output may be moved to a mode-0600 temporary artifact. |

The historical packet hit an effective 100-agent-call invocation ceiling while a larger value appeared admissible. Probe the exact runtime, use the lower requested/configured/observed ceiling, reserve headroom, and include recursive descendants in a coordinator-owned global reservation. Per-manager counters and semaphores are not tree-global controls. Only a provider-side control proven to stop consumption before the limit is a hard spend or token boundary. Record observational guard values, overshoot, and stop status without relabeling them as hard limits. Maximum concurrency means the greatest concurrency proven runnable for the frozen condition and service regime, not the configured semaphore or number of ready rows.
