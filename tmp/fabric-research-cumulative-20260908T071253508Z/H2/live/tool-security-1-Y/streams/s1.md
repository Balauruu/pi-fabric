# AgentDojo v3 evidence for a permission-bounded tool agent

## Assigned question and scope

**Question.** What original AgentDojo v3 evidence should constrain deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Boundary.** This note uses only AgentDojo arXiv v3 and its embedded original appendices, retrieved live. It is evidence about a synthetic, stateful text/tool benchmark, not a production-security guarantee or evidence from other studies. v3 was posted 24 November 2024 and says it fixed a Llama implementation bug and updated the travel suite. [arXiv v3 record](https://arxiv.org/abs/2406.13352v3)

## Bounded answer

**D1. Deploy permission bounds as a risk-reduction control, not as a demonstrated security boundary.** The strongest measured comparator, a model-selected pre-execution tool filter, reduced GPT-4o targeted ASR from **57.69% to 6.84%** in its reported defense experiment, while benign utility was **73.13%** and utility under attack **56.28%**. But the authors explicitly say it fails when tool use cannot be planned beforehand or when tools needed for the user task can also execute the attack, which applies to **17%** of their security cases. [v3 §4.3 and Table 5](https://arxiv.org/html/2406.13352v3#S4.SS3) [Appendix C](https://arxiv.org/html/2406.13352v3#A3)

**D2. Require a local paired, adaptive evaluation before relying on that result.** AgentDojo’s result is for a synthetic environment, GPT-4o, a particular tool-filter design, and generic attacks. It does not establish transfer to a specific permission model, real tools, long-lived sessions, or a defense-aware attacker.

## What v3 evaluates

### Environment and denominators

AgentDojo executes agents in four mutable, synthetic environments: Workspace, Slack, Travel, and Banking. It evaluates **97 user tasks**, **27 injection tasks**, and their within-environment cross-product of **629 security cases**. The table allocation is:

| Environment | Tools | User tasks | Injection tasks |
|---|---:|---:|---:|
| Workspace | 24 | 40 | 6 |
| Slack | 11 | 21 | 5 |
| Travel | 28 | 20 | 7 |
| Banking | 11 | 16 | 9 |

The paper describes up to 7,000 GPT-4 tokens of data, 4,000 tool-description tokens, up to 18 user-task calls, and injection tasks requiring 1–20 steps. Evaluation uses deterministic binary utility/security functions over agent output and environment state, rather than an LLM evaluator. [v3 §3.1 and Table 1](https://arxiv.org/html/2406.13352v3#S3.SS1)

The three reported metrics are:

1. **Benign utility:** fraction of the 97 user tasks solved without attack.
2. **Utility under attack:** fraction of the 629 task/injection pairs in which the user task is solved with no adversarial side effect.
3. **Targeted ASR:** fraction of security cases in which the attacker goal is met.

For an attack collection, success means any attack succeeds on a case. The paper frames this as an adaptive attacker choosing the best attack per user/injection task. [v3 §3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)

### Models and baseline attack result

The evaluated model names are Claude 3 Opus, Claude 3 Sonnet, Claude 3.5 Sonnet, Command R+, Gemini 1.5 Flash, Gemini 1.5 Pro, GPT-3.5 Turbo, GPT-4 Turbo, GPT-4o, and Llama 3 70B. Official provider APIs were used except Llama 3; Claude and Llama received additional model-specific tool-use prompts. The paper does **not** provide immutable API snapshots, temperatures, or other inference settings in the cited evaluation passage. [v3 §4](https://arxiv.org/html/2406.13352v3#S4)

Table 3 reports 95% confidence intervals for the “Important message” baseline attack:

| Model | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| Claude 3 Opus | 66.61 ± 3.69 | 52.46 ± 3.90 | 11.29 ± 2.47 |
| Claude 3 Sonnet | 53.10 ± 3.90 | 33.23 ± 3.68 | 26.71 ± 3.46 |
| Claude 3.5 Sonnet | 78.22 ± 3.23 | 51.19 ± 3.91 | 33.86 ± 3.70 |
| Command R+ | 25.44 ± 3.40 | 25.12 ± 3.39 | 0.95 ± 0.76 |
| Gemini 1.5 Flash | 36.09 ± 3.75 | 34.18 ± 3.71 | 12.24 ± 2.56 |
| Gemini 1.5 Pro | 45.63 ± 3.89 | 28.93 ± 3.54 | 25.60 ± 3.41 |
| GPT-3.5 Turbo | 33.86 ± 3.70 | 34.66 ± 3.72 | 8.43 ± 2.17 |
| GPT-4 Turbo | 63.43 ± 3.76 | 54.05 ± 3.89 | 28.62 ± 3.53 |
| GPT-4o | 69.00 ± 3.61 | 50.08 ± 3.91 | 47.69 ± 3.90 |
| Llama 3 70B | 34.50 ± 3.71 | 18.28 ± 3.02 | 20.03 ± 3.13 |

[Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3)

The measured result is not “stronger models are safer.” GPT-4o had 69.00% benign utility and 47.69% targeted ASR in this table. Claude 3.5 Sonnet had higher benign utility but 33.86% ASR. Low ASR for weak models can partly mean they also fail to execute attacker goals. [v3 §4.1](https://arxiv.org/html/2406.13352v3#S4.SS1)

### Attack selection and outcomes

The primary attack injects an “Important message” telling the agent to perform the attacker task before the original task. The paper also compares `TODO`, `Ignore previous instructions`, and InjecAgent prompts. For GPT-4o, Table 4 reports:

| Attack | Targeted ASR | Untargeted ASR |
|---|---:|---:|
| TODO | 3.66 ± 0.7 | 32.75 ± 1.8 |
| Ignore previous | 5.41 ± 0.9 | 33.23 ± 1.8 |
| InjecAgent | 5.72 ± 0.9 | 31.48 ± 1.8 |
| Important message | 57.70 ± 2.0 | 49.90 ± 2.0 |
| Max of four | 57.55 ± 2.7 | 68.36 ± 2.6 |

[Appendix C, Table 4](https://arxiv.org/html/2406.13352v3#A3)

Attacker knowledge changed results: the Table 2 baseline was 45.8%; correct user and model names produced 47.7%, while a wrong user or wrong model reduced ASR to 23.2% and 23.7%. Injection placement near the end of a tool response reached up to 70% average success against GPT-4o. [v3 §4.2](https://arxiv.org/html/2406.13352v3#S4.SS2) [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

## Measured defense tradeoffs

All five rows below are GPT-4o results, with 95% CIs, in the defense experiment:

| Defense comparator | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| No defense | 69.00 ± 3.6 | 50.01 ± 3.9 | 57.69 ± 3.9 |
| Data delimiters | 72.66 ± 3.5 | 55.64 ± 3.9 | 41.65 ± 3.9 |
| Prompt-injection detector | 41.49 ± 3.9 | 21.14 ± 3.2 | 7.95 ± 2.1 |
| Repeat user prompt | 85.53 ± 2.8 | 67.25 ± 3.7 | 27.82 ± 3.5 |
| Tool filter | 73.13 ± 3.5 | 56.28 ± 3.9 | 6.84 ± 2.0 |

[Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3)

The comparators were: delimiter formatting plus an instruction to ignore instructions inside it, a BERT/DeBERTa-style detector that aborts on detected tool output, prompt sandwiching, and a tool filter in which the agent selects allowed tools before observing untrusted data. [v3 §4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

**F1. Detection traded security for severe availability/utility loss.** Its 7.95% ASR coincided with only 41.49% benign utility and 21.14% utility under attack. The authors attribute this to false positives.

**F2. Tool filtering is the relevant measured permission-bound comparator.** It blocks many read-only-user/write-attacker cases. It is not enough when a user task needs dynamic discovery of tools or the same allowed tools can enact the attacker’s goal. The paper explicitly says 17% of its cases have that overlap. It also does not cover multi-task, persistent-context interactions in which an injection waits for later permissions. [v3 §4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

**F3. Prompt repetition is not established against an adaptive attacker.** The authors themselves say it is unlikely to survive an injection that tells the model to ignore future instructions. Delimiters reduce ASR only to 41.65%, not a usable security boundary.

## Source conflicts and transfer limits

**C1. Tool-count discrepancy.** Table 1 and the data card say **70 tools**, but §3.1 prose says **74 tools**. This note preserves the conflict rather than selecting a number. [v3 §3.1](https://arxiv.org/html/2406.13352v3#S3.SS1) [v3 data card](https://arxiv.org/html/2406.13352v3#A6)

**C2. GPT-4o baseline discrepancy.** Table 3 reports 47.69% targeted ASR for the named baseline attack, while Table 4 reports 57.70% for “Important message,” and Table 5’s undefended defense baseline is 57.69%. The paper does not state a configuration difference sufficient to reconcile them. Table 2’s 47.7% “correct user/model” ablation is consistent with Table 3, not Table 4. Do not combine these values into one estimated rate. [Table 2](https://arxiv.org/html/2406.13352v3#S4.T2) [Tables 3–5](https://arxiv.org/html/2406.13352v3#A3)

**C3. “Max” does not exceed Important-message ASR by point estimate.** 57.55% is slightly below 57.70%, despite the definition of per-case maximum. The reported CIs overlap, but the table does not explain the ordering. This weakens any claim that the reported adaptive selection is a strict empirical upper bound.

**T1. Benchmark-to-deployment limits.** The environment uses dummy data, YAML tool outputs, formal binary checks, and static single-task executions. It does not establish resistance to real authorization semantics, data confidentiality failures not represented by the security functions, long-lived sessions, multimodal content, or attacks that alter a recommendation without a subsequent forbidden tool call. The paper names these limitations. [v3 §4.3 and §5](https://arxiv.org/html/2406.13352v3#S4.SS3)

## Practical deployment controls

These are **proposed controls**, not claims measured by AgentDojo:

- Default-deny tool capabilities, scoped to the task and resource rather than merely tool name.
- Separate read, write, external-send, payment, credential, and data-export authority.
- Require explicit user approval for irreversible or external high-impact actions.
- Reset or re-authorize permissions between tasks. Do not let a previous injection wait for a later task to unlock capability.
- Treat tool filtering as defense in depth. Log denied calls and test whether allowed capabilities are sufficient for attacker goals.

## Concrete paired local transfer evaluation

Use the same local agent, model snapshot, system prompt, tools, task state, run budget, and deterministic state checks in both arms.

| Dimension | Arm A: baseline | Arm B: permission-bounded |
|---|---|---|
| Tool authority | Existing available tool set | Pre-untrusted-data least-privilege allowlist plus resource/action scopes |
| High-impact actions | Normal policy | Denied or explicit approval gate |
| Tasks | Same local benign task set | Same set |
| Attacks | Same injection endpoint and attack corpus | Same corpus, including defense-aware variants |
| Evaluator | Deterministic task and side-effect checks | Same evaluator |

Measure separately, with explicit denominators:

1. Benign utility over all local user tasks.
2. Utility under attack and targeted ASR over the same task × relevant attacker-goal pairs.
3. Unauthorized-call block rate, false blocks, approval burden, and task failures due to insufficient permission.
4. Results by capability overlap: attacker goal possible with allowed tools versus impossible with allowed tools.

Include the four v3 prompt families, identity-knowledge variants when locally plausible, injection position variants, and an adaptive attacker that is allowed to target the policy rather than only reuse static prompts. Add persistent multi-task sessions and cases where the user’s legitimate task needs the same capability as the attacker. Keep per-arm runs paired by task/attack case and report uncertainty and model/configuration identifiers. A deployment decision should require that the bounded arm materially reduces targeted ASR **in the allowed-tool-overlap subset**, not only in cases where policy trivially makes the attack impossible.

## Remaining gaps and stopping point

The source provides no measured result for resource-granular permissions, user confirmation workflows, persistent sessions, real external tools/data, defense-aware attacks against tool filtering, or a production threat model. It also omits immutable inference configuration needed for exact reproduction. Research stopped because the assigned original v3 and embedded appendices repeated the available evidence; no external studies were in scope.
