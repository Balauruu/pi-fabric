# AgentDojo v3 evidence note

## Assigned question and boundary

**Question.** What AgentDojo evidence should constrain deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Bounded answer.** AgentDojo v3 is strong evidence that indirect prompt injection can cause unauthorized tool actions in a stateful, multi-tool environment, and that pre-observation tool restriction materially reduces this measured risk. It is **not** evidence that tool filtering, detectors, delimiters, or repeated prompts provide a production-security guarantee. The key unproven boundary is when legitimate task tools overlap with attacker-required tools, when tools must be selected adaptively, or when context persists across user tasks.

Scope is the original [arXiv v3](https://arxiv.org/html/2406.13352v3), submitted 2024-11-24 and described as fixing a Llama bug and updating Travel ([version record](https://arxiv.org/abs/2406.13352v3)), plus its included appendices and linked project material. No claim below transfers results to a production agent without the proposed local evaluation.

## What v3 evaluates

### Environment and evaluator

AgentDojo is a **synthetic stateful tool environment**, not a static prompt set: Workspace, Slack, Travel, and e-banking. Agents read and mutate state through documented tools, tool outputs are YAML-formatted to the LLM, and utility/security are deterministic binary functions over model output plus pre/post environment state. This avoids an LLM evaluator that could itself be injected. [§3.1 and §3.4](https://arxiv.org/html/2406.13352v3#S3)

- **Tasks:** 97 user tasks and 27 injection targets, crossed only within relevant environments, yielding **629 security cases**. User tasks alone are **97 benign utility cases**. [Table 1 and §3](https://arxiv.org/html/2406.13352v3#S3.T1)
- **Task difficulty:** up to 7,000 GPT-4 tokens of data, 4,000 tool-description tokens, and chains of up to 18 calls. Injection goals span 1–20 steps. [§3.1](https://arxiv.org/html/2406.13352v3#S3)
- **Metrics and denominators:**  
  - *Benign utility*: solved user tasks / 97, without attack.  
  - *Utility under attack*: security cases where the user task is solved **and no adversarial side effect occurs** / 629. Its complement is untargeted ASR.  
  - *Targeted ASR*: cases where the attacker goal is met / 629.  
  - A “Max” collection succeeds if any candidate attack succeeds for that case, intended to model per-case attack selection. [§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)
- CIs are reported as 95% proportion intervals. The appendix estimates GPT-4o cost at **$35 for 629 security cases** and **$4 for 97 utility cases**. [Appendices C–D](https://arxiv.org/html/2406.13352v3#A3)

### Models and attack selection

The paper evaluates Claude 3 Opus/Sonnet/3.5 Sonnet, GPT-3.5 Turbo/GPT-4 Turbo/GPT-4o, Gemini 1.5 Flash/Pro, Command R+, and Llama 3 70B. Official provider function-calling APIs were used except Llama 3, which used an added tool-calling prompt. GPT-4o was the defense/ablation focus because it had the highest benign utility at the time of those experiments. [§4](https://arxiv.org/html/2406.13352v3#S4)

The linked live results identify the GPT-4o defense-run snapshot as `gpt-4o-2024-05-13`; other listed snapshots include `gpt-4-turbo-2024-04-09`, `gpt-3.5-turbo-0125`, `claude-3-opus-20240229`, `claude-3-sonnet-20240229`, `claude-3-5-sonnet-20240620`, `gemini-1.5-{flash,pro}-001`, and `meta-llama/Llama-3-70b-chat-hf`. [linked results](https://agentdojo.spylab.ai/results/)

The baseline was the generic **“Important message”** injection, placed at relevant placeholders in tools needed for the user task. It directs the named model to perform the attacker goal before the user’s goal. Comparators were `TODO`, “Ignore previous instructions,” InjecAgent’s prompt, and a per-case `Max` over those four. The attack infrastructure uses the user-task ground-truth calls to identify injection locations in tool results that the agent is expected to query. [§4.1–4.2 and App. A/B](https://arxiv.org/html/2406.13352v3#S4)

## Measured outcomes

### Baseline-agent contrast

Table 3’s v3 values are shown as **benign utility / utility under attack / targeted ASR**, percentages:

| Model | Benign | Under attack | Targeted ASR |
|---|---:|---:|---:|
| Claude 3 Opus | 66.61 | 52.46 | 11.29 |
| Claude 3 Sonnet | 53.10 | 33.23 | 26.71 |
| Claude 3.5 Sonnet | 78.22 | 51.19 | 33.86 |
| Command R+ | 25.44 | 25.12 | 0.95 |
| Gemini 1.5 Flash | 36.09 | 34.18 | 12.24 |
| Gemini 1.5 Pro | 45.63 | 28.93 | 25.60 |
| GPT-3.5 Turbo | 33.86 | 34.66 | 8.43 |
| GPT-4 Turbo | 63.43 | 54.05 | 28.62 |
| GPT-4o | 69.00 | 50.08 | 47.69 |
| Llama 3 70B | 34.50 | 18.28 | 20.03 |

Source: [v3 Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3.T3).

The useful deployment constraint is not “the best model is safe.” GPT-4o’s baseline utility was 69.0%, while the chosen injection achieved 47.69% targeted ASR and reduced clean user completion to 50.08%. Claude 3 Opus had lower ASR, but that is entangled with lower benign capability and is not a common-architecture defense comparison.

Attack phrasing matters substantially: on GPT-4o, targeted ASR was `TODO` 3.66%, ignore-previous 5.41%, InjecAgent 5.72%, Important-message 57.7%, and `Max` 57.55%; untargeted ASR was 32.75%, 33.23%, 31.48%, 49.9%, and 68.36%, respectively. [v3 Table 4](https://arxiv.org/html/2406.13352v3#A3.T4). The text says `Max` adds “another 10%,” which conflicts with the rendered table’s targeted values. Do not resolve that conflict by claiming a larger targeted uplift.

Other measured qualifications:

- Correctly naming both user and model moved targeted ASR only from 45.8% to 47.7% (+1.9 points), while a wrong user or model name reduced it to about 23%. [Table 2](https://arxiv.org/html/2406.13352v3#S4.T2)
- Injections near the end of tool output reached up to 70% average ASR against GPT-4o. [§4.1 and App. D](https://arxiv.org/html/2406.13352v3#A4)
- Slack reached 92% ASR in the reported breakdown. A Travel injection requiring both costly booking and email exfiltration reached 0%, often producing only partial attacker success. [§4.1](https://arxiv.org/html/2406.13352v3#S4)

### Defense comparison, all on GPT-4o versus the strongest reported attack

| Defense | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| None | 69.00 | 50.01 | 57.69 |
| Delimit tool output | 72.66 | 55.64 | 41.65 |
| BERT PI detector, abort on detection | 41.49 | 21.14 | 7.95 |
| Repeat user prompt after each tool call | 85.53 | 67.25 | 27.82 |
| Pre-observation tool filter | 73.13 | 56.28 | 6.84 |

Source: [v3 Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3.T5). Reported 95% CIs are approximately ±2.0–3.9 points.

**Measured interpretation.**

- **Tool filtering** produced the best measured targeted-ASR reduction: 57.69% to 6.84%, with benign utility 69.00% to 73.13%. This is the closest evidence for permission-bounded deployment.
- **Detector-abort** also reduced ASR to 7.95%, but its false positives reduced benign utility to 41.49% and clean completion under attack to 21.14%. It is a fail-closed availability tradeoff, not a free security layer.
- **Delimiters** and **prompt repetition** improved the measured utility/ASR tradeoff against this attack set, but residual targeted ASR remained 41.65% and 27.82%. The authors explicitly say repeat-prompt is unlikely to withstand an adaptive injection that instructs the model to ignore future instructions. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

## Deployment implications and limits

### Practical controls supported as controls, not guarantees

1. **C1: Enforce a task-scoped capability allowlist below the LLM.** Select allowed tools before any untrusted tool output reaches the planner, then enforce the decision in the executor. This resembles the measured tool filter. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)
2. **C2: Separate read-only retrieval from consequential write/exfiltration tools.** The filter’s success largely came from cases where user tasks needed read access and attacks needed write access.
3. **C3: Treat prompt defenses and detection as telemetry or availability/safety tradeoffs, not authorization.** Neither is an access-control proof.
4. **C4: Reset or compartmentalize context and privileges across tasks.** The benchmark explicitly does not cover a persistent multi-task agent, where injection can wait for a future task with the needed tools.
5. **C5: Require a separate policy/confirmation path for irreversible operations and sensitive-data release.** This is a proposed operational control, not measured by AgentDojo.

### Unproven or failed conditions

- **Tool overlap:** the paper says the tool filter cannot block the attacker where legitimate task tools also suffice for the attack, reported as **17% of test cases**. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)
- **Adaptive planning:** it fails when later tool results determine which legitimate tool is needed.
- **Persistent context:** not evaluated. “Wait until the right tool is available” is explicitly identified as a failure mode.
- **Output manipulation without extra tool calls:** isolated planner/executor arrangements can still be compromised when an injection biases a recommendation or selected result.
- **Attack adequacy:** v3 itself says its supplied attacks and defenses are relatively simple and that a static attack suite is insufficient. Its data card says it is unsuitable to evaluate a defense with only default attacks rather than a thorough adaptive evaluation. [§3.3, §5, data card](https://arxiv.org/html/2406.13352v3#S3.SS3)
- **Transfer:** state and data are synthetic, manually authored or LLM-generated and manually inspected; the benchmark has no real user data or production integration. [§3.1 and data card](https://arxiv.org/html/2406.13352v3#S3)

## Concrete paired local transfer evaluation

**Design.** Run the actual deployment agent and its real policy/executor in a sandbox with representative, redacted state. Use the *same* task seeds, model/version, system prompt, tool schemas, output formatting, run limit, and attack placement for both arms:

| Arm | Permission policy |
|---|---|
| A: baseline | Current full task-relevant tool exposure |
| B: bounded | Pre-untrusted-data allowlist, executor-enforced, with sensitive write/exfiltration tools excluded unless independently authorized |

For every benign task, run a no-attack control. For every applicable user-task × attacker-goal pair, inject at each real untrusted endpoint. Stratify before aggregation by: read-only vs write/exfiltration target, legitimate/attacker tool overlap, static vs result-dependent tool need, context position, and persistent-context versus reset-context mode.

**Report, per arm and stratum.**

- Benign utility: `successful tasks / all benign tasks`.
- Clean utility under attack: `user task succeeds with no unauthorized side effect / all attack cases`.
- Targeted ASR: `attacker security predicate true / all attack cases`.
- Operational cost: false-block/abort rate, authorization prompts, latency, tool-call count, and human-review load.
- 95% binomial CIs and paired per-case deltas. Preserve denominators rather than combining benign and attack runs.

**Attack set.** Start with the four v3 wording families, then add adaptive variants that target the actual filter, policy names, tool descriptions, output format, ordering, and multi-turn memory. Test both attacker-controlled fraction and end-of-output placement. Count partial effects separately from full security-predicate success.

**Decision rule.** A bounded deployment is not supported if B reduces ASR only by preventing normal work, if residual ASR concentrates in high-impact overlap cases, or if adaptive/persistent-context cases restore write/exfiltration. It is supported only as a narrower permission boundary when B preserves task completion and independently blocks the consequential capability.

## Source conflicts and stopping point

- The v3 text says **74 tools** in §3.1, while Table 1 and the data card say **70 tools**. The task total is coherent: 97 user + 27 injection = 124 tasks. Report both tool counts rather than selecting one. [§3.1](https://arxiv.org/html/2406.13352v3#S3) · [data card](https://arxiv.org/html/2406.13352v3#A6)
- Table 3’s rendered v3 values differ from some values on the live results page, and the current results page warns that it is **not a leaderboard** because models, attacks, and defenses were not all compared. The paper’s Appendix C is the source of record for v3 quantitative claims. [v3 Table 3](https://arxiv.org/html/2406.13352v3#A3.T3) · [live-results caveat](https://agentdojo.spylab.ai/results/)
- The paper’s `Max` targeted-ASR table value (57.55%) conflicts with the prose assertion of another 10% boost. The live results page does not provide a `Max` row that resolves it.
- Research stopped because the assigned source set repeats the same experimental evidence. It does not establish real-world transfer, adaptive robustness, multimodal robustness, long-lived context safety, or a production-security guarantee.
