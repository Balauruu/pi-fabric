# AgentDojo v3 evidence for a permission-bounded tool agent

## Assigned question, scope, and bounded answer

**Question:** What AgentDojo evidence should constrain deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Scope:** Only the original [AgentDojo arXiv v3](https://arxiv.org/html/2406.13352v3), including its embedded appendices, treated as the relevant source through **2026-09-07**. This is benchmark evidence, not a production-security guarantee.

**Bounded answer:** AgentDojo v3 supports treating indirect prompt injection as a deployment-blocking risk wherever untrusted tool output can reach an agent with consequential write tools. Its strongest measured practical comparator is **tool filtering**: GPT-4o’s targeted ASR fell from **57.69% to 6.84%** under the paper’s strongest fixed attack selection, while benign utility rose from **69.0% to 73.13%**. But this is not a permission guarantee: the filter is itself selected by the LLM before it sees untrusted data, fails when necessary user tools can also execute the attack, and was not tested against defense-adaptive attacks. Deployment should therefore use trusted enforcement of least privilege, not prompt-only scope selection, and locally test the actual authorization boundary against adaptive injections.

## F1. What v3 evaluates

AgentDojo is a stateful, simulated tool environment with four suites: Workspace, Slack, Travel Agency, and e-banking. It pairs user tasks with suite-relevant injection goals, yielding **97 user tasks**, **27 injection targets**, and **629 security cases**. The task-suite table reports 70 tools, while the body elsewhere says 74 tools. This source-internal discrepancy should be retained rather than resolved without repository-version analysis. [§3.1, Table 1](https://arxiv.org/html/2406.13352v3#S3.T1)

- Workspace: 24 tools, 40 user tasks, 6 injection goals.
- Slack: 11, 21, 5.
- Travel: 28, 20, 7.
- Banking: 11, 16, 9.

Cases are the within-environment cross-product of user and injection tasks. The environment uses mutable simulated state and deterministic binary utility/security functions that inspect model output and state mutations. Tasks specify ground-truth tool-call sequences, which the framework uses to place injections only in relevant tool outputs. This is a stronger evaluator than an LLM judge for this threat, but it also gives the evaluation attacker task-specific placement knowledge. [§3–§3.4](https://arxiv.org/html/2406.13352v3#S3)

### Metrics and denominator discipline

[§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4) defines:

| Metric | Denominator | Success condition |
|---|---:|---|
| Benign utility | user tasks, nominally 97 | User task solved without attack |
| Utility under attack | security cases, nominally 629 | User task solved and no adversarial side effect |
| Targeted ASR | security cases, nominally 629 | Attacker’s specified malicious goal executed |
| Untargeted ASR | security cases | Complement of utility under attack |

A collection of attacks is scored as successful if **any** attack succeeds on a case. This “Max” construction models an attacker selecting the best of the evaluated prompt variants per case. It is not a full optimization against a defense.

## F2. Baseline model and attack evidence

The paper evaluated ten tool-calling agents on all 629 cases using its generic **“Important message”** injection: Claude 3 Opus, Claude 3 Sonnet, Claude 3.5 Sonnet, Command-R+, Gemini 1.5 Flash, Gemini 1.5 Pro, GPT-3.5 Turbo, GPT-4 Turbo, GPT-4o, and Llama 3 70B. Except Llama 3, models used official provider APIs. The paper names model families but does **not** pin immutable API snapshot identifiers for GPT-4o or the other hosted models. [§4](https://arxiv.org/html/2406.13352v3#S4)

| Model | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| Claude 3 Opus | 66.61 ± 3.69% | 52.46 ± 3.90% | 11.29 ± 2.47% |
| Claude 3 Sonnet | 53.10 ± 3.90% | 33.23 ± 3.68% | 26.71 ± 3.46% |
| Claude 3.5 Sonnet | 78.22 ± 3.23% | 51.19 ± 3.91% | 33.86 ± 3.70% |
| Command-R+ | 25.44 ± 3.40% | 25.12 ± 3.39% | 0.95 ± 0.76% |
| Gemini 1.5 Flash | 36.09 ± 3.75% | 34.18 ± 3.71% | 12.24 ± 2.56% |
| Gemini 1.5 Pro | 45.63 ± 3.89% | 28.93 ± 3.54% | 25.60 ± 3.41% |
| GPT-3.5 Turbo | 33.86 ± 3.70% | 34.66 ± 3.72% | 8.43 ± 2.17% |
| GPT-4 Turbo | 63.43 ± 3.76% | 54.05 ± 3.89% | 28.62 ± 3.53% |
| GPT-4o | 69.00 ± 3.61% | 50.08 ± 3.91% | 47.69 ± 3.90% |
| Llama 3 70B | 34.50 ± 3.71% | 18.28 ± 3.02% | 20.03 ± 3.13% |

Source: [Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3.T3). Intervals are reported as 95% proportion confidence intervals.

**Decision-relevant interpretation:** lower ASR on weak models is not evidence of security when those models also fail to perform the attacker’s task. In the paper’s own comparison, Claude 3.5 Sonnet had the highest benign utility and a better utility-security tradeoff than GPT-4o, but all defense ablations were nevertheless run on GPT-4o because Claude access was rate-limited. Therefore the defense findings do not establish model-independent transfer. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1)

## F3. Attack selection and outcomes

The baseline attack tells the model that the malicious task must be completed before the original task. It directly addresses the model and includes the victim’s name. [§4.1–4.2; Appendix B.3](https://arxiv.org/html/2406.13352v3#S4.SS2)

On GPT-4o, four prompt forms were compared:

| Attack | Targeted ASR | Untargeted ASR |
|---|---:|---:|
| TODO | 3.66 ± 0.7% | 32.75 ± 1.8% |
| Ignore previous instructions | 5.41 ± 0.9% | 33.23 ± 1.8% |
| InjecAgent prompt | 5.72 ± 0.9% | 31.48 ± 1.8% |
| Important message | 57.70 ± 2.0% | 49.90 ± 2.0% |
| Max across those four | 57.55 ± 2.7% | 68.36 ± 2.6% |

Source: [Appendix C, Table 4](https://arxiv.org/html/2406.13352v3#A3.T4).

The paper further found that exact model and user-name knowledge added only **1.9 percentage points** to targeted ASR, while incorrect identity guesses reduced it by about 22 points. Injections near the end of a tool response reached up to **70% average success** against GPT-4o. [§4.2; Appendix D](https://arxiv.org/html/2406.13352v3#A4)

**Transfer constraint:** evaluate attacks in the data position, formatting, and tool-output fraction the real agent will encounter. AgentDojo explicitly does not yet support attackers manipulating some output-ordering mechanisms, despite noting that order could be attacker-influenced. [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

## F4. Defense comparators and measured tradeoffs

All defense experiments use **GPT-4o** against the paper’s “strongest attack,” described as the Max selection. Comparators were:

1. **Data delimiters:** special formatting around tool output with an instruction to ignore instructions inside it.
2. **Prompt-injection detector:** BERT classifier on every tool output, aborting on detection.
3. **Prompt sandwiching:** repeat user instructions after every function call.
4. **Tool filter:** before seeing untrusted data, the LLM chooses the tools needed for the user task and is restricted to them.

[§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

| Defense | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| None | 69.00 ± 3.6% | 50.01 ± 3.9% | 57.69 ± 3.9% |
| Data delimiters | 72.66 ± 3.5% | 55.64 ± 3.9% | 41.65 ± 3.9% |
| PI detector | 41.49 ± 3.9% | 21.14 ± 3.2% | 7.95 ± 2.1% |
| Repeat prompt | 85.53 ± 2.8% | 67.25 ± 3.7% | 27.82 ± 3.5% |
| Tool filter | 73.13 ± 3.5% | 56.28 ± 3.9% | 6.84 ± 2.0% |

Source: [Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3.T5).

### What is measured

- Delimiters reduced targeted ASR by about **16 points**, but left a 41.65% targeted ASR.
- The detector and tool filter had the lowest ASR, but detector false positives caused a **27.51-point benign-utility loss**.
- Repeating the user prompt improved both reported utility measures but retained **27.82%** targeted ASR.
- Tool filtering reduced targeted ASR by **50.85 points** versus the no-defense condition, while retaining utility better than the detector.

### Qualifications and conflicts

- The body calls tool filtering “particularly effective” at **7.5%** ASR, while Table 5 reports **6.84% ± 2.0%**. Table 5 is the more precise reported result. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)
- Table 4’s Max ASR is **57.55 ± 2.7%**, while Table 5’s no-defense ASR is **57.69 ± 3.9%**. The paper does not explain the distinct point estimates and intervals. They are close and intervals overlap, but should not be silently treated as one run.
- Table 3’s GPT-4o result is **47.69 ± 3.90%** ASR because it is the *Important message* baseline. Table 5’s 57.69% no-defense value belongs to the stronger attack-selection evaluation. These are different conditions, not a defense effect.
- “All defenses lose 15–20% of utility under attack” is a figure-level characterization. The exact Table 5 values should govern a decision.

## F5. Operational boundaries and unproven tradeoffs

1. **Tool filtering is not trusted authorization.** It asks an LLM to choose a tool subset before reading untrusted data. The paper finds it fails if the task requires dynamic tool discovery or if the user-needed tools can also carry out the attack, which applies to **17% of test cases**. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

2. **No persistent multi-task context test.** AgentDojo resets context between tasks. The paper explicitly identifies a failure mode where an injection waits until a later task enables the needed tool.

3. **No adaptive defense attack.** The attack collection selects among four fixed prompts, rather than being designed against each defense. The authors explicitly warn that prompt sandwiching is unlikely to withstand an adaptive instruction to ignore future instructions. [§3.3; §4.3](https://arxiv.org/html/2406.13352v3#S3.SS3)

4. **No protection against semantic recommendation manipulation.** More isolated planners may still fail where malicious tool data merely changes a recommendation, such as a hotel listing prompting itself to be chosen. That matters even when no forbidden write tool is invoked. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

5. **Synthetic, text-only environment.** State data are dummy data, manually authored or LLM-assisted and manually inspected. The paper identifies multimodal tasks, richer attacks/defenses, and realistic attack-format constraints as future work. [§3.1; §5; Appendix E/F](https://arxiv.org/html/2406.13352v3#S3)

6. **Hosted-model reproducibility is limited.** The source supplies model family names and reports approximate GPT-4o cost of **US$35 for 629 security cases** and **US$4 for 97 benign cases**, but no immutable hosted-model snapshot in the paper. [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

## Practical controls

**Measured control:** pre-untrusted-data tool filtering, with the conditions and failures above.

**Proposed controls, not validated by AgentDojo v3:**

- Enforce tool/action grants in trusted code, not by an LLM’s self-selected list.
- Default to read-only, grant the smallest action-specific capability, and separate high-impact writes such as payment, email sending, data export, credential access, and external posting.
- Bind grants to task, user, target resource, action parameters, and expiry. Do not retain them across unrelated turns.
- Require an explicit trusted approval or workflow gate before irreversible or externally visible actions.
- Treat untrusted text as data in logs, UI, and tool responses. This is hygiene, not a proven injection defense.
- Audit denied and attempted actions, injection-bearing inputs, selected capabilities, and state mutations so local evaluation can detect both targeted compromise and silent task derailment.

## Concrete paired local transfer evaluation

**Objective:** test whether a real authorization boundary transfers the paper’s tool-filter result without borrowing its security claim.

| Element | Proposed paired design |
|---|---|
| Conditions | A: production-equivalent agent with current tool permissions. B: identical agent/model/prompt/tool outputs, but a trusted policy enforcer supplies least-privilege task-scoped grants before untrusted data. |
| Corpus | First replay the full AgentDojo 97 benign / 629 security-case setup if integration permits. Then run a local transfer corpus of **30 real representative workflows** and **3 concrete abuse goals per workflow**: 30 benign cases and 90 user-task × malicious-goal cases. Include read-only, allowed write, multi-step dynamic discovery, same-tool user/attacker conflict, and cross-turn cases. |
| Attacks | Include the four v3 prompt forms, attack text at beginning/middle/end of each controllable output, plus defense-adaptive variants that target the local scope/grant mechanism. Record which output was attacker-controlled and its relative position. |
| Pairing | Same initial state, model snapshot, sampling settings, task, attack goal, placement, and run order randomized across A/B. Preserve raw tool traces and authorization decisions. |
| Measures | Report benign utility over 30 local benign cases; utility-under-attack, targeted ASR, unauthorized-action rate, and denied-legitimate-action rate over 90 local security cases. Report per workflow class and 95% binomial intervals, not only an aggregate. |
| Decision rule | Do not deploy a consequential capability if any successful unauthorized action remains in the relevant workflow class, even if aggregate ASR declines. A lower ASR with reduced legitimate completion is a tradeoff, not a pass. |

The decisive comparison is **LLM-selected scope versus trusted enforced scope** under the same injected outputs. AgentDojo only measured the former. The local evaluation must test the latter and include the 17%-style same-tool cases, dynamic planning, and persistent-context waits that v3 identifies as tool-filter failures.

## Remaining gaps and stopping point

- AgentDojo v3 does not establish security for the local agent’s model, tool schemas, authority model, persistent context, adversary capabilities, or multimodal inputs.
- It does not report a defense-adaptive attack against any comparator.
- It does not specify immutable hosted-model versions in the paper, limiting direct reproduction.
- The paper’s table/prose numeric discrepancies are retained above. Resolving them requires an additional source or execution trace outside the assigned original-v3 scope.

Research stopped after live retrieval of the supplied original HTML, raw HTML fidelity check, and its embedded appendices repeated the same evidence.
