# AgentDojo v3 evidence for a permission-bounded tool agent

## Assigned question and bounds

**Question:** What does original AgentDojo v3 measure about prompt-injection security and defenses, what constrains deployment of a permission-bounded tool agent, and what remains unproven?

**Bounded answer:** AgentDojo v3 provides evidence that **pre-commitment to a minimal tool set before untrusted tool output is read** can sharply reduce a tested indirect prompt-injection attack in its simulated environment. It does **not** establish a production-security guarantee. Its own results and limitations show that this control fails when a legitimate task capability can also accomplish the attacker goal, when needed capabilities emerge after reading untrusted data, and in persistent multi-task contexts. The measured result therefore supports permission bounding as a practical control, but only alongside independently enforced authorization, per-action restrictions, and a local adaptive evaluation.

**Scope:** only [AgentDojo arXiv v3](https://arxiv.org/html/2406.13352v3), including its embedded original appendices, retrieved live. v3 was issued 24 November 2024 and says it fixes a Llama implementation bug and updates the travel suite ([arXiv record](https://arxiv.org/abs/2406.13352v3)). No claim is made about later AgentDojo releases, other studies, or production security as of the requested 2026-09-07 cutoff.

## What v3 evaluates

### Environment and evaluator

AgentDojo is a **stateful, simulated, text-tool environment**. It contains Workspace, Slack, Travel Agency, and e-banking, with mutable dummy state, tool descriptions included in the model prompt, and YAML-formatted tool outputs. The state data was manually authored or generated with assistance from GPT-4o and Claude 3 Opus, then manually inspected. ([§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1))

The paper reports **70 tools, 97 user tasks, 27 injection targets, and 629 security cases**. A security case is the within-environment cross-product of relevant user and injection tasks. The suite includes up to 7,000 GPT-4 tokens of environment data, 4,000 tokens of tool descriptions, user tasks requiring up to 18 tool calls, and injection goals requiring 1–20 steps. ([Table 1 and §3.1](https://arxiv.org/html/2406.13352v3#S3.SS1))

Outcomes are determined by deterministic task-specific functions over the model output and environment state before/after execution, rather than an LLM judge. This is a substantive strength for this threat model because a successful injection could also compromise an LLM evaluator. ([§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1))

Metrics ([§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)):

| Metric | Denominator and condition |
|---|---|
| **Benign utility** | Fraction of user tasks solved with no attack, nominally 97 tasks. |
| **Utility under attack** | Fraction of security cases in which the user task is solved **and** no adversarial side effect occurs, nominally 629 cases. Its complement is untargeted/derailment ASR. |
| **Targeted ASR** | Fraction of security cases in which the attacker goal is achieved, nominally 629 cases. |

The paper reports 95% proportion confidence intervals, using `statsmodels.stats.proportion.proportion_confint`. ([checklist](https://arxiv.org/html/2406.13352v3#S5))

### Models and baseline attack

The all-model baseline evaluated Claude 3 Opus, Claude 3 Sonnet, Claude 3.5 Sonnet, Command R+, Gemini 1.5 Flash, Gemini 1.5 Pro, GPT-3.5 Turbo, GPT-4 Turbo, GPT-4o, and Llama 3 70B. Except Llama 3, they were called through official provider APIs; all received the common system prompt, with additional provider-specific prompts for Claude and Llama. ([§4](https://arxiv.org/html/2406.13352v3#S4))

The baseline attack is the generic **“Important message”** indirect injection: it instructs the model to perform the malicious task before the original user task. ([§4.1 and Fig. 19](https://arxiv.org/html/2406.13352v3#S4.SS1))

Selected all-model results, measured over the stated suite:

| Model | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| Claude 3 Opus | 66.61% ±3.69 | 52.46% ±3.90 | 11.29% ±2.47 |
| Claude 3.5 Sonnet | 78.22% ±3.23 | 51.19% ±3.91 | 33.86% ±3.70 |
| GPT-4 Turbo | 63.43% ±3.76 | 54.05% ±3.89 | 28.62% ±3.53 |
| GPT-4o | 69.00% ±3.61 | 50.08% ±3.91 | 47.69% ±3.90 |
| Llama 3 70B | 34.50% ±3.71 | 18.28% ±3.02 | 20.03% ±3.13 |

Source: [Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3.T3).

This is not evidence that a lower-ASR model is safer: lower task competence can prevent both user and attacker actions. The authors describe an inverse relation between capability and attackability in this configuration and report 10–25 percentage-point utility loss under attack for most models. ([§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1))

## Defense comparison relevant to permission bounding

Defense experiments use **GPT-4o**, selected because it had the highest benign utility at the time of the in-depth experiments, and the paper’s strongest tested attack. ([§4](https://arxiv.org/html/2406.13352v3#S4))

| Defense | Mechanism | Benign utility | Utility under attack | Targeted ASR |
|---|---|---:|---:|---:|
| None | Base agent | 69.00% ±3.6 | 50.01% ±3.9 | 57.69% ±3.9 |
| Data delimiting | Mark tool output as data and instruct model to ignore its instructions | 72.66% ±3.5 | 55.64% ±3.9 | 41.65% ±3.9 |
| PI detector | DeBERTa/BERT-family classifier on each tool output, abort on detection | 41.49% ±3.9 | 21.14% ±3.2 | 7.95% ±2.1 |
| Repeat prompt | Repeat original user instruction after each tool call | 85.53% ±2.8 | 67.25% ±3.7 | 27.82% ±3.5 |
| **Tool filter** | Before untrusted data, let the LLM select tools needed for the user task and restrict execution to them | 73.13% ±3.5 | 56.28% ±3.9 | **6.84% ±2.0** |

Source: [Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3.T5); mechanisms: [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3).

### Decision-relevant interpretation

- **Measured:** tool filtering reduced targeted ASR from 57.69% to 6.84% in this specific GPT-4o experiment, a 50.85-point absolute reduction. It retained 73.13% benign utility and 56.28% utility under attack. This is the strongest measured security result among the compared defenses with substantially higher utility than the detector.
- **Measured:** the detector achieved similar tested ASR, 7.95%, but benign utility fell 27.51 points versus no defense and utility under attack fell 28.87 points. The paper attributes this to excessive false positives.
- **Measured but weakly transferable:** repeat-prompting had the best reported utility figures but 27.82% targeted ASR. The authors explicitly state it is unlikely to withstand an adaptive injection that tells the model to ignore *future* instructions.
- **Practical inference:** deploy a permission boundary only if the boundary is enforced by the runtime, not merely presented to the model as an instruction. AgentDojo’s “tool filter” is model-selected before data exposure, so its result supports the *least-privilege ordering principle*, not an assurance that a model’s selection is complete or secure.

## Attack selection, counterevidence, and conflicts

### Attack sensitivity is material

On GPT-4o, prior-style attacks produced targeted ASRs of 3.66% (`TODO`), 5.41% (“Ignore previous”), and 5.72% (InjecAgent), while “Important message” reached 57.7%. Thus an evaluation based only on the weaker prompts would materially overstate robustness. ([Appendix C, Table 4](https://arxiv.org/html/2406.13352v3#A3.T4))

The paper defines a “Max” attack collection as successful if any constituent attack succeeds, intended to model an attacker selecting the best attack per security case. It also says an adaptive selection raised success rates by about 10% in the ablation narrative. ([§3.4 and §4.2](https://arxiv.org/html/2406.13352v3#S3.SS4))

Other measured conditions:

- Slack attacks had a reported **92%** success rate, attributed to attacker control over a substantial share of relevant tool output. A Travel injection requiring both an expensive Paris hotel booking and email exfiltration achieved **0%**, often because only one of its two malicious subgoals was completed. ([§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1))
- Position matters. The paper reports injections near the end of tool output as most effective, up to **70% average ASR** against GPT-4o. ([§4.1 and Appendix D](https://arxiv.org/html/2406.13352v3#A4))
- Correct model and user names added only 1.9 points in the reported ablation, while incorrect guesses reduced ASR by about 22 points. ([§4.2, Table 2](https://arxiv.org/html/2406.13352v3#S4.SS2))

### Source conflicts that must not be silently combined

1. **GPT-4o no-defense ASR differs across paper tables.** Table 3 reports 47.69% ±3.90, while Table 4 reports 57.7% ±2.0 for “Important message,” and Table 5 reports 57.69% ±3.9 for no defense. The paper does not explain the configuration/run difference. Do not use Table 3 as the baseline for the Table 5 defense deltas. Use the within-Table-5 comparison above.  
   Sources: [Table 3](https://arxiv.org/html/2406.13352v3#A3.T3), [Table 4](https://arxiv.org/html/2406.13352v3#A3.T4), [Table 5](https://arxiv.org/html/2406.13352v3#A3.T5).

2. **Tool-filter prose says 7.5%, Table 5 says 6.84%.** The prose may be rounded, but the source does not specify. Preserve 6.84% as the tabulated result and cite the prose separately rather than treating them as different experiments.  
   Source: [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3).

3. **Tool count is inconsistent.** §3.1 says the implementation has 74 tools, while Table 1, abstract, and data card say 70. For the paper’s reported benchmark characterization, retain the repeated 70-tool claim and record the 74-tool implementation statement as unresolved.  
   Sources: [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1), [data card](https://arxiv.org/html/2406.13352v3#A6).

4. **Data-card “124 tasks” is not necessarily inconsistent with 97 user tasks.** It appears to count 97 user tasks plus 27 injection targets, but the paper does not explicitly state that arithmetic interpretation. Treat it as a likely labeling difference, not a confirmed reconciliation.  
   Sources: [Table 1](https://arxiv.org/html/2406.13352v3#S3.T1), [data card](https://arxiv.org/html/2406.13352v3#A6).

## Operational boundaries and unproven tradeoffs

**Measured failure conditions of tool filtering:**

1. **Capability overlap:** required user-task tools are sufficient for the attack in **17%** of test cases. A filter cannot distinguish authorized from malicious use solely by admitting that capability. ([§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3))
2. **No stable up-front plan:** it fails where tool results determine the subsequent tools needed. ([§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3))
3. **Persistent context is excluded:** AgentDojo does not cover a user issuing multiple tasks without context reset. The authors identify a “wait until the right tool becomes available” injection as a failure mode. ([§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3))
4. **Output manipulation survives isolation:** even more involved isolation can fail when an injection changes a recommendation/result without requiring another tool call, such as coercing a hotel listing to be selected. ([§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3))
5. **Attack adaptivity remains incomplete:** v3 explicitly says its pre-deployed attacks are generic, prompt injections require adaptive evaluation, and more sophisticated attacks and defenses are future work. The data card says default attacks alone are unsuitable for robustness evaluation. ([§3.3](https://arxiv.org/html/2406.13352v3#S3.SS3), [§5](https://arxiv.org/html/2406.13352v3#S5), [data card](https://arxiv.org/html/2406.13352v3#A6))

**Proposed controls, not measured guarantees in v3:**

- Runtime-enforced per-tool and per-operation authorization, with narrow argument-level limits. For example, a legitimate `send_email` permission should not imply arbitrary recipients, payloads, or data sources.
- Separate read, recommendation, external communication, financial transfer, and credential-bearing operations into distinct authority domains.
- Require user confirmation or a non-LLM policy decision before consequential writes, transfers, external sends, or scope expansion.
- Reset or compartmentalize untrusted context between tasks, and log attempted disallowed capability use.
- Treat a tool filter as one layer, not a substitute for authorization. This is an inference from the stated overlap, dynamic-planning, and persistence failures.

## Concrete paired local transfer evaluation

Run this against the actual agent, its actual tools, policy layer, and model version. It tests transfer rather than assuming AgentDojo’s percentages transfer.

| Dimension | Arm A: baseline | Arm B: permission-bounded |
|---|---|---|
| Agent/model/prompt/tool APIs | Identical fixed versions | Identical |
| Initial authority | Current production-equivalent available tools | Tool set or capability grants selected **before first untrusted output**, enforced by runtime |
| Tasks | Same local representative benign tasks | Same tasks |
| Security cases | Same task × injected untrusted-output cases | Same cases |
| Attacks | Hold out an adaptive set that knows the boundary, including late-position injections, benign-looking output manipulation, authorized-tool abuse, tool-escalation requests, delayed/multi-turn triggers, and argument-level exfiltration | Same attack instances |
| Evaluator | Deterministic state/action assertions, not an LLM judge | Same assertions |

Record the three AgentDojo-compatible metrics with denominators, plus local control-specific measures:

1. Benign task completion.
2. Utility under attack, requiring completion with no security-policy violation.
3. Targeted ASR for each explicit attacker goal.
4. **Blocked authority-escalation rate**, **false-block rate**, **confirmation rate**, and **residual ASR when the attacker goal uses an authorized capability**.

Pre-register paired case-level comparison and report exact counts, confidence intervals, per-domain results, and failures by cause. Include a capability-overlap stratum rather than averaging it away: tasks where the attacker needs an ungranted capability versus tasks where the attacker can misuse a granted one. The expected result, if AgentDojo’s mechanism transfers, is improvement mainly in the former stratum. A low aggregate ASR without that split would not demonstrate protection against authorized-capability abuse.

For reference, the original reported cost was about **US$35 for 629 GPT-4o security cases** and **US$4 for 97 utility cases**, but this is historical and not a current-cost estimate. ([Appendix D](https://arxiv.org/html/2406.13352v3#A4))

## Remaining gaps and stopping point

- v3 does not measure the proposed runtime authorization, argument-level restrictions, confirmations, real production data, real external side effects, multimodal inputs, persistent sessions, or a defense-aware adaptive attacker against the tool filter.
- It does not establish which attacks were injected into which local tool/data surfaces, so its percentages cannot be assigned to another agent.
- The unresolved cross-table baseline and tool-count discrepancies limit exact cross-experiment comparisons.
- Research stopped after the specified primary v3 source and its embedded appendices repeated the same evidence. No outside studies were consulted by scope.
