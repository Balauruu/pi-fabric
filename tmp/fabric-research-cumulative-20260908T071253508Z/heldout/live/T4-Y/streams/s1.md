# Research note: Software Factory Playbook and Wayfinder for Pi architectural work

## Assigned question and bounded answer

**Question.** As of **2026-09-07**, what do Maciej Dziuba’s Software Factory Playbook and Matt Pocock’s Wayfinder prescribe for architectural analysis and decisions, where do they complement rather than duplicate each other, and what remains necessary in Pi?

**Answer.** They address different control problems:

- **Software Factory Playbook** is a **feature-delivery governance workflow**: progressively commit product, architecture, program design, then reviewable vertical implementation slices with explicit human approval. Its architecture work is deliberately concise and implementation-facing.
- **Wayfinder** is a **multi-session uncertainty-management workflow**: maintain a tracker-backed, dependency-aware map of decision questions, resolve one decision at a time, and stop at a clear route rather than automatically implementing.

Use **Wayfinder first** only when the destination or major decisions are genuinely unclear across more than one agent session. Use **Software Factory** after the route is clear, for the feature’s product-to-slice execution. Neither is itself a sufficiently deep architecture-analysis method. Pi should add evidence-led repository investigation and explicit architectural judgment before approving Software Factory Gate 2.

## Findings

### F1. Software Factory is a gated implementation contract, not a general architecture decision method

The Playbook mandates four sequential human-approved gates and forbids implementation code before Gate 4’s slice plan is approved. [Canonical source](https://gist.githubusercontent.com/Maciejdziuba/88890d7e0eeefa5a8738bbe9fd5e20b8/raw/SKILL.md)

| Gate | Required artifact and judgment |
|---|---|
| Product | User problem, measurable success metric, announcement, and throwaway plain-HTML screen mockups. Technical language is prohibited. |
| Architecture | Existing-system fit, endpoints, data/query outlines, main end-to-end flow, and external systems or environment-variable names. It explicitly says to read relevant existing code first. |
| Program design | Changed/created files and rationale, types and signatures without bodies, call stacks, planned test assertions, and least-confident decisions. |
| Vertical slices | Approved slice plan, then tracer bullet first, happy path second, and one independently testable capability per later slice. |

**State and authority boundary.** It persists artifacts in `docs/plans/<feature-slug>/`, beginning with `00-status.md`. The status records approval state and completed slices. A later discovery that invalidates an earlier approval requires returning that gate to in-progress and obtaining approval again. Approval is unambiguously human authority.

**Implementation boundary.** The source requires disk writes for plans, mockups, status tracking, optional ADRs, and external-context documentation. It also instructs running/curling/browser-testing each slice. Those are prescribed actions, not capabilities demonstrated by the source.

**Assumptions.**

- The work is a real feature, roughly multi-file or a review-hostile diff of about 100+ lines.
- A human can make meaningful approvals at each gate.
- The agent can inspect the existing codebase before architecture planning.
- The project can safely store decision artifacts under `docs/`.
- A thin end-to-end tracer bullet is technically feasible.

**Explicit exclusions.** Skip the process for trivial edits, explicitly process-free work, throwaway code, and pure prototypes.

**Failure modes and transfer limits.**

- Gate 2 requests a fit, endpoints, data, flow, and external dependencies, but provides no method for evaluating alternatives, quality attributes, dependency direction, failure domains, migration/rollback, security boundaries, operational consequences, or trade-offs.
- Its “least confident decisions” list exposes uncertainty but does not prescribe how to acquire evidence or decide it.
- The fixed sequence can introduce ceremony and delay on small or rapidly changing work.
- A tracer bullet proves wiring, not correctness, performance, security, resilience, data-migration safety, or operational readiness.
- “Prove it works” has no stated acceptance threshold beyond running, curling, or browser testing.

### F2. Wayfinder is a decision-frontier and collaboration protocol, not a feature plan

Wayfinder is explicitly for work “more than one agent session can hold.” It turns a loose idea into a tracker-backed map of **decision tickets**, where a ticket resolves a decision rather than an implementation slice. [Canonical source](https://raw.githubusercontent.com/mattpocock/skills/main/skills/engineering/wayfinder/SKILL.md)

**Method.**

1. Define the destination first, using grilling and domain modeling.
2. Breadth-first map the first decision frontier and fog of war.
3. Create one canonical map issue labelled `wayfinder:map`.
4. Create only presently specifiable child decision tickets, then wire dependency edges.
5. Resolve research tickets in parallel through subagents.
6. In later sessions, claim one frontier ticket before working it, resolve it, record the resolution as a comment, close it, add a one-line linked index entry, and graduate newly specific fog into tickets.

**State model.**

- **Map issue:** low-resolution index with Destination, Notes, Decisions so far, Not yet specified, and Out of scope.
- **Decision ticket:** one sharply stated question, sized for one 100K-token agent session.
- **Frontier:** open, unblocked, unclaimed tickets.
- **Fog:** in-scope uncertainty not yet sharp enough to make a ticket.
- **Out of scope:** consciously excluded work that never graduates unless a new effort redraws the destination.
- **Claim:** assignment to the responsible developer before work, preventing concurrent sessions from duplicating it.

**Authority and permission boundaries.**

- HITL tickets require a human who speaks for themselves. The agent must not answer its own grilling questions.
- AFK research may be delegated to subagents.
- The workflow assumes permission and configured operations for issue creation, labels, child relationships, dependency edges, assignment, comments, closure, querying, and possibly branch creation.
- It says tracker-specific operations must be supplied. Without one, it defaults to a local-Markdown tracker, but the source does not define that tracker’s concrete implementation.
- By default it plans, not implements. Execution is allowed only when an effort’s Notes explicitly override that default.

**Ticket types.**

- **Research, AFK:** acquire external or local facts needed for a decision.
- **Prototype, HITL:** make a cheap artifact for a human reaction.
- **Grilling, HITL:** conversation and decision clarification.
- **Task, HITL or AFK:** non-decision work needed to unblock a decision, such as access provisioning or data movement.

**Failure modes and transfer limits.**

- A dependency graph renders workflow state and availability. It is not evidence that an architectural choice is sound.
- Assignment is a weak concurrency control mechanism if people do not claim promptly, assignments are stale, or tracker permissions/configuration differ.
- The “one non-research ticket per session” rule can slow tightly coupled work.
- Ticket proliferation, vague destination statements, or premature decomposition can convert uncertainty into administration rather than reduce it.
- Parallel research increases coordination and provenance burden. The source requires a context pointer, but does not define evidence standards, conflict resolution, or synthesis criteria.
- The method does not define an ADR format, architectural acceptance criteria, or a test for whether a resolved decision is correct.

## Comparison and complementarity

| Concern | Software Factory | Wayfinder | Combined use |
|---|---|---|---|
| Primary unit | A feature progressing to code | A decision under uncertainty | Use Wayfinder to make high-impact choices, then Factory to deliver the selected route |
| State store | Repository documents and status file | Issue tracker map, tickets, dependencies, comments | Keep decision detail in its canonical system and cross-link |
| Human authority | Approval at every gate and slice boundary | Human must resolve HITL tickets | Keep both. Wayfinder does not replace product/design approval |
| Architecture | One Gate 2 template plus Gate 3 interfaces and tests | Decomposes questions, does not answer them | Evidence acquisition and architecture judgment must be inserted before Gate 2 approval |
| Delivery | Prescribes vertical slices and validation | Explicitly planning by default | Factory owns implementation follow-through |
| Multi-session handling | Resume from plan documents | Shared dependency-aware frontier | Wayfinder scales uncertainty. Factory preserves one feature’s approved execution context |

**Decision:** Do not substitute one for the other. Wayfinder is not a richer Software Factory Gate 2, and Software Factory’s gate documents are not a shared decision frontier.

**Packaging and compatibility.**

- Software Factory claims compatibility with “any agent that supports the `SKILL.md` format,” naming Claude Code and Amp. That is a conditional packaging claim, not proof of Pi compatibility, installation, invocation semantics, permission handling, or safe execution.
- Wayfinder is itself a `SKILL.md` with `disable-model-invocation: true`. It assumes a generic Skill tool and a configured tracker-operation layer. It makes no Pi-specific compatibility claim.
- No source establishes that either workflow is installed, enabled, or runnable in Pi. Neither source supplies a security model.

## Recommended operating workflow

### A1. Evidence acquisition

For a multi-file feature, begin with a bounded, read-only repository investigation. Record:

- relevant modules, runtime path, interfaces, data ownership, existing conventions, and tests
- external dependencies and permission boundaries
- competing options and unknowns
- evidence links/paths and confidence

Do not approve Factory Gate 2 from a navigation graph or a catalog listing alone.

### A2. Architectural judgment

If a question is sharp but unresolved, make it a Wayfinder decision ticket. Use evidence plus explicit criteria such as fit, coupling, failure isolation, data integrity, migration/rollback, security, operability, cost, and reversibility. Keep the chosen option, rejected alternatives, assumptions, and invalidation triggers in the ticket resolution.

If the route is already clear in one session, skip Wayfinder as its source prescribes and proceed directly to the applicable Factory gates.

### A3. Decision recording

- Keep the detailed cross-session decision in the Wayfinder ticket when Wayfinder is used.
- Put feature-specific approved design in Software Factory’s Gate 2 and Gate 3 documents.
- Create an ADR only for a decision that outlives the feature. Cross-link rather than duplicate the decision verbatim.
- Treat a changed assumption or contradictory evidence as a backtrack condition, not a reason to silently amend implementation.

### A4. Implementation follow-through

After Gate 4 approval, use Factory slices:

1. tracer bullet with explicit scope and known non-goals
2. happy path
3. one capability, edge case, error path, or operational concern per slice

For every slice, define a falsifiable acceptance check before implementation, run the appropriate targeted verification, record the result, update status, and ask for re-steering.

## Conditional adoption and local evaluation

**Adopt Software Factory conditionally** for normal, review-sensitive multi-file features when a human can approve gates and repository documentation writes are acceptable.

**Add Wayfinder conditionally** when any of these are true:

- the destination cannot yet be stated precisely
- material decisions have unknown dependencies
- work exceeds one session
- several people or agents need a visible, concurrency-safe decision frontier
- external research, access, or prototypes block architectural judgment

**Do not adopt Wayfinder for a small, already-clear route.** Its own source says not to create a map in that case.

### Evaluation that could change the choice

Run a controlled local comparison on **four to six comparable real feature proposals** that exceed the Playbook’s own multi-file/roughly-100-line threshold. Keep repository snapshot, model, tools, human reviewers, time budget, and permissions constant.

- **Control:** existing planning practice.
- **Treatment A:** Software Factory alone.
- **Treatment B:** Wayfinder for pre-design uncertainty, then Software Factory.
- **Applicable mechanism test:** proposals with a clear destination but uncertain implementation. Measure post-Gate-2/3 reversals, reviewer-requested architectural changes, time to first working end-to-end slice, escaped acceptance failures, and human review effort.
- **Exploratory test:** proposals with unclear destination or cross-team dependencies. Measure time to a human-approved decision, number of reopened/invalidated decisions, duplicated work, and unresolved blockers at handoff.

Pre-register pass/fail thresholds before beginning. For example, retain Wayfinder only if it reduces unresolved high-impact decisions or duplicate investigation without materially increasing elapsed decision time. Retain Factory only if it reduces late architectural reversals or review burden without causing unacceptable planning overhead.

This is a local decision aid, not validation of either source’s claims.

## Evidence limits and remaining gaps

- Neither source reports efficacy data. There are no outcomes, metrics, trials, baseline comparisons, participant details, resource costs, or null results to transfer.
- The sources make process claims, not measured-effectiveness claims.
- GitHub discovery signals are not efficacy evidence. The live repository metadata retrieved after the cutoff reported substantial stars and forks, and the live gist metadata reported forks/comments, but those values are post-cutoff and would indicate engagement at most.
- Maintenance evidence exists: the Playbook had three gist revisions through 2026-08-04; Wayfinder’s file history contains iterative changes through 2026-08-19, including clarification of invocation semantics and research-ticket handling. This supports active maintenance, not correctness or effectiveness.
- This stream did not survey alternative packages or execute, install, configure, mutate trackers, or test either workflow. Pi-specific installation, invocation, tracker integration, permission behavior, and effectiveness remain to be verified locally.
