# Complementary Pi Tools for Architectural Work

## Assigned question and boundary

Identify Pi-native or directly compatible skills that add repository evidence, architectural judgment, ADR recording, or implementation follow-through without duplicating the supplied Playbook and Wayfinder methods.

**Bounded recommendation:** use the already available **pi-fovea + codebase-scouting + codebase-design + domain-modeling** sequence. Do not add the investigated third-party architecture-review or repo-explorer packages by default. Consider `pi-codeontime-code-intelligence` only after a local pilot proves that persistent indexing and review improve outcomes enough to justify its larger trust and configuration surface.

No installation, execution, configuration change, or mutation was performed.

## Findings

### F1. Installed Pi stack is complementary when its roles remain separate

| Need | Tool/skill | Observed status | Material contribution | Boundary |
|---|---|---:|---|---|
| Repository evidence | `pi-fovea` | Installed locally at **0.22.1**; its `fovea_*` extension tools are registered | Cross-language graph, focused source windows, impact candidates, change obligations | Navigation/impact hypotheses, not architecture judgment or proof |
| Repository evidence discipline | `codebase-scouting` | Available locally | Bounded questions, observation ledger, re-reading decisive citations, distinguishes evidence/inference/unknowns | Does not build a graph or choose architecture |
| Architectural judgment | `codebase-design` | Available locally | Judges interfaces by depth, leverage, locality, seam placement, and dependency/test strategy | Does not establish that a proposed boundary matches actual repository behavior |
| Decision recording/domain constraints | `domain-modeling` | Available locally | Glossary challenge, concrete scenarios, ADR gate and compact ADR format | Does not validate implementation or determine an architecture unaided |

**Why this is non-duplicative:** the graph and scout process acquire evidence, `codebase-design` turns evidence and constraints into a design judgment, and `domain-modeling` records only significant decisions. None should substitute for the supplied methods’ architectural analysis.

### F2. pi-fovea is the best immediate evidence adjunct, but not an architectural authority

The installed package declares `pi-fovea` 0.22.1, Node `>=20`, a Pi extension at `src/index.ts`, a skill directory, optional `@ast-grep/cli`, and Pi API peer dependencies with `"*"` ranges. Its declared repository is [monotykamary/pi-fovea](https://github.com/monotykamary/pi-fovea). This establishes packaging intent and the local installed version, not compatibility with every Pi release or security assurance.

Its skill prescribes:

1. `fovea_sketch` for a production-first silhouette.
2. `fovea_focus` for a symbol, route, literal, environment key, or path.
3. `fovea_dwell` only when focus reports collapsed relevant neighbors.
4. `fovea_impact` before changes to obtain likely review order, causal channels, expected-but-unchanged files, and obligations.

The source explicitly says to skip it for a repository of only a few dozen files and that tests, CI, and rollout remain final verification. It supports full extraction claims for TypeScript/JavaScript, Python, Go, and Rust, with outline-oriented support for several other languages, plus literal/config and Proto/GraphQL relationships. These are publisher claims, not independently tested here.  
Sources: [installed skill specification](/home/balauru/.pi-profiles/fabric/npm/node_modules/pi-fovea/skills/pi-fovea/SKILL.md), [manifest](https://github.com/monotykamary/pi-fovea/blob/main/package.json), [README: “When not to reach for fovea”, “Install”, language coverage](https://github.com/monotykamary/pi-fovea#readme).

**Method/evidence limitation:** its README reports tests on eight cloned projects for a route-signature promotion heuristic, with junk below approximately `0.27` and real route shapes above approximately `0.75`. That is evidence about separating those signature categories under its own corpus and cutoff, not evidence of architectural-decision accuracy, task success, user productivity, precision/recall for all graph edges, or superiority to Wayfinder/Playbook. The README also names a rate–distortion benchmark command, but no published result table, comparator, sample, resource accounting, or task outcome was recovered.  
Source: [README: route-shape discovery passage](https://github.com/monotykamary/pi-fovea#readme).

**Permission/state boundary:** Fovea maintains graph/cache and sync state. Its skill says per-repository JSONL caches live in `$TMPDIR`, uses content hashes, and supports session/repository sync scopes. These implementation claims do not eliminate the broader Pi extension risk: Pi documents that extensions run with full system permissions and may execute arbitrary code. Project-local extensions load only after project trust.  
Sources: [Fovea README](https://github.com/monotykamary/pi-fovea#readme), [Pi extensions security and trust model](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/extensions.md).

### F3. The installed local skills provide the missing judgment and ADR layers

`codebase-design` defines a **deep module** as substantial behavior behind a small interface, emphasizing leverage, locality, seams, adapters, and tests across the external interface. Its linked deepening guidance distinguishes in-process, local-substitutable, owned remote, and true external dependencies, and specifies when ports/adapters are justified. This is a concrete decision lens after evidence gathering, not a graph-derived conclusion.  
Sources: [skill](/home/balauru/.pi-profiles/fabric/skills/engineering/codebase-design/SKILL.md), [dependency and testing guidance](/home/balauru/.pi-profiles/fabric/skills/engineering/codebase-design/DEEPENING.md).

`domain-modeling` requires glossary conflicts and ambiguous terms to be surfaced, scenarios used to sharpen boundaries, and an ADR only if a decision is hard to reverse, surprising without context, and results from a real trade-off. Its ADR format is deliberately compact: a title plus 1–3 sentences, optionally status, alternatives, and consequences.  
Sources: [skill](/home/balauru/.pi-profiles/fabric/skills/engineering/domain-modeling/SKILL.md), [ADR format](/home/balauru/.pi-profiles/fabric/skills/engineering/domain-modeling/ADR-FORMAT.md).

This is a useful correction to tool-led architecture: a dependency graph can show relationships, but cannot establish ownership, business meaning, preferred interface, reversibility, or a trade-off’s acceptability.

## Recommended workflow

1. **Evidence acquisition**
   - State the architectural question, decision owner, constraints, and required observations.
   - Use `fovea_sketch`, then `fovea_focus`/`fovea_impact` only to locate likely code paths and impact candidates.
   - Use `codebase-scouting` to gather targeted primary repository evidence, re-read decisive ranges, and close each observation as supported, checked-negative, or unresolved.
   - Treat graph edges, inferred coupling, and generated summaries as leads until source evidence confirms them.

2. **Architectural judgment**
   - Apply the supplied Playbook/Wayfinder analysis.
   - Use `codebase-design` to compare candidate seams and interfaces by caller knowledge, leverage, locality, dependency category, test strategy, reversibility, and failure containment.
   - Use `domain-modeling` to test disputed terms and ownership through concrete scenarios.
   - Keep facts, assumptions, options, and recommendations separately labeled.

3. **Decision recording**
   - Write an ADR only when the three local gates hold: hard to reverse, surprising later, genuine trade-off.
   - Record the decision, decisive evidence, constraints, alternatives rejected for non-obvious reasons, consequences, owner, and explicit revisit trigger.
   - Maintain `CONTEXT.md` only for domain vocabulary, not implementation detail.

4. **Implementation follow-through**
   - Run `fovea_impact` against the accepted change scope to derive review/test obligations.
   - Implement through the accepted seam, test observable behavior at that seam, and use repository CI/test commands as the completion gate.
   - Re-open the ADR if a failed obligation changes an assumption, cost, or boundary. Do not silently “make the tests pass” by changing the architectural intent.

## Conditional adoption and local evaluation

Adopt no new package unless a controlled local comparison changes this result.

**Comparator:** existing workflow above versus the same workflow plus one candidate package. Keep the same model, task set, runtime budget, repositories, and scoring rubric. Do not combine measurements across incompatible task sets.

**Sample:** include:
- a small repository where Fovea should lose on setup overhead,
- a large unfamiliar single-language repository,
- a cross-language or contract-heavy repository,
- architecture-change tasks with known affected files, tests, and accepted decisions.

**Measures:**
- evidence precision and recall against a human-created decisive-evidence set,
- time and model tokens to a citation-complete evidence packet,
- number of unsupported claims and missed affected tests/files,
- blinded reviewer score for decision rationale and ADR completeness,
- implementation pass rate and post-change regression rate.

**Adoption gates:**
- Fovea remains if it materially improves evidence completeness or time on repositories larger than the context window without increasing unsupported claims.
- A persistent-index extension is adopted only if it beats Fovea plus scouting on the same tasks and its storage, remote-embedding, secret-handling, and trust behavior pass source review.
- No tool is adopted merely because it appears in a catalog, has a package version, provides a graph, or reports fixture-only measurements.

## Provenance, compatibility, and remaining gaps

Pi supports skills from global, trusted project, package, settings, and CLI locations. It validates Agent Skills-style frontmatter but intentionally diverges by allowing the skill name to differ from its directory. This supports direct skill portability at the specification level, not behavioral equivalence across harnesses.  
Source: [Pi skills documentation](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/skills.md).

Pi packages can declare skills/extensions in `package.json`; packages run with full system access, and Pi recommends reviewing third-party source. Versioned npm references and Git tags/commits can be pinned, but pinning constrains updates rather than proving safety or compatibility.  
Source: [Pi packages documentation](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/packages.md).

**Gaps and stop condition:**
- No package-download counts, stars, user adoption data, independent security audit, reproducible external benchmark, or peer-reviewed decision-effectiveness study was found or treated as evidence.
- No current runtime compatibility probe was run. The local Fovea package version and registered tool names are observed, but effectiveness and behavior on a target repository remain untested.
- The fetched `main`-branch source documents are mutable. They establish current published specifications at retrieval, not an immutable 2026-09-07 release snapshot. Pin commits before any adoption decision.
