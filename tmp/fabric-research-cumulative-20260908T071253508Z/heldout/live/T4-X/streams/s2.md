# Complementary Pi Tools Research Note

## Assigned question and bounded answer

Which current Pi skills/extensions or directly compatible skills materially complement the supplied architecture methods, without duplicating them?

**Recommendation:** adopt the already configured **pi-fovea** selectively for repository evidence and change-impact follow-through, and use the directly compatible **codebase-design** and **domain-modeling** skills for architectural judgment and ADR capture. Do not add a second architecture-mode or spec-workflow package without a separate evaluation. They primarily duplicate the core methods rather than fill an evidentiary, judgment, or recording gap.

This is a source-based snapshot at the requested **2026-09-07** cutoff. No package was installed, executed, configured, or modified.

## Findings

### F1. `pi-fovea` is complementary evidence navigation, not architecture judgment

`pi-fovea` builds a cross-language repository graph, then offers progressively scoped `sketch`, `focus`, `dwell`, and `impact` operations. Its documented `impact` result includes causal paths, expected-but-unchanged co-change companions, coverage gaps, and an obligation ledger. It explicitly says project tests, CI, review, and rollout remain separate final gates.  
Sources: [README: purpose, commands, limitations](https://github.com/monotykamary/pi-fovea/blob/main/README.md), [local skill](file:///home/balauru/.pi-profiles/fabric/npm/node_modules/pi-fovea/skills/pi-fovea/SKILL.md).

**Best fit:** evidence acquisition before an architectural decision, and impact/review planning after one. It can reduce the cost of finding candidate owners, call paths, routes, literals, protocol anchors, and likely dependents in a large or cross-language repository.

**Not a fit:** choosing boundaries, evaluating business trade-offs, determining desired domain semantics, or deciding whether a historical co-change signal is causation. A graph edge, heat score, or co-change prior is evidence to inspect, not a recommendation to accept.

**Conditional adoption:** use it when the repository exceeds the working context, is unfamiliar, or spans languages/projects. Its own documentation says a few dozen files may be cheaper to read directly.  
Source: [README: “When not to reach for fovea”](https://github.com/monotykamary/pi-fovea/blob/main/README.md).

### F2. `codebase-design` complements judgment after evidence is established

The configured `codebase-design` skill supplies an explicit decision vocabulary: module, interface, seam, adapter, depth, leverage, and locality. It tests whether a proposed abstraction hides complexity or merely redistributes it. Its companion “Design It Twice” procedure asks for materially different interfaces and compares them on depth, locality, and seam placement.  
Sources: [skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md), [Design It Twice](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/DESIGN-IT-TWICE.md).

This is **architectural judgment**, not repository discovery. It materially complements a navigation or research workflow by turning verified code facts and constraints into comparable interface/seam alternatives.

**Failure mode:** it is a design heuristic, not a proof that a proposed module improves operational properties. Parallel designs can amplify model-generated alternatives without adding independent repository evidence. Require every claimed dependency, invariant, and caller impact to link back to inspected source.

### F3. `domain-modeling` fills the decision-recording gap

The configured `domain-modeling` skill distinguishes a domain glossary from implementation detail, challenges ambiguous vocabulary against code, and offers an ADR only when the decision is hard to reverse, surprising without context, and involves a real trade-off.  
Sources: [skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md), [ADR format](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/ADR-FORMAT.md), [context format](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/CONTEXT-FORMAT.md).

The ADR format is deliberately lightweight: a short decision and rationale, with status, options, and consequences only when useful. This is a good complement because it records the judgment and its conditions without replacing the upstream methods’ analysis.

**Limit:** it specifies when and how to write an ADR. It does not validate the decision, ensure team acceptance, create implementation tasks, or prove later code conforms to the ADR.

### F4. `codebase-scouting` is useful discipline but mostly overlaps evidence acquisition

The configured `codebase-scouting` skill requires bounded questions, a closure ledger, source citations, distinction between observation/inference/unknowns, and direct verification of decisive citations.  
Source: [local skill](file:///home/balauru/.pi-profiles/fabric/skills/codebase-scouting/SKILL.md).

Use its **citation and uncertainty discipline** when architectural claims depend on code. Do not make it a second mandatory scouting workflow if the supplied method already governs repository investigation. It does not supply architectural criteria or durable decision recording.

### Effectiveness evidence and exact limits

`pi-fovea` contains:

1. A **route-shape discovery** claim: tests on eight cloned projects found corpus junk below an estimated posterior of about `0.27`, and real route shapes above about `0.75`; the implementation’s promotion cutoff is `0.55` with at least four sites and two files.  
   Source: [README](https://github.com/monotykamary/pi-fovea/blob/main/README.md).

2. A local `bench.ts` specification. It compares Fovea’s bounded focus output to an alphabetically ordered outline at 500/1000/2000/4000-token budgets. Its target is the same Fovea field rendered at 16,000 tokens, using recall of names as the metric. It also reports cold/warm build time and focus latency.  
   Source: [benchmark source](https://github.com/monotykamary/pi-fovea/blob/main/scripts/bench.ts).

Neither is decision-grade evidence that Fovea improves architectural decisions, developer correctness, implementation quality, or time-to-ship:

- no published benchmark output was located;
- the benchmark’s oracle is Fovea’s own unbounded output, not independently adjudicated architectural ground truth;
- the comparator is a deliberately weak alphabetical outline, not the supplied methods or an expert investigator;
- queries are selected from highly connected symbols and anchors, so they are not representative of ambiguous architecture questions;
- the eight-project route result concerns extractor discrimination, not end-to-end architectural efficacy.

No measured effectiveness evidence was found for `codebase-design` or `domain-modeling`; they are workflow specifications. Their value is plausible but unmeasured here.

## Recommended workflow

1. **Acquire evidence.** State the decision question, required observations, and disconfirming evidence. For large/unfamiliar repositories, use Fovea only to identify candidate source windows, coverage gaps, and impact hypotheses. Read and cite the actual source. Use the scouting ledger discipline to label facts, inferences, and unknowns.

2. **Make architectural judgment.** Apply the supplied analysis method, then use `codebase-design` to compare a small number of seam/interface alternatives on caller knowledge, invariants, error modes, leverage, and locality. Use `domain-modeling` only where terminology or context ownership is genuinely disputed.

3. **Record the decision.** If the choice is hard to reverse, surprising, and a real trade-off, write the minimal ADR: context, decision, rationale, and only relevant rejected options/consequences. Record evidence links and explicit assumptions. Keep the glossary separate from implementation choices.

4. **Follow through.** Translate accepted ADR consequences into implementation acceptance checks. Before edits, use Fovea impact as a review checklist, not as a mandate. After implementation, inspect the named dependencies and run the repository’s authoritative verification. Mark the ADR superseded if subsequent evidence invalidates it.

## Concrete local evaluation that could change the choice

Run this only after authorization, with no package changes during the comparison.

- Select **8–12** real architecture questions from two repositories: at least one small repository and one unfamiliar, multi-module or cross-language repository.
- Lock model, model version, prompt, context budget, time budget, and investigator experience. Counterbalance order.
- Compare:
  - **A:** supplied workflow only.
  - **B:** supplied workflow plus Fovea for evidence/impact, `codebase-design` for alternatives, and `domain-modeling` for ADR capture.
- Have an independent reviewer score source-cited claims against the repository and score ADRs for accurate context, real alternatives, explicit consequences, and consistency with implemented code.
- Measure: citation precision/recall, missed affected files, unsupported architectural claims, time, tool calls/tokens, ADR corrections after review, and implementation acceptance-check pass rate.

Adopt Fovea for the target repository class only if B preserves or improves independently reviewed evidence accuracy and reduces investigation cost by a predeclared material threshold, for example 20%, without increasing unsupported claims or missed impacts. Reject or restrict it if extractor coverage gaps, false dependency/co-change implications, proactive state behavior, or overhead erase that advantage. The design and ADR skills should remain optional unless they improve review quality or decision reversibility in the same pilot.

## Remaining gaps and stopping point

- No primary, published end-to-end effectiveness trial for the candidate tools was located.
- No package artifact signature, dependency audit, or compatibility matrix was found. Those require separate supply-chain and version testing, not catalog inference.
- No broader candidate package was recommended because discovered architecture-mode/spec packages were only search metadata here, not primary-source-reviewed implementations, and appear workflow-overlapping.
- The supplied methods were read as boundary sources but intentionally not re-analysed in this assigned stream.
