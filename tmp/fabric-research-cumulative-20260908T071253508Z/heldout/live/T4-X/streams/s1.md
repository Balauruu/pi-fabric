# Research note: Software Factory Playbook vs. Wayfinder for Pi

## Assigned question and bounded answer

**Question.** What do the two named primary sources actually prescribe for architectural analysis and decision-making, and how should Pi use them without confusing workflow guidance, navigation, compatibility, or popularity with measured effectiveness?

**Bounded answer.** They operate at different layers:

- **Software Factory Playbook** is a **feature-delivery control process**: sequential human approval gates from product framing through architecture and program design to small implementation slices.
- **Wayfinder** is a **multi-session uncertainty-reduction process**: a tracker-backed map of decision tickets, resolved one at a time until a route to a stated destination is clear.

Use **Wayfinder before the Playbook** only when the destination or decisive architectural questions are genuinely unclear and exceed one session. Once the route is clear, use the **Playbook’s Gates 1–3** to turn that route into an approved feature design, then Gate 4 for implementation follow-through. Neither source supplies a rigorous architecture-evaluation method, empirical effectiveness results, threat model, or compatibility/security proof.

**Scope.** Fresh retrieval of only the two named primary sources, plus Pi’s authoritative skills documentation to assess SKILL.md packaging. No installation, execution, configuration, tracker mutation, browser automation, or package-alternative survey. The requested **2026-09-07** cutoff cannot be independently established from the live sources retrieved here. This is a current-source snapshot, not a verified historical snapshot for that future date.

## Findings

### F1. Software Factory Playbook prescribes four ordered approval gates

The Playbook requires explicit human approval at each gate and prohibits implementation code before the Gate 4 slice plan is approved. It targets nontrivial features, roughly multi-file work, new endpoints/tables/screens, or diffs around 100+ lines. It explicitly exempts trivial changes, explicit process bypasses, throwaway work, and prototypes.  
[Playbook: workflow and applicability](https://gist.github.com/Maciejdziuba/88890d7e0eeefa5a8738bbe9fd5e20b8)

1. **Product.** Define end-user problem, one measurable business success metric, announcement text, and plain HTML screen mockups. Technical design is prohibited.
2. **Architecture.** Read relevant existing code first. Record system fit, endpoints, data/query outlines, end-to-end call flow, and external dependencies. It says to record environment-variable *names*, never values.
3. **Program Design.** Record every changed/created file, types and method signatures without bodies, main call stacks, test assertions, and “least confident decisions.”
4. **Vertical Slices.** Approve a build-order plan, first create a running tracer bullet, then one small capability at a time. After each slice, prove it works, update status, and explicitly ask whether to continue or re-steer.

**State and authority boundary.** Its durable state is repository documentation under `docs/plans/<feature>/`: a status file, gate documents, mockups, and slice plan. The resume rule requires a fresh session to read those documents, continue at the first unapproved gate or unchecked slice, and not redo approved work unless requested or invalidated. The human alone approves gates. A later discovery invalidating an approved decision requires backtracking, updating the earlier document, and re-approval.

**Failure controls it explicitly includes.**

- Prevents premature code by stopping at approval gates.
- Prevents imagined-codebase design by requiring relevant-code reading at architecture.
- Prevents hidden design choices by requiring signatures, call stacks, test plan, and low-confidence choices before implementation.
- Prevents horizontal, hard-to-review delivery through tracer bullets and vertical slices.
- Prevents context loss by compacting decisions to docs at each boundary.
- Prevents false confidence in tests by prohibiting tests that already pass pre-change and prohibiting weakening/skipping tests.

**Limits.** These are prescriptions, not demonstrated outcomes. The source makes qualitative assertions about reviewability, context, and cost of changing decisions but reports no study, model, task corpus, sample size, comparator, success rate, time/cost measure, or independent replication. It also does not specify how to compare architectural alternatives, quantify uncertainty, evaluate security/privacy, reconcile stakeholder conflicts, or decide when a proposed “success metric” is causally attributable to the feature.

### F2. Wayfinder prescribes tracker-backed decision mapping, not feature implementation

Wayfinder is for “a huge chunk of work” whose destination is obscured by uncertainty. It makes a shared issue-tracker map canonical and treats each child issue as a question whose resolution is a decision, not a build slice.  
[Wayfinder: full SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/wayfinder/SKILL.md)

Its core procedure is:

1. **Name the destination** first, using grilling and domain modeling.
2. **Map breadth-first** across the decision space and identify immediate, well-formed questions.
3. Create one map issue labelled `wayfinder:map`, with destination, notes, closed-decision index, unspecified fog, and out-of-scope boundary.
4. Create precise child decision tickets, then add blocking edges in a second pass.
5. Work only the frontier: open, unblocked, unclaimed tickets.
6. Claim a ticket before work, resolve it, post the answer as a resolution comment, close it, and append only a one-line linked gist to the map.
7. Let answers graduate newly precise questions from “Not yet specified” into tickets, or close newly out-of-scope tickets.
8. Stop when no decisions remain before implementation. Default behavior is “plan, don’t do.”

**Ticket/state model.**

- The **map** is an index, not a duplicate decision store.
- Each ticket holds one question and, on closure, its answer.
- **Fog of war** is in-scope but not yet precise enough to ticket.
- **Out of scope** is beyond the destination and must not “graduate” unless a new effort redraws the destination.
- Dependency relations define the frontier. The source prefers native tracker blocking because it is visibly rendered for humans.
- It permits no more than one ticket per session, except research tickets. It anticipates concurrent sessions editing the tracker.

**Ticket types and authority.**

- **Research, AFK:** external/local information gathering.
- **Prototype, HITL:** cheap artifact used to raise discussion fidelity.
- **Grilling, HITL:** discussion. The source says the agent must not answer the human’s side.
- **Task, HITL or AFK:** prerequisite work that unblocks a decision, not delivery work.

Wayfinder requires human participation for HITL tickets and says a human must speak for themselves. That is a meaningful authority boundary. By contrast, its AFK research and task tickets can involve subagents.

**Limits and failure modes.**

- It is not an architecture method. A dependency/frontier graph says what decision is next, not whether a decision is technically sound.
- It depends on a configured tracker and documented tracker operations. The source says to ask the user to run setup if no tracker is provided, with a local-Markdown tracker as fallback. It does not establish that a particular Pi environment has a compatible tracker, native child issues, assignments, labels, blocking edges, comments, or concurrency controls.
- It specifies concurrent editing but no conflict-resolution policy for simultaneous map/ticket updates.
- “One ticket per session” limits overload but can create coordination and throughput costs.
- The scope boundary depends heavily on a correctly named destination. A vague or politically disputed destination can make the map misleading.
- “Research” can surface facts, but does not itself define evidence quality, source hierarchy, decision criteria, or how contradictory evidence changes a decision.
- Like the Playbook, it supplies no measured efficacy: no benchmark, comparison, sample, completion rate, or controlled evaluation.

### F3. The methods complement rather than replace each other

| Decision stage | Better fit | Why |
|---|---|---|
| Destination unclear, decision space too large for one session | Wayfinder | It explicitly models uncertainty, blocking, concurrent claims, scope, and progressive discovery. |
| Architecture alternative must be judged | A separate architecture-analysis method | Neither source provides criteria, evidence standards, trade-off analysis, or decision rules. |
| Feature intent, system fit, interfaces, and tests must be approved | Playbook Gates 1–3 | It turns an agreed route into reviewable product, architecture, and program-design artifacts. |
| Implementation after design approval | Playbook Gate 4 | It constrains delivery to running, reviewable vertical slices with proof and re-steering. |
| Durable institutional decision record | Wayfinder ticket resolution plus a Playbook ADR | Wayfinder preserves investigation detail in one ticket. The Playbook explicitly recommends ADRs for decisions that outlive a feature. Avoid copying the same decision into both. |

**Recommended relationship.** Wayfinder should resolve only the few architectural questions that block a route. The Playbook should then package the resulting selected architecture for feature approval and implementation. Do not use a Wayfinder map as evidence that an architecture is correct, and do not use a Playbook gate document as evidence that important unknowns were discovered.

## Pi compatibility and complementary capabilities

### F4. SKILL.md packaging is documented as compatible, not operationally proven

Pi documents support for the Agent Skills standard and discovery of directories containing `SKILL.md`; it can also load skills from other harnesses’ skill directories.  
[Pi Skills documentation](file:///home/balauru/.local/share/pi-node/node-v22.23.1-linux-x64/lib/node_modules/@earendil-works/pi-coding-agent/docs/skills.md)

Therefore:

- **Playbook:** its `name` and `description` frontmatter are compatible in format with Pi’s documented skill requirements. Its claim that it works in “any agent that supports SKILL.md” is a packaging claim, not proof that Pi can satisfy its workflow’s write, test, UI-proof, or approval interactions.
- **Wayfinder:** its format is likewise compatible. Its `disable-model-invocation: true` is documented by Pi as requiring user invocation via `/skill:wayfinder`, rather than automatic model invocation. This matches Wayfinder’s deliberate, user-driven process.
- **Not established:** installation status of either source skill, tracker tooling, issue mutation permissions, credentials, branch/worktree support, or actual invocation in this Pi profile. No such action was taken.

### F5. Observed configured complements, limited to roles named by Wayfinder

This Pi profile’s configured skill inventory includes **`grilling`**, **`domain-modeling`**, and **`prototype`**. Wayfinder explicitly calls for grilling plus domain modeling to establish the destination and for grilling tickets, and names prototype tickets as its low-fidelity artifact method.

These are complementary roles:

- **`domain-modeling`:** makes the destination and architectural vocabulary less ambiguous before mapping or approving design.
- **`grilling`:** forces unresolved assumptions, trade-offs, owners, and exit criteria into explicit human discussion.
- **`prototype`:** tests a contested interaction, API shape, data-model behavior, or UX hypothesis before architecture is committed.

This is **configured availability**, not measured effectiveness, compatibility certification, or evidence that the skills’ workflows will interoperate without adaptation.

### F6. Permission and implementation boundaries in Pi

- The Playbook requires repository writes to plans, ADRs, mockups, implementation code, and status files, plus commands or browser/curl checks to prove slices. Those are later implementation permissions, not required for this research.
- Wayfinder requires tracker creation, labels, child links, dependency links, assignments, comments, and closures. Those are consequential tracker mutations and require an available, authorized tracker integration.
- Wayfinder’s source also prescribes research subagents and throwaway branches for research. This is a workflow instruction, not evidence that the local Pi configuration has safe or enabled subagent, branch, or tracker capability.
- Neither source defines a least-privilege permission model, data-classification policy, secret-handling policy, code-review requirement, or rollback protocol.

## Recommended practical workflow

1. **Evidence acquisition.** Write a bounded decision question with alternatives, constraints, stakeholders, assumptions, evidence required, disconfirming evidence sought, and an explicit decision deadline. Gather primary system evidence first: code paths, runtime/configuration facts, interfaces, operational constraints, and owned-team statements. Keep source links and distinctions between observed facts, assumptions, and inferences.

2. **Wayfind conditionally.** Start a Wayfinder map only if the destination is unclear or important questions cannot be stated and resolved in one session. Map breadth-first. Create tickets only for precise questions. Use native tracker blocking only if it is actually supported and authorized. Do not perform delivery work in a decision ticket except prerequisite work that unblocks a decision.

3. **Apply architecture judgment outside the map.** For each decisive ticket, evaluate alternatives against explicit criteria: functional fit, coupling/cohesion, failure isolation, data consistency, security/privacy, operability, migration/rollback, cost/latency, team ownership, and reversibility. State evidence confidence and what would falsify the selected option. Record rejected alternatives and why.

4. **Record once, link everywhere.** Close the Wayfinder ticket with the detailed resolution and evidence. Put only a one-line linked gist in the map. If the decision has durable architectural consequences, create or supersede an ADR as the Playbook recommends. Do not duplicate full rationale in map, ticket, ADR, and feature plan.

5. **Move to the Playbook.** Use Gate 1 for product intent, Gate 2 to validate the chosen architecture against actual code, Gate 3 to make interfaces, files, call stacks, tests, and low-confidence assumptions reviewable, and Gate 4 to deliver tracer bullet then vertical slices. Reopen the relevant decision record if implementation evidence invalidates its assumptions.

6. **Verify each slice.** Before marking a slice complete, execute its stated behavioral proof and confirm that its tests could fail before the change. Record deviations, operational observations, and re-steering decisions in the feature plan and ADR/ticket where durable.

## Conditional adoption decision

**Adopt both, conditionally.**

- Adopt **Wayfinder** for cross-cutting, ambiguous efforts only when a tracker with the required issue semantics and mutation authority is available, and when the effort has enough uncertainty to justify map maintenance.
- Adopt **Software Factory Playbook** for consequential feature delivery once the destination and pivotal architecture choices are sufficiently clear.
- Do **not** adopt either as the sole architectural-decision method. Add an explicit alternative-comparison and evidence-confidence template.

## Local evaluation that could change the choice

Run one representative, non-production architectural change through two comparable planning exercises:

- **Control:** current planning practice.
- **Treatment:** Wayfinder only if uncertainty qualifies, then Playbook Gates 1–3 before implementation.

Pre-register the same task, model, time budget, participants, codebase access, and acceptance criteria. Measure:

1. Time to an approved, internally consistent architecture decision.
2. Number and severity of post-approval assumptions invalidated during implementation.
3. Rework after first implementation slice.
4. Reviewer ability to answer interface, data-flow, rollback, and ownership questions from records alone.
5. Decision-record completeness: alternatives, evidence, risks, owner, reversal trigger, and tests.
6. Total human coordination and tracker/document maintenance time.

Choose the combined workflow only if it improves reviewability or reduces rework enough to justify process cost. Reject or narrow Wayfinder if map/ticket maintenance dominates. Reject or narrow the Playbook if gate latency materially delays low-risk work without reducing rework.

## Evidence limits and stopping point

- No primary source reports effectiveness data. Absence of a reported experiment is **not** evidence of ineffectiveness.
- The Playbook attributes its workflow to Dex Horthy/HumanLayer and a podcast, but the retrieved source itself is a GitHub Gist authored by Maciej Dziuba. This establishes stated provenance, not independent validation of the attributed ideas.
- Wayfinder is a file on the `main` branch of Matt Pocock’s repository. A branch URL is mutable. The retrieval exposed a cloned repository snapshot internally but no durable commit permalink was retained from the source page.
- No discovery popularity, stars, install count, issue activity, user study, benchmark, or comparative trial was inspected or claimed.
- No package alternatives were surveyed, per assignment boundary.
- Research stopped after the two supplied primary sources and Pi’s packaging documentation repeated the relevant workflow and compatibility evidence. Further claims would require tracker-specific, implementation-specific, or evaluation evidence outside scope.
