# T2/R1 research note: measured run-design interventions

**Question.** Which original evaluations, through **2026-09-07**, measure coding-agent run-design choices while distinguishing fixed-model/effort interventions from model or compute changes?

**Scope.** Repository-level issue resolution only. “Fixed model” means the policy model is unchanged within the primary contrast. “Fixed effort” additionally requires equal trajectory/token/time budgets. Several useful studies fail the latter condition and are labeled accordingly. This is evidence for R1, not a final adoption decision.

## Bounded answer

The strongest direct evidence is limited:

1. **Context-file injection:** one paired, repeated two-agent study found a bounded correctness null, with a narrow efficiency mechanism in one repository.
2. **Tool/interface feedback:** SWE-agent shows a large same-model interface bundle improvement over shell-only, but the bundle changes search, editing, feedback, demonstrations, and workflow. It does not isolate test feedback alone.
3. **Decomposition:** SWE-Edit reports improved resolution and lower cost, but introduces GPT-5-mini subagents, so it is not a fixed-model intervention.
4. **Retries/test-time scaling:** restart and replay studies show measurable compute-performance trade-offs, but change total compute and introduce monitors or extra trajectories. They answer budget allocation, not fixed-effort run design.
5. **Validation signals:** oracle-information studies establish upper bounds, not deployable causal effects. They must not be read as measured gains from an agent merely running tests.

## Reasoning and counterevidence

### F1. Context quality and delivery should not be conflated
The context-file study varies delivery, but for two repositories its selective wiki is approximately 10× and 18× larger than the original file. Its `none` versus always-on result is the cleanest contrast. The study also reports different injection channels, system prompt for Claude and user-prompt prepend for Codex. Therefore, its bounded null applies to these files, tasks, agents, and delivery mechanics, not repository retrieval generally.

### F2. More interaction is not automatically better
SWE-agent reports successful runs completed sooner: GPT-4 Turbo resolved runs had median $1.21 and 12 steps, versus mean $2.52 and 21 steps for unsuccessful runs ([Appendix B.3](https://arxiv.org/html/2405.15793v3)). This is descriptive, not proof that earlier stopping causes success. It does, however, contradict a simple “raise the cap or add more searches” assumption.

### F3. “Validation” evidence has different evidentiary levels
- Executing hidden gold tests is an outcome evaluator.
- Agent-visible test results are feedback.
- ORACLE-SWE injects ground-truth-like information and measures an upper bound.
- SWE-Edit’s final evaluation is execution-based, but its editor benchmark partly uses a GPT grader.

These should not be combined into a claim that adding validation loops has a known isolated production effect.

### F4. Benchmark success is an imperfect outcome
[SWE-ABS](https://arxiv.org/html/2603.00520) re-evaluated 11,041 originally passing patches from the top 30 SWE-bench Verified agents. Strengthened tests rejected 2,184, or **19.78%**, and dropped the leading score from 78.80% to 62.20%. Its augmented evaluation produced an average 14.56-pp resolve-rate drop and rank correlation ρ=0.82 with the original leaderboard. This is not a result against any run design, but it constrains all studies reporting only original test-pass rate.

### F5. Public PR-derived tasks carry leakage risk
[DeepSWE](https://arxiv.org/html/2607.07946) explicitly identifies the central risk of mining public GitHub fixes: issues, discussions, and fixes may be present in pretraining, so apparent resolution can partly be recall. Its 113 original long-horizon tasks are a useful counterweight, but one benchmark alone does not solve external-validity limits.

## Operational evidence table for a fixed-policy study

This is an evaluation artifact and measurement gate, **not an adoption recommendation**.

| Candidate change | Paired unit | Keep fixed | Primary outcome | Efficiency outcomes | Reject / escalate condition |
|---|---|---|---|---|---|
| Context delivery | Same task, seed block, base commit, hidden test suite | Model version, reasoning setting, tool set, token/step/time cap | Hidden-test pass | Wall time, input/output tokens, tool calls, full-suite runs | Effect is within predeclared practical bound or task-specific harms appear |
| Tool feedback format | Same task and action budget | Model, commands available, test command, context cap | Hidden-test pass and invalid-edit rate | Recovery steps, test executions, token cost | Bundle changes prevent attribution. Split into separate tool-feedback and edit-format arms |
| Validation/repair loop | Same failed first attempt, replayed deterministically where possible | Model, initial trajectory budget, evaluator, repair cap | Recovery among initially failing attempts and final pass | Extra test runtime, repair tokens, false accept/reject | Evaluator disagreement or weak-test sensitivity is material |
| Retry/restart | Same task and total end-to-end token budget | Model, total budget, final evaluator | Best-of-budget pass | Marginal pass per added token, abort false-positive rate | Gains require excess total budget or abort would-pass rate exceeds threshold |
| Decomposition | Same task, total policy-equivalent budget | Main model and submodel policy if possible, tool capability | Hidden-test pass | Tokens by role, context length, edit failure | Different submodel or privileged retrieval means classify as architecture-plus-model change |

## Concrete paired-evaluation artifact

```yaml
study: run-design-change-v1
unit: {task_id, base_commit, seed_block}
population:
  task_sources: [held-out internal issues, post-cutoff or access-controlled tasks]
  strata: [language, repository_size, task_type, baseline_difficulty_band]
arms:
  control: existing_run_design
  treatment: one_named_run_design_delta
constants:
  model_id: exact production model identifier
  reasoning_effort: fixed
  tools_and_permissions: fixed
  max_steps: 120
  total_token_budget: 200000
  wall_time_limit_s: 1800
  evaluator: hidden regression_plus_new_adversarial_tests
record_per_run:
  - resolved_hidden_tests
  - original_tests_pass
  - adversarial_tests_pass
  - tokens_input_output_cached
  - wall_time_s
  - tool_calls_by_type
  - test_commands_and_results
  - edit_failures
  - retries_and_abort_reason
analysis:
  pairing: within_task_seed_block
  primary_estimand: mean(treatment_resolved - control_resolved)
  uncertainty: task_clustered_bootstrap_CI
  secondary: [cost_per_resolved, failure_modes, evaluator_disagreement]
  reporting: all_task_level_deltas_and_budget_violations
```

## Remaining gaps and stopping point

- No inspected primary study cleanly isolates **test-output feedback** from all other tools while holding model and total effort fixed.
- No inspected primary study cleanly isolates **repair-loop count** at an equal total token budget.
- The direct context null is small, Python-only, and based on an under-review preprint.
- Retry evidence changes compute allocation and adds a monitor, so it cannot answer the strict fixed-model-and-effort question.
- Security was not measured in these sources. No security conclusion follows.

Research stopped after primary evaluations repeated the same design pattern or shifted from controlled run-design intervention to model training, multi-agent systems, or benchmark construction.
