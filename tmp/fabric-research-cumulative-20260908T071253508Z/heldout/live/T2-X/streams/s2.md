# T2 holdout note: counterevidence and operational inference

## Assigned question and boundary

**R2:** What reliability limits, nulls, leakage, and evaluator limitations constrain claims that run design improves a coding agent?  
**R3 contribution:** What fixed-model experiment controls and adoption/failure signals follow?

**Scope:** coding-agent run design only. Hold model identity and reasoning effort fixed. Cutoff: **2026-09-07**. This note does not rank interventions, claim universal effects, infer security properties, or survey primary run-design interventions.

## Bounded answer

Run design can materially change observed outcomes, but a single benchmark pass rate is not decision-grade evidence. The main threats are:

1. **Outcome validity:** passing benchmark tests can overstate functional resolution.
2. **Training and prompt leakage:** static public tasks and issue discussions can make success partly retrieval or memorization.
3. **Stochastic-run variance:** one run and especially best-of-\(N\) reporting overstate typical performance.
4. **Configuration dependence:** the same trace signal can mean success in one framework and failure in another.
5. **Benchmark scope:** current evidence is heavily Python, GitHub-issue, Docker/test-harness, and often oracle-test-visible.

The operational consequence is not “avoid run-design changes.” It is to use a **paired, repeated, frozen-model evaluation** with an independent holdout and human/stronger validation of a sampled set of passes before adoption.

## Findings

### F1. Passing tests is not equivalent to resolving the task

[SWE-Bench+](https://arxiv.org/html/2410.06992v2) manually reviewed 251 SWE-Agent + GPT-4 patches that had passed all associated SWE-bench Full tests. Three authors independently compared generated and gold patches, issue reports, tests, and trajectories, resolving disagreements jointly (§2).

| Measured result | Comparator / implication |
|---|---|
| 32.67% of passed patches had a solution stated directly in the issue or comments | A “resolved” result may reflect answer copying, not agentic problem solving. |
| 31.08% were incorrect, incomplete, or changed unrelated files/functions while still passing tests | Test pass alone was an inadequate correctness evaluator in these cases. |
| 63.75% of the 251 passes were classified suspicious | This is a validity problem for that sample and setup, not a general false-pass rate. |
| SWE-Agent + GPT-4’s reported 12.47% rate fell to 3.97% after filtering suspicious cases | This is a source-bound reclassification contrast, not a causal estimate of any run-design effect. |
| On SWE-bench Verified, its reviewed successful patches included 12.50% incorrect and 9.82% incomplete fixes. The source reports 55.36% suspicious fixes overall and a rate change from 22.4% to 10.0%. | “Verified” improved curation but did not remove this evaluator risk in that study. |

**Qualification.** The audit is of one agent–model and its successful patches, not a random sample of all coding agents. It does, however, directly invalidate using test pass as the *only* adoption criterion for a run-design change.

### F2. Leakage can confound a run-design comparison even when the model is unchanged

[SWE-Bench+](https://arxiv.org/html/2410.06992v2) reports that over 94% of original SWE-bench issues and PRs predate the tested models’ stated cutoffs. It built a 548-task successor from issues after October 2023, manually excluding issue/comment answer leakage (§§1, 3–4).

On its newer set, reported resolved rates were: SWE-Agent + GPT-4 **0.55%**, SWE-RAG + GPT-4 **0.73%**, SWE-RAG + GPT-3.5 **0.55%**, and AutoCodeRover + GPT-4o **3.83%**. The paper’s stated prior leaderboard comparators were **3.97%**, **1.31%**, **0.17%**, and **18.83%**, respectively. These are not clean A/B estimates because both dataset and evaluation conditions differ.

More importantly, filtering answer leakage did **not** solve evaluator validity: the paper reports that, on average, **67.72%** of initially resolved SWE-Bench+ instances did not truly resolve the issue after manual patch validation (§4).

**Operational inference:** do not tune a context, retry, or validation policy on a public static set and then use that same set as sole proof of adoption. It can select policies that exploit dataset-specific hints, test gaps, or prior exposure.

### F3. Repeated runs are necessary, and pass@k must not be presented as single-run reliability

[SWE-rebench](https://papers.nips.cc/paper_files/paper/2025/file/21bec6ace947b1b58967b945c8ac0f10-Paper-Datasets_and_Benchmarks_Track.pdf) explicitly identifies high stochastic trajectory variance as a benchmarking threat (§3.1): a run may recover from an error in one seed and fail in another. It warns that reporting the best run can overstate resolved rate.

Its protocol provides a concrete precedent:

- 294 executable tasks from 169 repositories.
- Fixed minimal ReAct scaffold, identical prompts, and developer-recommended generation parameters.
- **Five runs per model** with different seeds.
- Reports SEM and pass@5, rather than a single result (§3.2, Appendix J).
- One full DeepSeek-V3 run across those 294 tasks took about **7 hours**. This is a source-specific runtime condition, not a generic cost estimate.

**Operational inference:** a run-design evaluation must report **per-run success**, not merely “solved at least once.” If retry is the changed feature, report both:
- probability of success within the fixed retry budget, and
- the distribution of attempts, wall-clock time, tool calls, and failures required to get it.

### F4. Trace heuristics do not transfer universally across run designs

[Same Signal, Different Semantics](https://arxiv.org/html/2605.18332) analyzes 64,380 public SWE-bench Verified trajectories, spanning 126 model–framework configurations and 43 frameworks. Its relevant design holds the LLM fixed across 6–8 frameworks for three tracer models, then compares a separate single-framework slice across 33 LLMs (§§1, 3–4).

Measured counterevidence:

- For error rate, **47** configurations associated lower error rates with resolution, while **48** associated higher error rates with resolution.
- Across 63 within-trajectory-type feature comparisons, framework variation exceeded LLM variation in **44/63 (69.8%)**.
- In one reported example, framework identity explained **64%** of between-configuration variance in mean turns versus **10%** for LLM family.
- The authors classify shorter trajectories, fewer revisits, lower entropy, and lower backtracking as direction-stable in at least 88% of configurations, but say their numeric thresholds still require per-framework calibration.

**Limit.** This is observational analysis of public submissions, not randomized A/B testing. The configuration matrix is sparse, log formats required custom parsers, and all trajectories used SWE-bench Verified with 100% oracle test visibility. The paper itself avoids absolute turn-count comparisons between loop agents and pipeline agents because their “turn” units differ.

**Operational inference:** do not adopt a generic rule such as “more validation,” “fewer errors,” “more retries,” or “shorter trajectories” based solely on correlations from another scaffold. Calibrate thresholds on the target agent and test causal A/B variants.

### F5. Freshness reduces one risk but does not establish full evaluator validity

[SWE-rebench](https://papers.nips.cc/paper_files/paper/2025/file/21bec6ace947b1b58967b945c8ac0f10-Paper-Datasets_and_Benchmarks_Track.pdf) uses a continuously refreshed benchmark and records dates to mark potentially contaminated model/task combinations. It also freezes dependencies for reproducibility. These are useful controls.

But its automated task-quality predictor had only **67% accuracy** and weighted F1 **0.65** for test-patch correctness on its 413-example validation set (§2.4 and Appendix F). Its benchmark also restricts tasks to 2025, English, Python, at most three modified files, at most 500 patch words, low-to-moderate LLM-assessed difficulty, and at most 50 fail-to-pass tests (Appendix H).

Therefore, freshness and executable tests reduce specific threats but do not prove evaluator correctness, production transfer, or coverage of harder/multilingual tasks.

## Proposed fixed-model experiment design

The following are **proposed controls**, derived from the limitations above. They are not measured claims.

### P1. Freeze all non-treatment factors

| Field | Baseline A | Candidate B | Required rule |
|---|---|---|---|
| Model and version | Exact provider/model snapshot | Same | No model substitution or fallback |
| Reasoning effort | Fixed level | Same | Log configured and actual setting |
| System/developer prompt | Exact bytes | Same | Treatment-specific instructions only |
| Tools, permissions, environment | Same tool versions and sandbox | Same | No hidden tools or changed access |
| Task context | Same initial repository commit and issue | Same | Log selected context and truncation |
| Runtime budget | Fixed wall-clock cap | Same, except where the treatment *is* retry allocation | Report actual runtime |
| Sampling | Same seed set | Same seed per task | Pair task × seed |
| Evaluator | Same frozen harness | Same | Blind validation sample to arm |

### P2. Use a three-way task split

1. **Development set:** tune only here.
2. **Frozen internal holdout:** make the adoption decision here.
3. **Fresh canary:** tasks created after the model’s known release/training boundary where possible, withheld from run-design development.

Stratify all splits by repository, task type, changed-file count, test count, and difficulty proxy. Keep repository groups intact where feasible to reduce project-specific tuning.

### P3. Measure reliability and cost, not just success

For every task × seed × arm, retain:

- test-harness result and failure class,
- patch and diff,
- wall-clock time, model calls, input/output tokens, tool calls,
- retries and repair cycles,
- termination reason,
- context artifact: selected files/chunks and token counts,
- exact evaluator image/version and dependency lock.

Report per arm: mean success across runs, task-level paired difference, uncertainty interval from paired bootstrap, seed variance, median and tail runtime, and cost per successful run. Separately report `pass@1`, fixed-budget `pass@k`, and the total budget consumed. Do not turn pass@k into a claim about ordinary one-run operation.

## Operational decision table

| Signal | Decision | Rationale |
|---|---|---|
| B improves frozen-holdout paired success and does not worsen sampled independent-validation failure/unclear rate or p95 runtime beyond the declared budget | **Adopt gradually** | A measured effect under frozen model and evaluator conditions. |
| B wins only on dev/static benchmark, not fresh canary or frozen holdout | **Reject or redesign** | Consistent with benchmark-specific tuning or leakage. |
| B improves pass@5 but not pass@1, while cost/tail latency rises | **Treat as a retry-policy option, not a general improvement** | It changes availability under a larger budget, not typical single-run reliability. |
| B increases raw harness passes but blinded sample finds incorrect/incomplete patches | **Block adoption** | Source evidence shows tests can accept invalid patches. |
| B’s result overlaps zero under paired uncertainty, or seed variance dominates the delta | **Continue measurement, do not adopt** | A single/best run is not reliable evidence. |
| B changes an allegedly “good” trace metric but not validated task outcome | **Do not adopt on trace metric alone** | Cross-framework evidence shows trace semantics are configuration-dependent. |
| Evaluator image, prompt, model revision, task commits, or tools differ between arms | **Invalidate and rerun** | Attribution to run design is lost. |

## Remaining gaps and stop condition

- No inspected source gives a randomized, fixed-model causal estimate for each individual run-design choice. This stream therefore supplies evaluation controls, not claims that any particular intervention works.
- No inspected evidence establishes production incident reduction, security improvement, or generalization outside repository-level issue repair. Those claims should remain unmade.
- Fresh benchmarks reduce contamination risk but are not contamination proofs, and their Python/task-selection constraints limit transfer.
- Research stopped after primary sources repeated the same central constraints: static-benchmark leakage, test-evaluator weakness, stochasticity, and scaffold-dependent behavior.
