# Decision-grade guide: evaluating permission-bounded tool agents

**Scope and evidence date.** This guide uses only five frozen primary-source snapshots, read on 2026-09-08. It ends here because the assignment freezes the evidence. A benchmark score, an evaluator score, and a proposed control are different claims. None establishes production security.

## Executive decision

Do not authorize a permission-bounded deployment from any included benchmark result alone. Use the benchmarks to construct a local, trace-preserving evaluation: measure repeat-run task completion, safe handling of recoverable tool faults, and adversarial boundary violations separately; validate its evaluator against human trace review; and enforce permissions outside the model. This conclusion is supported by (a) sharp degradation under repeated runs and recoverable tool hazards, (b) documented evaluator-human disagreement and judge instability, and (c) prompt-injection results whose useful controls have explicit failure conditions.

## Reliability and recoverable failures

### Repeat-run reliability is a separate release criterion

S1's pass^k answers a stringent question: whether every run of the same task succeeds, not whether one sampled run succeeds. Its >60% average versus <25% pass^8 comparison is direct evidence that a one-run aggregate can conceal instability. Use an identical local task and tool-state seed across repeated trials, report pass^1 and pass^k (with k chosen before execution), and retain individual traces. Do not convert S1's percentage to a prediction for another model, domain, policy, or production workflow.

### Recovery must be measured under resolvable faults

S2 supplies a useful experimental construction, not an operational guarantee: begin with a task that succeeds, inject a specified fault while leaving a verifiable recovery path, then compare completion under clean versus faulted conditions. Its five hazard types map to concrete probes: stale schema, invalid/ambiguous arguments, explicit runtime error, missing/non-canonical result, and conflicting sources. Record fault type, tool, attempt count, fallback/cross-check, evidence supporting the final answer, clean comparator, and exact-match or deployment-specific outcome metric. A hint-assisted result measures assistance plus agent recovery, not unaided reliability.

S5 adds a distinct failure mode: an agent can claim it obtained a tool result without calling a tool. Therefore require trace checks for tool-result provenance and separately report fabricated-result assertions. Rejection of injected bad parameters and recovery after an error are empirically independent across S5's 13 models (Spearman ρ=.041, p=.893); neither metric can stand in for the other.

## Evaluator validity

Automated scoring needs its own evidence chain. S3 found both false negatives and false positives from brittle state matching, trajectory lock-in, incorrect ground truth, reward-basis mismatch, rubric drift, hallucinated completion, and answer-only scoring. S5 independently shows a substring heuristic can be near chance against its small human sample. These are not interchangeable audits, but together they rule out treating an unvalidated convenient score as ground truth.

Use deterministic checks for permission use, state transitions, required confirmations, and output provenance where the deployment specification is objective. For qualitative or underspecified outcomes, predefine a rubric, preserve full trajectory and rubric version, and audit a stratified sample with blinded human reviewers. Report agreement, disagreement categories, and repeat-score dispersion. A model-selected judge with highest agreement on the calibration labels must not be declared best solely from that calibration set, as S5 explicitly notes the overfitting risk.

## Security boundaries and controls

S4 measures prompt-injection susceptibility in its synthetic environments. It does **not** prove production safety. It proposes/evaluates controls that can guide an architecture:

- **External permission enforcement:** scope every call to an allowlisted capability, resource, operation and arguments. This is an operational control, not a benchmark measurement. It addresses the gap S4 exposes when a malicious goal needs write access while the user task only needs reads.
- **Task-scoped tool filtering:** S4's GPT-4o result is promising in-suite, but it fails when tools cannot be planned in advance, when user-required tools can also perform the attack, which the source says is true for 17% of cases, and potentially across multi-task retained context. It is not sufficient alone.
- **Confirmation and transaction boundaries:** require an independently enforced user confirmation for consequential writes, use idempotency/rollback where applicable, and log the authorization, requested effect and result. S1's policies include confirmation requirements, but S1 measures compliance in its simulation rather than security against a hostile tool output.
- **Untrusted-output handling:** label tool/web content as data, do not let it expand authority, require validated provenance before final claims, and fail closed on contradictory/incomplete evidence. These controls align with S2's recoverable-fault tasks and S5's fabricated-tool-use finding; they are recommended controls, not measured security proofs.
- **Adaptive adversarial testing:** S4 explicitly warns against relying on default attacks. Test attacks that know the deployed tool/API and permission boundary, including attempts to induce authorized-looking but out-of-scope writes. A fixed-suite ASR is only a lower-bounded observation for that suite/attack configuration.

## Smallest resolving evaluation for one permission-bounded deployment

Run one pre-registered, deployment-faithful suite with a fixed agent/model version, prompts, tool schemas, policy, evaluator and environment snapshot.

1. **Cases:** a minimal set covering each allowed read and write capability, each confirmation gate, denied cross-resource/argument request, a multi-step task, and at least one retain-context/multi-task sequence if production retains context.
2. **Reliability arm:** run clean cases repeatedly under identical initial state and stochastic settings, reporting pass^1, pass^k, per-case outcomes and complete traces.
3. **Recoverable-fault arm:** for each material integration, inject one S2-style resolvable fault with a documented recovery path. Compare clean and faulted completion, unsafe effects, hallucinated/fabricated tool result claims, retries and time/cost. Do not score an unavailable recovery path as agent failure without labeling it as such.
4. **Security arm:** execute paired benign task plus adaptive injection attempts that target the actual allowed tools, resources and context. Primary safety outcome is any externally verified out-of-scope effect or unauthorized disclosure, not model self-report. Run a nonzero set of attacks before permitting writes.
5. **Evaluator audit:** deterministically verify effects and authority where possible. Blindly human-review a stratified trace sample, including automated passes/fails, security near-misses and recoveries. Rerun any LLM-judge pipeline and publish evaluator-human agreement and score spread.

**Decision rule.** Start only with the least privilege needed for the tested use case. Expand a capability only after the local suite demonstrates the predeclared task, recovery, boundary and evaluator criteria for that capability. The frozen sources provide no numeric deployment threshold, so no threshold is invented here.

## Limitations

This is a bounded synthesis of supplied snapshots, not a retrieval or implementation audit. The sources use different models, years, task populations, metrics and simulators, so their figures must not be pooled. S2 is specifically v1 and S4 contains the retained prose/Table-5 discrepancy. S3 and S5 are separate evaluator-validity evidence streams. No supplied source measures this deployment, live integrations, authorization implementation, latency, operational cost beyond the stated benchmark estimates, or adaptive attack coverage sufficient to establish security.
