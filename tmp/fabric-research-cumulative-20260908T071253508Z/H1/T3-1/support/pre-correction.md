# Decision guide: evaluating permission-bounded tool-using agents

**Scope and research date.** This guide uses only the five supplied primary-source snapshots, inspected on 2026-09-08. It addresses simulated or deterministic benchmark environments, not a live deployment. The investigation ends here because the evidence corpus is frozen. Benchmark measurements, evaluator measurements, and proposed controls are not proof of production security.

## Executive answer

A permission-bounded agent should not be approved from a single task-success score, a single benchmark run, or a prompt-injection defense result. The strongest source-bound decision is to require a **versioned, repeated, trace-preserving local evaluation** that separates: (1) authorized tool invocation and state change, (2) user-task completion and communication, (3) recovery after injected but recoverable tool failures, (4) evaluator agreement with human trace review, and (5) security outcomes under relevant untrusted-tool-data attacks.

The evidence establishes three different, non-interchangeable facts:

- **Repeat-run task reliability is often low.** In tau-bench, GPT-4o function calling exceeded 60% average task success in its retail setting but fell below 25% `pass^8`, the probability all eight i.i.d. repeats of a task succeed. This supports measuring repeated semantic variants, not assuming `pass^1` is operational reliability. It does not measure real permissions or adversarial security.
- **Recoverable tool failures materially reduce completion.** ToolBench-X v1 found no tested model above 0.60 overall exact final-task accuracy under its injected hazards. Hints recovered much more lost accuracy than extra interaction rounds, which supports testing hazard diagnosis and specific recovery behavior. It does not establish live-API availability, because its tools are deterministic Python implementations and every injected instance deliberately retains a recovery path.
- **Scores require evaluator validation and security requires containment.** The evaluator-validity audit found 92 evaluator-human disagreements in 496 audited cases (18.5%) and 18.9-point end-to-end score spread across 23 repeated LiveMCPBench runs. AgentProp-Bench independently found a weak substring correctness heuristic at chance-level agreement with human labels, while a calibrated LLM judge was better but imperfect. AgentDojo shows prompt injection can cause harmful actions in its test environment and that tool filtering can reduce measured targeted attack success where the user needs read tools and the attacker needs distinct write tools. Neither finding proves a production agent is secure.

**Recommendation.** Deploy only behind narrowly scoped, server-enforced permissions, explicit authorization for consequential operations, auditable traces, bounded recovery, and a local evaluation that tests the exact model, prompt, tool wrappers, identity/authorization mechanism, tool allowlist, and data boundary. Treat a failed deterministic safety gate as a failure regardless of a fluent final response. Treat results outside that configuration as transfer-limited evidence.

## Reliability and recoverable tool failure evidence

### 1. Measure repeatability separately from average success

tau-bench uses fixed semantic task instructions and database transitions while the simulated user and agent messages are sampled. Its `pass^k` is the proportion of tasks for which all k sampled runs succeed, estimated from repeated trials, whereas `pass@k` asks whether at least one succeeds. This is the right direction for an agent that must succeed consistently, not eventually discover an answer. In its reported setting, GPT-4o FC's retail success declines from over 60% at one run to below 25% at eight. The study's airline result, 35.2% `pass^1` for GPT-4o, shows the domain matters.

The result should not be over-read. Retail and airline databases, policies, synthetic task instructions, and LM-simulated users are simplified. The benchmark authors also tuned instructions using GPT-4-turbo trials, and report that four of 40 sampled initial retail failures were task-instruction typo or ambiguity and were fixed. Its reward is exact final state plus required-response substrings, and the source explicitly says that this can be necessary but insufficient for a policy-compliant episode. A local repeat-run test therefore needs both an outcome predicate and a trace review of authorization, confirmation, and denied actions.

### 2. Test failures that remain recoverable, but do not confuse recovery with security

ToolBench-X v1 distinguishes where a tool interaction diverges from the clean contract:

- **Specification drift:** documentation and runtime contract differ.
- **Invocation error:** the intended call is altered, dropped, coerced, defaulted, truncated, or rejected at the wrapper/tool boundary.
- **Execution failure:** a valid call encounters timeout, connection, runtime, or parsing failure.
- **Output drift:** the result exists but changes wrapper, unit, nesting, alias, or canonical form.
- **Cross-source conflict:** multiple branches are incomplete, inconsistent, or differently formatted and require reconciliation rather than voting.

The benchmark validates a clean path and at least one injected-environment recovery path per retained case. Its measured differences are therefore evidence about diagnosis and adaptation, not a rate of irrecoverable incidents. Across its full v1 set, output hazards are easier on average (0.581) than invocation hazards, and the source calls execution, cross-source and especially invocation hazards dominant failure modes. Post-error retries occur in 44–76% of trajectories yet are weakly associated with success. The study's 200-task diagnostic reports a roughly 35–50-point baseline-to-clean-oracle gap. A hazard hint recovers roughly 60–80% of this loss, while more no-hint turns have much smaller gains. The supported inference is that the tested agents often need anomaly identification, not merely more calls.

For a deployment, recoverability must be defined by policy: a retry may be legitimate for an idempotent read but unsafe for payment, deletion, sending, booking, or any non-idempotent write. The evidence supports bounded, classified recovery with verification. It does not support unconstrained autonomous retry.

## Evaluator validity: measurement evidence versus controls

### 3. Validate the evaluator before using its score as a release gate

The evaluator-validity audit's 18.5% aggregate disagreement is not directly comparable with tau-bench, ToolBench-X, AgentDojo, or AgentProp-Bench rates because their tasks, agents, success definitions, and review methods differ. It nevertheless directly establishes that tool-agent evaluation can measure evaluator artifacts. Its tau² example is especially relevant: all five expected actions and database state matched, but a `$708` response was rejected because a required substring encoded `$1,628`, which included flights the user had asked to cancel. Conversely, a transfer-to-human without a required return tool call passed when unchanged state and an incomplete rubric allowed it.

The audit proposes decomposing invocation correctness, task completion, and outcome verification. That is an operational design proposal, supported by a reported Tool-Veritas agreement of 401/420 (95.5%) across 70 tasks and six models. It is not a universal guarantee: distributions and configurations differ from the four audited benchmarks, and all 19 reported disagreements were strict false negatives.

AgentProp-Bench supplies a separate evaluator calibration result, not corroboration through an independent audit of the same corpus. Its labels show why a substring heuristic must not gate deployment correctness. The source retained the LLM ensemble rather than selecting GPT-4o-mini despite the latter's higher κ on the calibration set, because selecting on that 100-label calibration set would overfit. A local evaluator should likewise pre-register its criteria, retain raw traces, blind human reviewers to automatic verdicts where feasible, quantify disagreement, and avoid selecting the judge solely because it wins on the same calibration labels.

### 4. Repetition must report uncertainty, not hide it

The 57.9–76.8% LiveMCPBench range is an end-to-end pipeline result: model trajectories vary and the default evaluator regenerates key points and then uses a stochastic judge. It is not an isolated judge-variance estimate. Still, it is sufficient to reject single-run leaderboard-like comparisons where the decision margin is smaller than plausible run variation. For local deployment, preserve seeds and versions where available, run enough repeats to estimate uncertainty, and report the full distribution or confidence interval alongside point estimates.

## Security boundaries and proposed controls

AgentDojo provides direct adversarial measurement in its simulated setting. It distinguishes benign utility, utility while attacked, and targeted ASR rather than treating a final answer as security evidence. On its full 629 security cases, model capability and attackability do not move in a simple favorable direction: the source reports stronger benign models can be easier to attack because a capable agent can also execute the malicious goal. GPT-4o's baseline Table 3 has 69.00% benign utility and 47.69% targeted ASR under the reported attack.

The source evaluates data delimiters, prompt-injection detection that aborts on a classifier hit, repeated user instructions after calls, and a pre-data tool filter. These are **tested design interventions**, not validated deployment boundaries. The prompt-injection detector's low ASR comes with substantial benign utility loss: 41.49% benign and 21.14% under attack. Repeating the prompt has 85.53% benign utility, 67.25% attacked utility and 27.82% targeted ASR in Table 5, but the prose warns it is unlikely to withstand an adaptive injection that tells the agent to ignore future instructions.

Tool filtering is the most useful permission-bound control in this evidence, provided the split actually exists: select the needed tool subset **before observing untrusted data**, and enforce that allowlist outside the model. The prose reports its ASR as 7.5%; Table 5 reports 6.84% (±2.0). This prose/table conflict is unresolved in the supplied v3 source and must be retained rather than normalized. The table is the more specific reported value, while both describe the same tested configuration. Crucially, the authors state the defense fails when future needed tools cannot be planned, when tools needed for benign work can also execute the attack (17% of test cases), and in multi-task persistent-context settings not covered by AgentDojo. It also cannot prevent a malicious tool result from biasing a recommendation without further tool hijacking.

AgentProp-Bench's interceptor result is a second, distinct operational-control experiment. Across five models, it reports reduced hallucination for tool-calling models: GPT-4o-mini −23.0 points, Qwen2.5-7B −24.0, Qwen2.5-14B −8.0, and Hermes-3-Llama-8B −4.0, with CIs excluding zero. Gemini-2.0-Flash is a −1.3-point null and rarely emits injectable tool calls. The source says threshold selection traces a model-specific precision/coverage frontier and that absolute arm rates lack human validation, although it argues shared judging bias makes between-arm deltas more robust. This supports testing an interceptor per model and operating point, not claiming it provides security.

## Source-bound decision table

| Decision criterion | Evidence and decision rule | Deployment consequence |
|---|---|---|
| **D1: Reliability release gate** | Use tau-bench's conceptual distinction: report first-run completion and all-repeat success, not only average success. Include task-family strata and confidence intervals. | Do not release on a single `pass^1` or one benchmark run. Set a local threshold for the deployment's task/impact class; this corpus supplies no universal threshold. |
| **D2: Recoverable tool failure** | Inject the five ToolBench-X v1 hazard classes only where a valid, policy-approved recovery exists. Record hazard, diagnosis, action, verification, and final state. | Permit bounded retry only for explicitly idempotent operations. For consequential writes, require a safe compensation/idempotency design or stop for review. |
| **D3: Evaluator validity** | Validate automatic verdicts against blinded trace-level human judgments and classify false positive/negative causes. Use separate invocation, completion, and outcome criteria. | A fluent answer cannot override a missing required state change. A state match cannot override missing authorization or a semantically wrong user outcome. |
| **D4: Security boundary** | Precompute a minimum tool allowlist before untrusted tool data and enforce it server-side. Evaluate attacks that use tools overlapping the benign allowlist. | Never treat model prompt instructions, delimiters, a detector, or a benchmark ASR as the permission boundary. Keep credentials and write authority out of the model's discretionary reach where possible. |
| **D5: Evidence retention** | Preserve model/version, system prompt, tool schemas/wrappers, policy, environment seed/state, tool outputs, evaluator version, attack corpus, and trace. | Results without those artifacts are not reproducible release evidence. |

## Smallest resolving evaluation for a deployment-specific permission-bounded agent

This is a proposed local evaluation design, not a reported experiment. It is the smallest design that directly resolves the unanswered deployment question while retaining the evidence distinctions above.

1. **Freeze the candidate configuration.** Name the exact model and version, agent prompt, tool schemas and wrappers, identity/authentication mechanism, server-side permission allowlists, data sources, evaluator code/version, and environment snapshot. Define the user objectives, prohibited actions, and the authorization evidence required for each consequential action.
2. **Create a small, representative task set.** Include normal read-only and write-authorized tasks, denied cross-user/cross-tenant requests, confirmation-required actions, and tasks that require the actual benign tool subset. Annotate accepted final state, required user-visible information, and forbidden state transitions. Do not require a single historical trajectory when more than one policy-compliant outcome exists.
3. **Run repeated clean tasks.** For each task, sample independent runs at the deployed settings and report first-run completion, all-runs-success probability at a declared k, task-family breakdown, and every trace. This resolves whether the candidate is stable under its own stochasticity, not whether tau-bench transfers.
4. **Run policy-approved recoverable failures.** For the same tasks, inject one classified fault at a time: stale schema/field, wrapper argument loss, transient execution failure, output serialization drift, and conflicting sources. Predeclare the sole allowed recovery path and a retry ceiling. Check that the agent neither fabricates a result nor performs a consequential action from incomplete evidence.
5. **Evaluate the boundary adversarially.** Place untrusted instructions in the actual data/tool-output channels. Include attacks requiring a forbidden tool, attacks requiring the same permitted tool as the benign task, and persistent-context/multi-task cases if the deployment has persistent context. Success requires both benign task completion and zero prohibited state transition or disclosure. If the benign and malicious goals share an unavoidable powerful tool, this evaluation cannot establish a prompt-level defense. Redesign permissions or split the operation.
6. **Calibrate scoring and decide.** Blindly human-review a stratified set of traces, compare it to automatic labels, and publish false-positive/negative counts. Reject any automatic pass with a failed authorization/state gate. Re-run the full candidate evaluation enough times to estimate uncertainty. Approve only if the predeclared reliability, recovery, evaluator-agreement, and zero-prohibited-action criteria all hold. Otherwise the smallest useful conclusion is the failure mode, not a general security claim.

## Material limitations

- The corpus has no live deployment, real user, real credential, cost, latency, uptime, or incident data. Missing values are unknown.
- tau-bench's simulated users and simplified retail/airline policies, ToolBench-X v1's deterministic tools and intentionally recoverable hazards, and AgentDojo's synthetic data/tested attack catalog constrain transfer to a production agent.
- ToolBench-X evidence is strictly v1. No v2 claim is made here.
- The evaluator audit and AgentProp-Bench study different benchmarks, samples, calibration procedures, and agents. Their evaluator results must remain separate.
- AgentDojo's unresolved prose/Table 5 tool-filter ASR conflict is preserved: 7.5% in prose and 6.84% (±2.0) in the table.
- Proposed operational controls are recommendations derived from the studies' conditions and limitations, not measurements of the target deployment.
