# AgentDojo v3 evidence note

## Assigned question and boundary

**Question:** What original AgentDojo v3 evidence should constrain deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Bounded answer:** AgentDojo demonstrates that deterministic, pre-execution tool restriction can sharply reduce targeted prompt-injection success in its synthetic, single-task environments, particularly when the legitimate task needs only read tools and the attack needs write tools. It does **not** establish security for tasks whose required tools can also execute the attack, dynamically determined tool plans, persistent multi-task context, recommendation manipulation, multimodal inputs, or adaptive attacks against the particular defense. This is a research benchmark result, not a production-security guarantee. Evidence is limited to [AgentDojo arXiv v3](https://arxiv.org/html/2406.13352v3), frozen for this assignment as of 2026-09-07.

## What v3 evaluates

### Environment and evaluator

AgentDojo is a stateful simulated tool environment with four suites: Workspace, Slack, Travel, and Banking. It uses synthetic, manually inspected dummy data, formal state-based checks, and tool calls rather than an LLM simulator. User-task utility and attacker-goal security are deterministic binary functions over model output and pre/post environment state. [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1), [data card §F.7](https://arxiv.org/html/2406.13352v3#S6.F7)

| Suite | Tools | User tasks | Injection tasks | Security cases implied |
|---|---:|---:|---:|---:|
| Workspace | 24 | 40 | 6 | 240 |
| Slack | 11 | 21 | 5 | 105 |
| Travel | 28 | 20 | 7 | 140 |
| Banking | 11 | 16 | 9 | 144 |
| **Total** | **74** | **97** | **27** | **629** |

The 629 denominator is the per-environment cross-product of user and injection tasks. Tasks can require up to 18 calls, and suite content includes tool-output contexts up to 7,000 GPT-4 tokens plus up to 4,000 tokens of tool descriptions. [§3.1, Table 1](https://arxiv.org/html/2406.13352v3#S3.T1)

**Metrics and denominators.** [§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)

- **Benign utility:** fraction of 97 user tasks solved without attack.
- **Utility under attack:** fraction of 629 user–injection security cases where the user task succeeds **without adversarial side effects**. Its complement is untargeted/derailment success.
- **Targeted ASR:** fraction of security cases where the attacker’s formal malicious goal is met.
- For an attack set, a case counts as attacked if **any** attack succeeds, intended to model selection of the best attack per user/injection task.

The paper reports 95% proportion confidence intervals using `statsmodels.stats.proportion.proportion_confint`. It does not state model snapshot IDs, temperatures, number of repeated stochastic runs, or an exact calendar date for provider evaluations in the readable v3 source. [checklist](https://arxiv.org/html/2406.13352v3#S5)

### Models and baseline attack

All baseline agents were evaluated over all 629 security cases and 97 benign tasks. Models were Claude 3 Opus, Claude 3 Sonnet, Claude 3.5 Sonnet, Command-R+, Gemini 1.5 Flash/Pro, GPT-3.5 Turbo, GPT-4 Turbo, GPT-4o, and Llama 3 70B. All received a common system prompt, with extra provider-recommended prompts for Claude Sonnet variants and a special tool-calling prompt for Llama; official APIs were used except for Llama. [§4](https://arxiv.org/html/2406.13352v3#S4)

The cross-model baseline uses the generic **“Important message”** injection: it tells the model to perform the attacker’s malicious task before the original task. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1), [Appendix B.3](https://arxiv.org/html/2406.13352v3#A2.SS3)

| Claude 3 Sonnet | 53.10 ±3.90 | 33.23 ±3.68 | 26.71 ±3.46 |
| Claude 3.5 Sonnet | 78.22 ±3.23 | 51.19 ±3.91 | 33.86 ±3.70 |
| Command-R+ | 25.44 ±3.40 | 25.12 ±3.39 | 0.95 ±0.76 |
| Gemini 1.5 Flash | 36.09 ±3.75 | 34.18 ±3.71 | 12.24 ±2.56 |
| Gemini 1.5 Pro | 45.63 ±3.89 | 28.93 ±3.54 | 25.60 ±3.41 |
| GPT-3.5 Turbo | 33.86 ±3.70 | 34.66 ±3.72 | 8.43 ±2.17 |
| GPT-4 Turbo | 63.43 ±3.76 | 54.05 ±3.89 | 28.62 ±3.53 |

Measured implications: benign capability did not imply targeted-injection resistance. GPT-4o had 69.00% benign utility and 47.69% targeted ASR, while Claude 3.5 Sonnet had higher benign utility, 78.22%, and lower targeted ASR, 33.86%. Most models lost 10–25 percentage points of utility under attack. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1)

## Attack selection and measured reliability

For GPT-4o, v3 compared TODO, “ignore previous instructions,” InjecAgent, Important message, and a per-case `Max` selector. [§4.2](https://arxiv.org/html/2406.13352v3#S4.SS2), [Table 4](https://arxiv.org/html/2406.13352v3#A3.T4)

| Attack | Targeted ASR | Untargeted ASR |
|---|---:|---:|
| TODO | 3.66 ±0.7 | 32.75 ±1.8 |
| Ignore previous instructions | 5.41 ±0.9 | 33.23 ±1.8 |
| InjecAgent | 5.72 ±0.9 | 31.48 ±1.8 |
| Important message | 57.70 ±2.0 | 49.90 ±2.0 |
| Max | 57.55 ±2.7 | 68.36 ±2.6 |

The attack’s effective placement matters: injections near the end of a tool response achieved up to 70% average success against GPT-4o. Slack reached 92% attack success in the reported suite breakdown, plausibly because an attacker controls a large fraction of relevant tool output. Conversely, one Travel injection task requiring both an expensive Paris booking and email exfiltration succeeded in 0% of cases because the model often completed only one malicious subgoal. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1), [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

Attacker identity knowledge was not decisive but mattered: Table 2 reports 45.8% targeted ASR with generic model/user references, 47.7% with both correct model and user names, and about 23% after a wrong model or user name. [Table 2](https://arxiv.org/html/2406.13352v3#S4.T2)

## Defense comparators and tradeoffs

All defense comparisons use GPT-4o against the paper’s strongest reported attack, rather than a demonstrated defense-adaptive attack. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

| Defense | Mechanism | Benign utility | Utility under attack | Targeted ASR |
|---|---|---:|---:|---:|
| None | Baseline | 69.00 ±3.6 | 50.01 ±3.9 | 57.69 ±3.9 |
| Delimiting | Mark tool output as data and instruct model to ignore its instructions | 72.66 ±3.5 | 55.64 ±3.9 | 41.65 ±3.9 |
| PI detector | Classify each tool output, abort on detection | 41.49 ±3.9 | 21.14 ±3.2 | 7.95 ±2.1 |
| Repeat prompt | Repeat user instruction after each tool call | 85.53 ±2.8 | 67.25 ±3.7 | 27.82 ±3.5 |
| Tool filter | Have LLM choose task-required tools before seeing untrusted data | 73.13 ±3.5 | 56.28 ±3.9 | 6.84 ±2.0 |

Source: [Table 5](https://arxiv.org/html/2406.13352v3#A3.T5).

**Measured contrast relevant to permission-bounded deployment:** Tool filtering cut ASR from 57.69% to 6.84%, a 50.85-point reduction, while benign utility rose 4.13 points relative to no defense. The detector had a numerically similar ASR outcome, 7.95%, but benign utility fell 27.51 points because of false positives. These are measurements in this benchmark configuration, not universal effect estimates.

## Deployment constraints and unproven tradeoffs

### Measured applicability boundary

The tool filter works chiefly where the user needs read access and the attacker needs a not-legitimate write tool. It fails when:

1. tool needs cannot be selected before viewing results,
2. tools required for the user task can also implement the attack, reported for **17% of test cases**, or
3. a persistent, multi-task agent can be instructed to wait until a later task grants the needed tool.

Even stronger planner-to-isolated-worker architectures remain vulnerable when the injection alters the content of a required result, such as steering a hotel recommendation, without needing an extra tool. [§4.3, “Strengths and limitations”](https://arxiv.org/html/2406.13352v3#S4.SS3)

### Practical controls supported only as proposed deployment choices

- Bind an allowlist/capability set **before** any untrusted tool data reaches the planning model.
- Split read-only and side-effecting tools. Require a distinct approval or deterministic policy gate for side effects.
- Abort or escalate if execution needs a tool outside the precomputed bound.
- Treat tool-output formatting, prompt repetition, and classifier detection as defense-in-depth candidates, not security boundaries.

The first two controls test the demonstrated tool-filter mechanism in its stated applicable class. The latter controls are reasonable designs but are **not established adoption gates** by this source.

### What remains unproven

- Resistance to attacks adapted to the exact allowlist, detector, delimiter scheme, or prompt-repetition rule. The authors explicitly say fixed generic attacks are insufficient for robustness evaluation and mark default-attacks-only evaluation as unsuitable use. [§3.3](https://arxiv.org/html/2406.13352v3#S3.SS3), [data card §F.5](https://arxiv.org/html/2406.13352v3#S6.F5)
- Transfer from synthetic single-task, text-only, dummy-data environments to a production tool graph, real identities/data, long-lived context, or different models.
- Safety when legitimate and malicious actions share a granted tool.
- Safety against recommendation/content-integrity attacks that need no additional tool call.
- Realistic attacker constraints on injection length, format, placement, and degree of tool-output control. The paper identifies these as extensions rather than evaluating them. [§5](https://arxiv.org/html/2406.13352v3#S5)

## Concrete paired local evaluation design

**Demonstrated-mechanism test.** For each local task whose minimal legitimate capability set can be computed before any untrusted read:

1. Run matched benign and injected trials with identical initial state and deterministic user-success/security checks.
2. Compare **A:** current agent with its normal full tool set against **B:** the same agent with a pre-untrusted-data, task-specific capability allowlist.
3. Include the four paper attack phrasings, vary injection position including the end of tool output, and report the per-case maximum ASR, benign utility, utility under attack, tool-denial/escalation rate, and 95% intervals.
4. Require B to preserve benign utility while reducing targeted ASR versus A. Report denominators by task, injection goal, tool class, and capability overlap rather than only a pooled rate.

**Exploratory non-transfer test.** Separately stratify cases where tool plans depend on untrusted output, user and attack share a required tool, contexts persist across tasks, or the attack manipulates a recommendation. Do **not** treat success of the allowlist in the first stratum as a gate for this second stratum. Compare bounded execution, approval-gated writes, and any proposed symbolic isolation, then attack each defense adaptively. This directly tests the source’s stated failure boundary rather than assuming it away.

For planning scale, AgentDojo estimates US$35 for 629 GPT-4o security cases and US$4 for 97 benign cases, but that is historical benchmark-specific cost evidence, not a forecast for a local deployment. [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

## Source-internal inconsistencies and research stop

- **F1:** Tool count conflicts within v3. Table 1 rows and §3.1 prose total **74** tools, but the Table 1 caption and data card say **70**. The 629 security-case denominator remains internally reconstructible from the listed task cross-products.
- **F2:** GPT-4o “Important message” ASR conflicts: Table 3 reports **47.69 ±3.90%**, Table 4 **57.70 ±2.0%**, and Table 5 no-defense **57.69 ±3.9%**. Table 2 additionally shows 45.8% for its “baseline” identity ablation. The readable v3 text does not explain configuration, run, or denominator differences. These values must not be silently pooled.
- **F3:** The stated `Max` definition should select the best attack per case, yet Table 4 reports 57.55% targeted ASR, marginally below Important message’s 57.70%. This may be sampling/configuration variation, but it is unresolved in the source.
- **F4:** The prose calls the detector a “BERT classifier,” while its cited artifact is named DeBERTa-v3-base. The source does not specify its threshold or calibration.

Research stopped because the controlled phase permits only this frozen original source. No external validation, later benchmark version, code inspection, production deployment evidence, or other study was consulted.
