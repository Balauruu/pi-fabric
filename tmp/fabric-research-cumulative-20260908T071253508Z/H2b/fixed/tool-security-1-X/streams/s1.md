# AgentDojo v3 evidence note

## Assigned question and boundary

**Question:** What original AgentDojo v3 evidence constrains deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Scope:** Only the frozen original [AgentDojo arXiv v3](https://arxiv.org/html/2406.13352v3), including its appendices. This is evidence about a simulated, stateful text-tool environment, not a production-security guarantee.

## Bounded answer

AgentDojo supports deploying **preplanned, least-privilege tool scopes** as a practical defense layer, but not treating it as a complete prompt-injection solution. In its GPT-4o defense experiment, tool filtering had the lowest reported targeted-ASR (6.84% ±2.0) while retaining 73.13% ±3.5 benign utility. It explicitly fails when required tools cannot be determined before untrusted data, when user-required tools can also execute the attack, and in persistent multi-task contexts. The source says that overlap applies to 17% of its cases. [§4.3; Table 5](https://arxiv.org/html/2406.13352v3#S4.SS3)

## Findings

### F1. What v3 evaluates

AgentDojo uses four simulated, mutable environments: Workspace, Slack, Travel, and Banking. Agents receive tool documentation, use text-formatted tool outputs (YAML in the reported runtime), and alter environment state. Success is evaluated with deterministic binary utility and security functions over model output and pre/post state, rather than an LLM judge. [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1)

Reported suite composition is:

| Environment | Tools | User tasks | Injection targets |
|---|---:|---:|---:|
| Workspace | 24 | 40 | 6 |
| Slack | 11 | 21 | 5 |
| Travel | 28 | 20 | 7 |
| Banking | 11 | 16 | 9 |
| **Total** | **70** | **97** | **27** |

The security evaluation cross-products relevant user and injection tasks, yielding **629 security cases**. Benign evaluation has **97 user tasks**. Tasks can require up to 18 calls, use data contexts up to 7,000 GPT-4 tokens plus up to 4,000 tokens of tool descriptions, and injection goals span one to 20 steps. [§3.1, Table 1](https://arxiv.org/html/2406.13352v3#S3.T1)

Metrics are:

- **Benign utility:** fraction of 97 user tasks correctly solved without attack.
- **Utility under attack:** fraction of security cases where the user task is correctly solved **without adversarial side effects**.
- **Targeted ASR:** fraction of security cases where the attacker goal is met.
- An attack collection is scored successful if **any** attack succeeds on a case, intended to model an adaptive attacker selecting the best attack per task. [§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)

### F2. Baseline-model evidence

All models were given a common system prompt. Claude 3/3.5 Sonnet received an additional Anthropic-recommended prompt; Llama 3 70B received an additional adapted tool-calling prompt. Official provider APIs were used except for Llama 3. [§4](https://arxiv.org/html/2406.13352v3#S4)

Against the generic “Important message” injection, Table 3 reports:

| Model | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| Claude 3 Opus | 66.61% ±3.69 | 52.46% ±3.90 | 11.29% ±2.47 |
| Claude 3 Sonnet | 53.10% ±3.90 | 33.23% ±3.68 | 26.71% ±3.46 |
| Claude 3.5 Sonnet | 78.22% ±3.23 | 51.19% ±3.91 | 33.86% ±3.70 |
| Command-R+ | 25.44% ±3.40 | 25.12% ±3.39 | 0.95% ±0.76 |
| Gemini 1.5 Flash | 36.09% ±3.75 | 34.18% ±3.71 | 12.24% ±2.56 |
| Gemini 1.5 Pro | 45.63% ±3.89 | 28.93% ±3.54 | 25.60% ±3.41 |
| GPT-3.5 Turbo | 33.86% ±3.70 | 34.66% ±3.72 | 8.43% ±2.17 |
| GPT-4 Turbo | 63.43% ±3.76 | 54.05% ±3.89 | 28.62% ±3.53 |
| GPT-4o | 69.00% ±3.61 | 50.08% ±3.91 | 47.69% ±3.90 |
| Llama 3 70B | 34.50% ±3.71 | 18.28% ±3.02 | 20.03% ±3.13 |

[Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3.T3)

Interpretation constrained to this experiment: capability did not monotonically improve targeted security. GPT-4o had high benign utility but high reported ASR. Low-ASR models may simply fail to execute attacker goals. Most models lost 10–25 percentage points of utility under attack. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1)

### F3. Attack selection and attack-condition evidence

The baseline “Important message” tells the agent to perform the malicious task before the user task. Attacks are inserted only into placeholders in tool outputs required by the user-task ground-truth call sequence. This makes injections likely to be retrieved, but means the evaluation is not a sample of arbitrary naturally encountered untrusted content. [§4.1; Appendix A](https://arxiv.org/html/2406.13352v3#S4.SS1)

For GPT-4o, Table 4 compares four prompt phrasings and “Max”:

| Attack | Targeted ASR | Untargeted ASR |
|---|---:|---:|
| TODO | 3.66% ±0.7 | 32.75% ±1.8 |
| Ignore previous | 5.41% ±0.9 | 33.23% ±1.8 |
| InjecAgent | 5.72% ±0.9 | 31.48% ±1.8 |
| Important message | 57.7% ±2.0 | 49.9% ±2.0 |
| Max | 57.55% ±2.7 | 68.36% ±2.6 |

[Appendix C, Table 4](https://arxiv.org/html/2406.13352v3#A3.T4)

The source also reports that correct model and user names modestly strengthened a related baseline from 45.8% to 47.7%, while a wrong user or model name reduced it to 23.2% and 23.7%, respectively. It reports Slack at 92% ASR and up to 70% average GPT-4o ASR for injections near the end of a tool response. [§4.1–4.2; Appendix D](https://arxiv.org/html/2406.13352v3#S4.SS2)

### F4. Defense comparators and tradeoffs

GPT-4o was the sole model used for defense and attack-component ablations because it had the highest reported benign utility in the authors’ suite at the time of those experiments. The tested defenses were delimiters, a per-tool-output DeBERTa/BERT-style injection detector that aborts on detection, prompt sandwiching, and pre-data tool filtering. [§4; §4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

| Defense | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| No defense | 69.00% ±3.6 | 50.01% ±3.9 | 57.69% ±3.9 |
| Delimiting | 72.66% ±3.5 | 55.64% ±3.9 | 41.65% ±3.9 |
| PI detector | 41.49% ±3.9 | 21.14% ±3.2 | 7.95% ±2.1 |
| Repeat prompt | 85.53% ±2.8 | 67.25% ±3.7 | 27.82% ±3.5 |
| Tool filter | 73.13% ±3.5 | 56.28% ±3.9 | 6.84% ±2.0 |

[Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3.T5)

Measured implications:

- **Tool filtering:** strongest reported targeted-ASR reduction with no reported benign-utility loss versus its undefended Table-5 comparator.
- **Detector:** similarly low ASR but substantial utility loss, attributed to false positives.
- **Prompt repetition:** better utility and lower ASR for this attack, but authors explicitly judge it unlikely to survive an adaptive injection that tells the model to ignore future instructions.
- **Delimiters:** modest improvement only. No tested defense reached zero ASR. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

## Operational boundaries and unproven tradeoffs

1. **Preplanning boundary:** Tool filtering fails when later tool output determines the necessary tools.
2. **Permission-overlap boundary:** It cannot prevent attacks that are executable through the same tools required by the user task. The source reports this for **17%** of its test cases.
3. **Session boundary:** The benchmark does not cover continuing multi-task conversations. An injection may wait until a later task grants a useful tool.
4. **Semantic-integrity boundary:** Even stronger isolation remains vulnerable when an injection changes a tool result or recommendation rather than causing an extra tool call.
5. **Threat-model boundary:** The original attacks and defenses are described as relatively simple. The paper says a default static attack set is unsuitable for robustness claims and calls for strong adaptive attack evaluation.
6. **Environment boundary:** Four synthetic text environments with dummy data do not establish transfer to real permissions, real data, multimodal inputs, or a production agent’s tool semantics. [§4.3; §5; Appendix F](https://arxiv.org/html/2406.13352v3#S4.SS3)

## Source conflicts and qualifications

- **C1 — GPT-4o baseline ASR conflict:** Table 3 reports GPT-4o targeted ASR **47.69% ±3.90**; Table 5’s “No defense” reports **57.69% ±3.9**. The source does not explain the different runs/configurations. Do not compare these as a single denominator-matched baseline.
- **C2 — Adaptive-attack conflict:** Section 4.2 says Max improves success “by another 10%,” yet Table 4 reports Max targeted ASR **57.55%**, slightly below Important message’s **57.7%**. The original source does not resolve this. The reported cells must not be silently corrected.
- **C3 — Tool-count conflict:** prose says **74 tools**, Table 1 totals **70**, and the data card says **70**. The task count also differs: the paper describes 97 user tasks plus 27 injection targets, while the data card calls the dataset “124 tasks.” Treat 70 tools / 97 user tasks / 629 security cases as the table and evaluation denominators, while retaining the conflict.

## Proposed paired local transfer evaluation

This is a proposed control, not measured AgentDojo evidence.

Run the same local stateful task set in two configurations:

- **P0:** normal agent with all tools available.
- **P1:** permission-bounded agent selects an allowlist before reading untrusted tool output. Enforce this allowlist outside the model at the tool gateway.

For each user task, construct paired cases with identical initial state and injected untrusted content at every realistically attacker-controlled retrieval point. Include at minimum the four reported prompt families, placement near the beginning and end of outputs, correct/incorrect system and user identity variants, and a defense-aware attack set. Partition cases before reporting:

- **disjoint-permission:** attack needs a write/effect tool absent from the user-task allowlist;
- **overlap:** attack can use a user-required tool;
- **adaptive-tool:** a later result determines needed permissions;
- **persistent-context:** an injection can wait for a later task;
- **semantic-integrity:** no extra tool call, but malicious content changes a recommendation or decision.

For each configuration and partition, report deterministic task success, task success without unauthorized side effects, targeted ASR, blocked-call count, false-block/abort rate, and permission expansion events. Preserve denominators and report confidence intervals. The decisive transfer result is not overall ASR alone: P1 should reduce ASR in **disjoint-permission** cases without unacceptable utility loss, while exposing its expected failure rate in the other four partitions.

## Decision constraint and research stop

Deploy permission bounding as a **gateway-enforced, pre-data least-privilege control** for tasks whose required capabilities can be fixed and are disjoint from sensitive effects. Pair it with explicit approval or separate authorization for high-impact effects. Do not represent it as a general prompt-injection defense.

Research stopped because the controlled override permits only the supplied original v3 source. The unresolved configuration conflicts, adaptive-defense robustness, persistent context, dynamic permission discovery, and semantic-integrity attacks require a local paired evaluation rather than extrapolation from this benchmark.
