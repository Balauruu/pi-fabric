# AgentDojo v3 evidence note

## Assigned question and boundary

**Question:** What original AgentDojo v3 evidence constrains deployment of a permission-bounded tool agent, and which defense tradeoffs remain unproven?

**Bounded answer:** AgentDojo v3 measures deterministic task completion and attacker-goal completion in four synthetic, stateful tool environments. It is strong evidence that an agent should have **task-scoped, least-privilege tool authority** and that this control must be evaluated against attacks tailored to its authority. It is **not** evidence of a production-security guarantee: its tool filter is only measured against a small fixed prompt set, does not solve cases where legitimate and malicious actions use the same tools, and does not cover persistent multi-task contexts. Source: [AgentDojo v3](https://arxiv.org/html/2406.13352v3).

Scope is the frozen v3 source only, as requested. “Measured” below means the paper reports it. The local evaluation design is a proposed transfer test, not a paper result.

## F1. What v3 evaluates

- **Environment:** four mutable, simulated environments: Workspace, Slack, Travel, and Banking. Agents use documented tools, receive YAML-formatted tool outputs, and operate over dummy data. User utility and attacker security checks are deterministic binary functions over model output plus before/after environment state, rather than LLM judging. [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1)
- **Workload:** 97 user tasks and 629 user-task/injection-task security cases. Tasks can require up to 18 calls, context data up to 7,000 GPT-4 tokens, and tool descriptions up to 4,000 GPT-4 tokens. [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1), [§4](https://arxiv.org/html/2406.13352v3#S4)
- **Attack setup:** per environment, security cases are the cross-product of relevant user and injection tasks. Injection candidates are restricted to placeholders in outputs of tools required by the user task’s ground-truth call sequence. This improves relevance but gives the benchmark attacker privileged knowledge of the task-required tools and controllable endpoints. [§3](https://arxiv.org/html/2406.13352v3#S3), [Appendix A](https://arxiv.org/html/2406.13352v3#A1)
- **Metrics and denominators:** benign utility is the fraction of the **97** user tasks solved with no attack. Utility under attack is the fraction of the **629** security cases where the user task succeeds with no adversarial side effect. Targeted ASR is the fraction of those security cases in which the attacker goal is achieved. A multi-attack “Max” is successful if *any* attack succeeds for a case. [§3.4](https://arxiv.org/html/2406.13352v3#S3.SS4)

## F2. Models, baseline attack, and outcomes

All models received a common system prompt, with extra provider-recommended prompts for Claude Sonnet variants and a separate adapted tool-calling prompt for Llama 3 70B. Official APIs were used except Llama 3. The baseline was “Important message,” which tells the agent to perform the malicious task before the original task. [§4–4.1](https://arxiv.org/html/2406.13352v3#S4)

**Table 3, percentages with reported 95% confidence intervals:**

|---|---:|---:|---:|
| Claude 3 Opus | 66.61 ±3.69 | 52.46 ±3.90 | 11.29 ±2.47 |
| Claude 3 Sonnet | 53.10 ±3.90 | 33.23 ±3.68 | 26.71 ±3.46 |
| Claude 3.5 Sonnet | 78.22 ±3.23 | 51.19 ±3.91 | 33.86 ±3.70 |
| Command-R+ | 25.44 ±3.40 | 25.12 ±3.39 | 0.95 ±0.76 |
| Gemini 1.5 Flash | 36.09 ±3.75 | 34.18 ±3.71 | 12.24 ±2.56 |
| Gemini 1.5 Pro | 45.63 ±3.89 | 28.93 ±3.54 | 25.60 ±3.41 |
| GPT-3.5 Turbo | 33.86 ±3.70 | 34.66 ±3.72 | 8.43 ±2.17 |
| GPT-4 Turbo | 63.43 ±3.76 | 54.05 ±3.89 | 28.62 ±3.53 |
| GPT-4o | 69.00 ±3.61 | 50.08 ±3.91 | 47.69 ±3.90 |
| Llama 3 70B | 34.50 ±3.71 | 18.28 ±3.02 | 20.03 ±3.13 |

Source: [Appendix C, Table 3](https://arxiv.org/html/2406.13352v3#A3.T3).

**Decision-relevant contrast:** GPT-4o lost 18.92 percentage points of utility under attack versus benign performance and had the highest reported Table-3 ASR, 47.69%. Claude 3.5 Sonnet had higher benign utility but lower reported ASR. This is evidence about those specific model/prompt/API configurations, not a general model-ranking claim.

Additional measured heterogeneity: GPT-4o’s Slack-suite ASR was 92%; a Travel injection requiring both an expensive booking and personal-data email exfiltration succeeded in 0% of cases. End-of-tool-output injection placement reached up to 70% average success against GPT-4o. [§4.1](https://arxiv.org/html/2406.13352v3#S4.SS1), [Appendix D](https://arxiv.org/html/2406.13352v3#A4)

## F3. Attack comparisons and source conflict

For GPT-4o, v3 compares TODO, “ignore previous instructions,” InjecAgent, Important Message, and “Max,” defined as selecting the best of those prompts per case. [§4.2](https://arxiv.org/html/2406.13352v3#S4.SS2)

| Attack | Targeted ASR | Untargeted ASR |
|---|---:|---:|
| TODO | 3.66 ±0.7 | 32.75 ±1.8 |
| Ignore previous | 5.41 ±0.9 | 33.23 ±1.8 |
| InjecAgent | 5.72 ±0.9 | 31.48 ±1.8 |
| Important message | 57.70 ±2.0 | 49.90 ±2.0 |
| Max | 57.55 ±2.7 | 68.36 ±2.6 |

Source: [Appendix C, Table 4](https://arxiv.org/html/2406.13352v3#A3.T4).

**C1. Internal numerical conflict:** Table 3 reports GPT-4o targeted ASR **47.69%**, while Table 4 reports Important Message targeted ASR **57.70%**, and Table 5’s no-defense row reports **57.69%**. Table 2 also gives 45.8% for a generic-name baseline and 47.7% with correct model and user names. The prose says “Max” boosts success by another 10%, yet its Table-4 targeted ASR, 57.55%, is slightly below Important Message’s 57.70%. The source does not reconcile these configurations. They must not be combined as one baseline or used to calculate defense deltas across tables without reproducing the exact run configuration.

## F4. Defense comparators and measured tradeoffs

Defenses were evaluated on **GPT-4o** against the authors’ “strongest attack,” with the paper presenting the following comparators:

1. Data delimiters plus an instruction to ignore embedded instructions.
2. A per-tool-output BERT prompt-injection detector that aborts on detection.
3. Prompt sandwiching, repeating the user instruction after each call.
4. Tool filter, where the LLM selects needed tools before it sees untrusted data.  
   Source: [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

| Defense | Benign utility | Utility under attack | Targeted ASR |
|---|---:|---:|---:|
| None | 69.00 ±3.6 | 50.01 ±3.9 | 57.69 ±3.9 |
| Delimiting | 72.66 ±3.5 | 55.64 ±3.9 | 41.65 ±3.9 |
| PI detector | 41.49 ±3.9 | 21.14 ±3.2 | 7.95 ±2.1 |
| Repeat prompt | 85.53 ±2.8 | 67.25 ±3.7 | 27.82 ±3.5 |
| Tool filter | 73.13 ±3.5 | 56.28 ±3.9 | 6.84 ±2.0 |

Source: [Appendix C, Table 5](https://arxiv.org/html/2406.13352v3#A3.T5).

**Measured interpretation:**

- Tool filtering had the lowest reported ASR, 6.84%, while preserving 73.13% benign utility. This supports permission-bounded tool exposure as a practical control in this benchmark.
- The detector also reduced ASR, 7.95%, but benign utility fell to 41.49%, consistent with the authors’ stated false-positive problem.
- Delimiters and prompt repetition improved the reported utility/ASR combination for this attack, but are prompt-level controls, not authority boundaries.
- All listed defenses still lost substantial utility under attack. The paper characterizes this as 15–20 percentage points. [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

## F5. Operational boundaries and unproven tradeoffs

**Measured failure conditions for tool filtering:**

- It fails when required tools cannot be planned before untrusted outputs are seen.
- It fails when the user’s legitimate tool set is sufficient for the malicious action. The paper says this applies to **17% of its security cases**.
- It may fail across multiple user tasks in a retained context, which AgentDojo does not cover, because an injection can wait for a later task that grants the needed tools.  
  Source: [§4.3](https://arxiv.org/html/2406.13352v3#S4.SS3)

**Unproven, not negative results:**

- No adaptive attack optimized specifically against each evaluated defense was reported. The paper explicitly says fixed attacks can make a non-robust defense appear successful and its data card says default attacks alone are unsuitable for robustness evaluation. [§3.3](https://arxiv.org/html/2406.13352v3#S3.SS3), [data card §F.5.2](https://arxiv.org/html/2406.13352v3#S5)
- More elaborate planner-to-isolated-worker architectures are suggested, not evaluated. The paper also states that symbolic isolation would remain vulnerable when injected content only changes a recommendation rather than causing an additional tool call.
- The benchmark uses synthetic, manually inspected dummy state and text-only tools. It does not establish transfer to real identities, permissions, data formats, durable sessions, multimodal inputs, or an attacker constrained by realistic injection length/format. The latter two are named future extensions. [§5](https://arxiv.org/html/2406.13352v3#S5), [data card](https://arxiv.org/html/2406.13352v3#S5)
- The source has an environment-tool-count inconsistency: prose says **74** tools, Table 1 caption and data card say **70**. The per-environment Table-1 counts sum to 74. This does not affect the 97/629 denominators but is a reproducibility qualification. [§3.1](https://arxiv.org/html/2406.13352v3#S3.SS1)

## Proposed paired local transfer evaluation

Run a paired, state-reset evaluation of the actual agent, with identical model, prompts, task cases, tool schemas, runtime limits, and injection placements:

- **A:** current full tool exposure.
- **B:** pre-untrusted-data capability plan that exposes only the minimal task-scoped tools, enforced outside the LLM. Log denied attempts and selected capabilities.

Include benign cases and paired user-task × attacker-goal cases. For every security case, test the original prompt families plus defense-aware variants that target the planner/filter, tool-overlap cases, delayed/persistent-context cases, and recommendation-manipulation cases. Report the same three AgentDojo metrics with separate denominators, 95% intervals, per-capability-family ASR, and an explicit count of cases where legitimate authority can already perform the attacker action.

**Deploy gate proposed from this evidence:** permission bounding is a useful defense-in-depth control only if B preserves acceptable benign utility and materially reduces targeted ASR under adaptive, local attacks. Do not treat a reduction against the fixed four-prompt set as a security guarantee.

## Remaining gaps and stop reason

The frozen original does not provide an adaptive-defense result, production transfer result, persistent-session result, multimodal result, or a reconciliation of the conflicting GPT-4o/attack-table values and tool totals. Research stopped because the controlled override limited evidence to this one frozen original source.
