# Fixed-model coding-agent run design: evidence note

**Question and scope.** As of 2026-09-07, what run-design changes improve a coding agent while its base model and reasoning effort remain fixed? Scope is repository-level GitHub issue repair, principally SWE-bench/Lite. Status: **partial but decision-grade for context, validation, and sampling**. Results do not establish production security, cross-language generality, or universal rankings.

## Findings

### Material evidence units

**E1 — bounded context and tool feedback improve one fixed GPT-4 Turbo agent configuration.**  
Source: [SWE-agent](https://arxiv.org/html/2405.15793), Table 3 and §5.1, source-unique in this note.  
- **Task/method:** SWE-bench Lite, 300 self-contained functional bug fixes. Ablations hold the SWE-agent/GPT-4 Turbo configuration fixed and vary one interface choice.
- **Comparator and result:** baseline 100-line viewer plus last-five observations resolves **18.0% (54/300)**. A 30-line viewer resolves **14.3%** (−3.7 points), whole-file context **12.7%** (−5.3), full conversation history **15.0%** (−3.0), no demonstration **16.3%** (−1.7), no edit interface **10.3%** (−7.7), and iterative rather than summarized search **12.0%** (−6.0).
- **Feedback/repair:** removing linting lowers resolution from **18.0% to 15.0%**. The paper attributes this to visible syntax-error feedback and recovery.
- **Cost condition:** Table 1 reports SWE-agent GPT-4 Turbo at **$1.67 average per Lite task** versus shell-only **$1.46** and RAG **$0.13**. Higher success is not free.
- **Decision:** use bounded, task-focused context and explicit machine-readable edit feedback. Do not assume more history or complete files improve performance.

**E2 — repair recovery is fragile after a failed edit.**  
Source: [SWE-agent](https://arxiv.org/html/2405.15793), Appendix B.3.3 / Figure 20, source-unique.  
- **Task/model:** all **2,294** SWE-bench trajectories for SWE-agent with GPT-4 Turbo.
- **Result:** **51.7% (1,185/2,294)** trajectories have at least one failed edit. An edit attempt has a **90.5%** eventual-success probability before a failed edit, falling to **57.2%** after one failed edit, a **42.8%** probability of never recovering after that error.
- **Decision:** make failed-edit handling a distinct repair state: expose the exact failure, re-read the changed region, and cap repeated identical repairs rather than consuming a general action budget.

**E3 — validation-driven selection can substantially change accepted-task yield, at measured marginal cost.**  
Source: [Agentless](https://arxiv.org/html/2407.01489), §5.2.3 Table 4, source-unique.  
- **Task/model/method:** SWE-bench Lite, **300** tasks; GPT-4o (`gpt-4o-2024-05-13`). The authors vary patch selection while retaining the default localization and repair pipeline.
- **Comparator/result:** majority voting selects **77/300, 25.67%**, at **$0.00** incremental average cost. Adding existing regression-test filtering gives **81/300, 27.00%**, at **$0.01**. Adding generated reproduction-test selection gives **96/300, 32.00%**, at **$0.25**.
- **Decision dimension:** accepted-task efficiency. The reported extra **$0.25/task** corresponds to +19 selected passing patches versus voting, but this is benchmark-specific and includes generated-test cost.

**E4 — decomposition plus diversified candidates outperformed merged context in the same GPT-4o repair pipeline.**  
Source: [Agentless](https://arxiv.org/html/2407.01489), §5.2.2 Table 3, source-unique.  
- **Method:** four independently sampled localization sets, then ten patches per set, **40 patches/task** total. The alternative merges multiple localization samples into one repair context.
- **Comparator/result:** greedy location with 40 samples: **88/300, 29.33%, $0.22** average repair cost. Merged multi-sample context: **85/300, 28.33%, $0.24**. Separate multi-samples, 4×10: **96/300, 32.00%, $0.29**.
- **Context condition:** the authors report that using all localized files creates context **>3,000** tokens, while subsequent element localization reduces context to **<800**.
- **Decision:** separate plausible localizations into bounded repair branches before merging all evidence into one prompt. This is an evaluated trade-off, not evidence that 40 candidates is optimal in another agent.

**E5 — iterative, structure-aware retrieval plus test feedback has an efficiency reference point, but not a controlled scaffold ablation.**  
Source: [AutoCodeRover](https://arxiv.org/html/2404.05427), abstract, §4.4, and evaluation setup, source-unique.  
- **Task/model:** SWE-bench Lite, **300** issues; GPT-4 `gpt-4-0125-preview`, temperature **0.2**, maximum output **1,024** tokens; experiments repeated **three times**. The agent can repeat context retrieval up to **10** times.
- **Run design:** AST/method-level iterative search. When tests are available, spectrum-based fault localization augments retrieval; patch validation retries generation up to a configured limit.
- **Outcome/cost:** **57/300, 19% pass@1**, about **4 minutes per resolved issue**, and **$0.43 average** reported cost.
- **Caveat:** this compares systems, not a same-scaffold toggle. The paper explicitly states spectrum-based fault-localization accuracy depends on test-suite quality.
- **Decision:** instrument retrieval iterations and test availability. Treat test-guided localization as conditional on a trustworthy failing/passing test signal.

**E6 — multiple trajectories can improve a stated fixed base-agent/scaffold result, but selection is a new component and cost is not reported.**  
Source: [OpenHands, “Inference-Time Scaling and Critic Model”](https://www.openhands.dev/blog/sota-on-swe-bench-verified-with-inference-time-scaling-and-critic-model), “Inference-Time Scaling” and “Building a Better Critic,” source-unique.  
- **Claim/method:** the post says the underlying agent model and scaffold were unchanged; it generated multiple trajectories and used a trained critic for selection.
- **Result:** SWE-bench Verified performance increased from **60.6%** with one rollout to **66.4%** with **five** attempts, +5.8 percentage points.
- **Caveat:** this is an organization report, not a peer-reviewed controlled study; it adds a Qwen 2.5 Coder 32B critic, so it is not a pure “same total model stack” result. No dollar, latency, or selection-error rate is reported.
- **Decision:** evaluate retries only with a fixed total budget and a pre-specified selector. Do not claim five attempts are economically better without measured marginal acceptance and spend.

## Counterevidence and evaluator limits

1. **Benchmark metric is test-suite passing, not general production acceptance.** [SWE-bench](https://arxiv.org/html/2310.06770), §2.2, defines “resolved” as a patch that applies and passes the task’s selected unit/system tests. This measures functional behavior under that harness, not maintainability, reviewability, security, or deployment safety.

2. **Evaluator coverage is limited.** The original SWE-bench has at least one fail-to-pass test per task, **40%** have at least two, and a median **51** additional tests run ([§2.3](https://arxiv.org/html/2310.06770)). That is meaningful execution-based evaluation, but it cannot show absent regressions outside tested behavior.

3. **Leakage and task-quality risks are real.** Agentless reports that Lite contains issue descriptions with exact ground-truth patches, misleading/insufficient descriptions, and constructs a filtered Lite-SS subset ([§6.1](https://arxiv.org/html/2407.01489)). It also reports that directly using the benchmark’s `PASS_TO_PASS` test list would produce **98%** Lite performance, and therefore modifies the official setup to run arbitrary regression and generated reproduction tests ([§4](https://arxiv.org/html/2407.01489)). This makes that result unsuitable for direct leaderboard comparison.

4. **Variance and local optima matter.** SWE-agent’s Figure 4 reports low average variance but substantial per-instance changes across runs; its successful runs tend to finish earlier and more cheaply than failed ones ([Appendix B.3](https://arxiv.org/html/2405.15793)). An apparent average retry gain can therefore be concentrated in a small task subset.

5. **Comparators are not a common leaderboard.** E1 uses GPT-4 Turbo, E3–E4 GPT-4o, E5 GPT-4, and E6 an unspecified OpenHands base agent plus a critic. Only within-source ablations support causal scaffold conclusions.

## Operational decision table

| Run-design choice | Default experiment | Adopt when | Do not adopt when |
|---|---|---|---|
| Context window/history | Compare bounded retrieved slices and summarized recent observations against full file/history | Paired accepted-task rate rises with no unacceptable token or latency increase | Gain vanishes by repository/task class or extra context raises failure rate |
| Edit/tool feedback | Add syntax, patch-application, test-command, and concise failure feedback | Failed-edit recovery and final acceptance rise | Feedback is noisy, omitted, or causes repeated identical repair loops |
| Validation and repair | Rank candidates by baseline regression tests, then issue-specific reproduction tests | Incremental accepted patches per dollar and per minute clears the release threshold | Reproduction test is invalid, no trustworthy baseline exists, or test-only score rises without holdout acceptance |
| Retries/branches | Fixed total token/time budget: one path versus \(k\) independent bounded branches plus identical selector | Marginal accepted-task yield exceeds the budget-normalized baseline | Selector cannot discriminate, tail latency is unacceptable, or benefits occur only on leaked/easy tasks |
| Decomposition | Separate localization hypotheses and repair each with bounded context | Location recall and accepted yield improve at equal total budget | Merged context is cheaper and equal on production-like holdout |

## Concrete paired evaluation artifact

Run every task in both arms from the same immutable repository snapshot, issue text, tool/container image, base model, reasoning setting, decoding configuration, total token ceiling, wall-clock ceiling, and maximum patch count.

| Field | Required value |
|---|---|
| `task_id`, repository, language, task class | Fixed paired identifier and stratification fields |
| `arm` | `baseline` or exactly one run-design change |
| `base_model`, reasoning effort, prompt version, tool version | Must be equal across arms |
| `context_policy` | Files/symbols, token count, truncation/summarization policy |
| `feedback_events` | Patch/apply/lint/test failures shown to the agent |
| `branches`, retry cap, selector | Exact run-design intervention |
| `total_input_tokens`, `total_output_tokens`, API cost, wall time | Efficiency denominators |
| `patches_generated`, tests run, test outcomes | Repair and validation trace |
| `blind_acceptance` | Independent reviewer or held-out executable acceptance result |
| `harness_resolved` | Official/standardized test result, reported separately from acceptance |
| `failure_class` | localization, edit, test, timeout, selector, environment, other |

**Primary endpoint:** paired difference in independently accepted tasks.  
**Secondary endpoints:** harness-resolved rate, median and p95 wall time, cost per accepted task, and failed-edit recovery.  
**Adoption rule:** promote only if the intervention improves the primary endpoint on a frozen, leakage-screened holdout, has no material regression in the other task strata, and its incremental cost per additional accepted task is within the production budget. Keep a test-only improvement as an experimental result, not a production-quality claim.

## Coverage and gaps

- **R1 — supported.** E1–E6 provide source-bound measurements for context, feedback, validation, decomposition, and retries. **Gap:** no single primary study holds every run-design factor and total budget constant.
- **R2 — supported/qualified.** Evaluator, task-quality, and comparator limits are documented. **Gap:** no inspected source quantifies contamination of each base model’s training corpus or production security behavior.
- **R3 — supported as inference.** The paired artifact and adoption rule preserve the fixed-model condition and separate test success from acceptance. **Gap:** thresholds require the production agent’s cost, latency, and acceptance baseline.
