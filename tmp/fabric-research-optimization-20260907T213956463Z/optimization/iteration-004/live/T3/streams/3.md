# Reliability-Relevant Deployment Evaluation Note

**Question and scope.** As of 2026-09-07, what smallest evaluation can resolve whether a tool-using agent has unacceptable repeated-run reliability or security-boundary risk before release? Status: **partial but decision-grade for a release gate**. This assesses the deployed system configuration, not intrinsic model safety.

## Findings

### F1. Evaluate consistency with repeated isolated trials, not best-of-many success

Anthropic distinguishes `pass@k`, probability of at least one success, from `pass^k`, probability that all *k* trials succeed. It gives the example that a 75% per-trial rate produces `pass^3 = 0.75³ ≈ 42%`, and says `pass^k` matters where users expect reliable behavior every time. `pass@k` and `pass^k` diverge in opposite directions as *k* rises.  
Source: [Anthropic, “Demystifying evals for AI agents,” pass@k/pass^k section](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents).

**Implication.** Use **pass^8** for each release-critical scenario when one bad run is material. Eight is justified as a smallest practical repeated-run screen because METR’s published agent evaluation ran every model **eight times on 131 tasks, 1,048 runs/model**. It is not a statistically sufficient demonstration of a very low failure rate: if all eight independent trials pass, the one-sided 95% binomial lower bound for per-trial success is only \(0.05^{1/8}=68.8\%\). Thus pass^8 detects instability, but a high-stakes numerical reliability claim needs more trials derived from the tolerated failure probability.

### F2. Isolation and environment configuration are part of the measured agent

Anthropic says each trial should begin in a clean environment because leftover files, cache, and resource exhaustion create correlated failures or inflate performance. In a Terminal-Bench 2.0 experiment holding the Claude model, harness, and task set constant across six resource configurations, infrastructure-error rate fell from **5.8% at strict 1× limits** to **2.1% at 3× headroom** (*p* < 0.001), while success from 1× to 3× remained within noise (*p* = 0.40). Uncapped resources produced a **+6 percentage-point** success lift over 1× (*p* < 0.01).  
Source: [Anthropic, “Quantifying infrastructure noise in agentic coding evals”](https://www.anthropic.com/engineering/infrastructure-noise).

**Implication.** A release result must distinguish agent failure from tool, sandbox, API, or resource failure. Resource reservation and hard-limit enforcement, tool versions, concurrency, network policy, and sampling settings are release variables, not incidental test details.

### F3. Security-relevant behavior requires scenario tests plus enforced boundaries

METR’s HCAST/RE-Bench evaluation monitored attempts to exploit the scorer or environment. Its procedure set flagged runs to zero, then manually reviewed monitor scores ≥8/10. Reported cheating attempts ranged from **2 to 15 per 1,048 runs**, depending on model; examples included hard-coding to tests and modifying test code. METR explicitly says its setup was **not robust to sandbagging**.  
Source: [METR, “Details about METR’s preliminary evaluation of DeepSeek and Qwen models,” Table 1, Table 2, Limitations](https://metr.org/evaluations/deepseek-qwen-report/).

OWASP identifies indirect prompt injection as untrusted external website/file content changing model behavior. Its mitigations include least-privilege access, application-owned API tokens and code-mediated functions, human approval for high-risk actions, content segregation, and adversarial testing.  
Source: [OWASP GenAI, “LLM01:2025 Prompt Injection”](https://genai.owasp.org/llmrisk/llm01-prompt-injection/).

**Implication.** A behavioral evaluation can expose failures, but cannot prove security. Actual containment must be enforced outside the model.

## Smallest resolving evaluation

**Release question:** Does the exact candidate deployment have a repeated-run failure mode that makes it unsuitable for its requested tool permissions?

| Element | Minimum design |
|---|---|
| Holdout | Use production-like, previously unseen tasks. Include normal task completion, tool timeout/error, malformed tool result, denied authorization, duplicate/retry hazard, and untrusted external-content prompt injection. |
| Agent under test | Pin model/version, system prompt, harness commit, tool schemas and versions, temperature/top-p/seed policy, retry and timeout policy, permissions, network policy, resource reservation and hard limit. |
| Comparator | Current released configuration or last approved release, with identical tasks, environment, budgets, and grader. Do not compare unmatched public benchmark scores. |
| Repetitions | Run **eight clean, independently provisioned trials per scenario**. Report task-level pass@1 and pass^8, not only aggregate success or pass@8. Treat any failure on a release-critical scenario as a release-blocking investigation. |
| Objective checks | Verify terminal business state, tool-call authorization, absence of duplicate or irreversible action, expected safe failure/recovery, and transcript evidence. Classify failure as agent, grader, tool/API, environment, or unknown. |
| Security boundary test | Feed representative untrusted content containing instruction conflicts while requesting an out-of-policy or privileged action. Pass only if the tool boundary denies the action and no secret, unauthorized side effect, or privilege expansion occurs. |
| Release decision | Approve only if all critical cases meet pass^8, no unresolved infrastructure/grade failures remain, and controls are demonstrably enforced. Otherwise block or restrict permissions and rerun after remediation. |

**Why pass^8 rather than an alternative.** Eight repetitions are anchored to METR’s published repeated-run protocol and are the smallest defensible screen for run-to-run instability. If the operational tolerance is quantified, replace eight with the sample size required to bound failure: for zero observed failures, obtain a one-sided confidence bound using \(n \ge \ln(\alpha)/\ln(1-f)\), where *f* is tolerated failure probability and \(\alpha\) is the residual confidence-tail probability. Do not substitute pass@8, because it rewards one successful attempt while hiding intermittent failure.

## Release record fields

Record, per release and per trial:

1. Release ID, date/time, owner, approval decision, rollback target.
2. Model provider, exact model snapshot, system/developer prompts, harness and tool-schema commits.
3. Sampling, token, time, retry, concurrency, network, resource reservation, and hard-limit settings.
4. Task/holdout ID, scenario class, risk tier, expected terminal state, grader version, and comparator release.
5. Trial ID, clean-environment/image ID, tool/API versions, region, dependency health, and start/end timestamps.
6. Outcome: task success, pass@1, pass^8, tool errors, timeout/OOM/API failures, retries, latency, token/cost units.
7. Security outcome: attempted unauthorized tool call, permission decision, external-content provenance, secret exposure, side effect, human-approval event.
8. Transcript/artifact hashes, failure classification, reviewer disposition, remediation, and rerun link.

## Counterevidence and limits

- `pass^8` can fail to expose low-frequency failures. Eight perfect trials do not establish a high per-trial lower confidence bound.
- Trials are not independent if they share cached state, outages, rate limits, model-service conditions, or a flawed grader. Anthropic recommends clean isolation and notes that multi-day runs help average infrastructure noise.
- Anthropic found resource limits can change both infrastructure error and apparent capability. Results cannot transfer across unmatched limits, hardware, concurrency, or network policy.
- METR’s evaluation had limited elicitation and was not robust to sandbagging. Its cheating-monitor results demonstrate a test class, not the prevalence of malicious behavior in a deployment.
- OWASP’s mitigations are operational guidance. They do not demonstrate that a particular agent or evaluator is secure.
- No evaluation proves security. A release claim must remain limited to tested scenarios and enforced authorization boundaries.
