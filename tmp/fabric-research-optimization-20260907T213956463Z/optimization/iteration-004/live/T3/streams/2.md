# Evaluator Validity and Version Evidence

**Question.** What evidence supports trustworthy evaluation of tool-using-agent reliability and security-relevant behavior?  
**Scope/date.** Original sources inspected. Status: **partial** as of 2026-09-07. “Cross-benchmark” here is qualified: the inspected evaluator audit spans models and domains, not multiple independently maintained benchmarks.

## Findings

### Material evidence units

| Evidence | Exact result and located support | Method, comparator, caveat | Decision dimension |
|---|---|---|---|
| **E1: automated evaluator validity** | [AgentProp-Bench, §5/Table 2](https://arxiv.org/html/2604.16706): substring judging had Cohen’s κ **0.049** and **0.015** against the two annotators, and **0.036** against 92-trace consensus. Three-LLM majority ensemble κ **0.432**. GPT-4o-mini alone κ **0.567**. Human-human κ **0.835**, **92%** raw agreement. | 100 stratified P2 tool-agent traces, 10–12 per proprietary model across three domains. Two blinded annotators label correctness. Ensemble is GPT-4o, Gemini-2.5-Flash, and GPT-4o-mini, majority vote. The audit includes 13 agents, four domains, 2,000 tasks and 14,750 traces. Calibration sample is only 100 traces, so it does not validate a judge for a different workflow or security label. **Source-unique: yes.** | Do not treat a string/substring reward as a valid correctness measurement. Calibrate the deployed evaluator against blinded expert labels. |
| **E2: security-relevant failure and intervention** | [AgentProp-Bench abstract and §§6–9](https://arxiv.org/html/2604.16706): injected parameter error reached a wrong final answer with human-calibrated probability **≈0.62**. Rejecting corrupted inputs and recovering after execution were nearly independent, Spearman **ρ=0.041**. Fabricated tool execution occurred in up to **37.5% of traces**. A runtime interceptor reduced hallucination by up to **24 percentage points**. | Deterministic Python tools with schema-validated JSON inputs, controlled parameter injection, 95% bootstrap CIs with 1,000 iterations, seed 42. Concurrent control differs only by interceptor. This is a simulator experiment, not proof that interception blocks adversarial prompt injection, privilege abuse, or production data exfiltration. **Source-unique: yes.** | Measure provenance separately from end-state success. Test error rejection, recovery, and unsupported-result claims independently. |
| **E3: repeat-run reliability** | [Original τ-bench paper, §3 and §5.1/Figure 4](https://arxiv.org/html/2406.12045): `pass^k` is the probability that **all k i.i.d. trials** for a task succeed, averaged across tasks. With the same task semantics but stochastic user and agent messages, the best GPT-4o function-calling retail agent had **>60% pass^1** but **<25% pass^8**. Experiments ran at least **3 trials/task**, agent temperature **0.0**, user temperature **1.0**. | τ-bench uses LLM-simulated users, domain API tools, policy rules, and database end-state versus annotated goal-state reward. It measures reliability in airline/retail customer-service simulations, not security. **Source-unique: yes.** | A one-run task-success rate is insufficient for deployment reliability claims. Report a repeat-success curve and preserve per-trial trajectories. |
| **E4: τ-bench release staleness** | [τ-bench repository README](https://github.com/sierra-research/tau-bench): “**WARNING: The tasks in this repo are not updated**”; it directs users to τ³-bench for fixed airline/retail tasks and new domains. | This is an explicit maintainer repository warning. Corrected-task releases are not score-compatible with the original task set without a paired rerun. **Source-unique: yes.** | Pin benchmark repository, commit/release, domain, evaluator configuration, user simulator, and task set. Do not compare original τ-bench scores with τ³-bench scores as one leaderboard. |
| **E5: maintained submission repeat requirement** | [τ²/τ³ leaderboard submission documentation](https://github.com/sierra-research/tau2-bench/blob/main/docs/leaderboard-submission.md) requires **4 trials per domain**, records `pass_1` through `pass_4`, and requires identical agent/user LLMs and arguments across runs. | Maintainer documentation specifies a reporting protocol, not statistical proof that four trials establish general reliability. | Preserve trial count and simulator/model configuration with any reported score. |

### Concrete counterevidence and limits

- **Evaluator error can change the conclusion.** In E1, the ensemble marked **25%** of traces correct while humans marked **38%**, an approximately **13 percentage-point** undercount in the calibration sample. A higher κ than a heuristic does not make the judge ground truth.
- **Repeat instability is material.** The original τ-bench result shows `pass^1` can conceal much lower all-repeats success. A later non-maintainer analysis of repository trajectories reports `pass^1` per-trial ranges up to **12 percentage points** and **43–64%** task outcome flips, but this is an issue-comment analysis rather than a paper or maintainer-validated result. See [issue #57](https://github.com/sierra-research/tau-bench/issues/57).
- **Security transfer is unsupported.** Database end-state success, policy compliance, and tool-output provenance do not establish resistance to prompt injection, authorization bypass, insecure tool scopes, data leakage, or adversarial tool output.
- **Release drift invalidates naïve comparison.** The original τ-bench repository is explicitly obsolete. Historical results must retain their release identity rather than be treated as results for the corrected benchmark.

## Deployment decision table

| Decision | Evidence threshold | Control |
|---|---|---|
| Accept automated correctness evaluation | Blinded human calibration on representative deployment traces, with κ, raw agreement, confusion matrix, prevalence, and disagreement review | Block release if the evaluator has not been calibrated for the exact rubric and agent/tool surface. |
| Claim reliable task completion | Per-task repeated runs with `pass^1…pass^k`, trial count, intervals, trajectories, model versions, decoding settings, and user-simulator configuration | Use all-repeats success, not mean one-run success, for high-consequence actions. |
| Permit consequential tool actions | Separate evidence for authorization, provenance, refusal, recovery, and unsafe-action handling | Enforce least privilege and independently verify tool execution/result provenance before irreversible actions. |
| Compare τ-bench results | Same release/commit, domains, evaluator, agent/user models, prompts, temperatures, trial count, and task inclusion | Mark original τ-bench as historical. Rerun both systems on the same current τ³ release before ranking. |

## Smallest resolving evaluation

Run a fixed, held-out sample of representative production tasks and security-relevant failure probes under the pinned current benchmark/deployment environment:

1. Collect at least four independent trajectories per task with the actual agent, tools, user/simulator model, and decoding configuration.
2. Have two blinded domain reviewers label correctness, unauthorized action, unsupported tool-result claim, refusal, and recovery.
3. Calibrate each automated evaluator against reviewer consensus. Report κ, raw agreement, confusion matrix, and per-class error.
4. Report `pass^1…pass^4`, per-trial results, bootstrap intervals, tool-action failure taxonomy, and complete traces.
5. Compare intervention versus concurrent no-intervention control on the same tasks. Do not declare security proven from this result.
