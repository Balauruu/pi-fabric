# Evaluation, Reliability, and Security Boundaries for Tool-Using Agents

**Decision.** Use state-based task evaluation, repeated-run reliability, trace-level failure analysis, and paired attack/utility measurement to decide what an agent may do. These methods produce bounded evidence about a named agent, tool surface, environment, task distribution, attack set, and budget. They do not establish that a deployment is secure. Authority must instead be enforced at the tool boundary.

## R1. What the primary evaluations and standards measure

|---|---|---|---|---|

### Evaluation interpretation

Final state and policy assertions are stronger than action-string matching or self-reported completion. `pass¹` reports first-run success; `pass^k` exposes consistency risk. For an attack evaluation, targeted ASR alone is incomplete because a defense can lower ASR by suppressing useful work. Report benign utility and utility under attack beside ASR.

## R2. Counterevidence, evaluator limits, and transfer constraints

### Counterevidence

1. **Single-run success hides tail risk.** τ-bench’s retail GPT-4o result falls from more than 60% pass¹ to below 25% pass⁸. A one-run average is not a reliability claim. [S1]
2. **Nominal model capability does not imply long-horizon execution.** WebArena’s best GPT-4 agent scored 14.41% against a 78.24% human baseline in a bounded replica. [S2]
3. **A lower attack rate can buy less useful work.** In the AgentDojo paper table, the GPT-4o detector reduced ASR from 57.69% to 7.95% while utility under attack fell from 50.01% to 21.14%. [S5]
4. **Automated evaluation can alter the conclusion.** AgentProp-Bench’s substring grader was near chance against human consensus and its ensemble undercounted correct traces by about 13 points. [S9]
5. **Low tool use is not necessarily safe behavior.** AgentProp-Bench reports Gemini-2.0-Flash fabricated tool-derived results in **37.5%** of relevant no-tool-call traces. A low injection-admission metric can reward non-execution or unsupported claims. [S9]
6. **Attack budget changes observed harm.** AgentHarm’s best-of-five setting raised harmful completion above the one-attempt result. One fixed prompt-injection set is an observed lower bound for that set, not an upper bound on attacker success. [S7]

### Constraints on inference

| Constraint | What it prevents | Required reading of a result |
|---|---|---|
| Simulated users, tools, or web replicas | A benchmark rate cannot represent production identities, data, authorization, outages, races, or blast radius. | Treat it as evidence for the stated abstraction only. |
| Fixed model, prompt, schema, policy, and budget | Hosted models, tool APIs, retrievers, policies, and scaffolds drift. Step limits and retries change both success and harm. | Bind every rate to model revision, environment image, prompt/policy, schemas, temperature, seed where applicable, steps, retries, time, and cost. |
| LLM or heuristic judge disagreement | A score can contain false positives, false negatives, reward hacking, and shared-model bias. | Use executable final-state and policy assertions for critical outcomes and blind human review of every prohibited effect plus a stratified disagreement sample. |
| Outcome-only scoring | A correct final state can conceal excess access, secret exposure, unsafe near-misses, and duplicate retries. | Score trace-level prohibited calls, provenance, authorization decisions, and information flows separately. |
| Default or non-adaptive attacks | An attacker can vary placement, encoding, tool outputs, timing, and routes after seeing a defense. | Use deployment-specific adaptive attacks and label residual ASR as specific to the tested attack set. |
| Public static tasks and API drift | Prior exposure, tuning, and changing APIs can inflate or destabilize scores. | Keep private holdouts, rotate perturbations, preserve fixed regression cases, and publish the evaluation manifest. LiveBench’s mitigations reduce rather than eliminate contamination risk. [S12] |
| Aggregation across sources | Paper tables and live dashboards may use different model snapshots, attacks, defenses, and denominators. | Do not cross-rank or average values without a configuration crosswalk. |

## R3. Deployment decisions and operational controls

| Decision | Evidence required | Enforced operational boundary | Concrete block, rollback, or incident signal |
|---|---|---|---|
| Permit read-only, reversible work | Private representative tasks with executable final-state checks, pass¹ and repeated-run success, trace-level failure taxonomy, and evaluator calibration. | Read-only scoped credentials, tenant checks, provenance logging, and an explicit incomplete state when no verified tool result exists. | Goal-state mismatch, unsupported completion claim, invalid call, action-budget exhaustion, or repeated unchanged-state action. |
| Permit reversible state changes | The read-only evidence plus fault injection for timeout, malformed response, stale read, partial completion, and 4xx/5xx behavior. | Typed arguments, server-side validation, per-action allowlist, idempotency key, state recheck, transaction or compensating action, and bounded retries. | Retry after ambiguous write, duplicate effect, rollback failure, unexpected write set, or repeated invalid actions. |
| Permit money movement, external commitments, secrets, privilege change, deletion, or code execution | Deployment-matched paired clean/attacked cases measuring policy conformance, targeted ASR, benign utility, utility under attack, and human review of security traces. | Separate authorization service, short-lived least-privilege credentials, resource and recipient allowlists, deterministic policy gate, and informed human approval. Isolated non-root execution with outbound network denied by default is required for code tools. | Unauthorized irreversible action, cross-tenant disclosure, secret routed externally, scope expansion, code-execution escape, missing authorization event, or missing audit record. |
| Allow untrusted content to reach an agent | Attack cases for every web, email, document, retrieval, memory, and tool-output ingress paired with every consequential sink. | Treat content as data, not authority. Preserve provenance through retrieval and tool arguments. Separate reading from privileged execution and constrain downstream capabilities. | Instruction-like untrusted content appears in the causal trace of a privileged call, goal drift, new memory changes authority, or low-trust retrieval reaches a high-impact action. |
| Enable recovery and retries | Fault-injection evidence that a retry cannot duplicate an effect and that the agent safely aborts after uncertain state. | Per-tool retry policy, duplicate-call detection, idempotency, state assertion before retry, bounded cost/time/turns, and reconciliation after ambiguous effects. | Same action and observation loop, changing arguments without new evidence, three consecutive invalid calls, timeout without reconciled state, or action-budget exhaustion. |
| Change model, prompt, tool schema, policy, retrieval, permissions, or orchestration | Differential rerun of locked private regression and adversarial suites with the old baseline retained. | Version pinning, staged rollout, kill switch, change-specific approval, and rollback threshold. | Unknown model revision, missing image/prompt/schema manifest, material regression in repeatability or policy conformance, or any new severe path. |

These controls are system safeguards and risk-owner decisions. A benchmark score does not substitute for server-side authorization, validation, or a policy gate.

### Instrumented failure signals

- **Protocol:** invalid tool-call JSON, schema rejection, unknown tool, wrong argument type, nonexistent identifier, repeated identical call, invalid-action threshold, timeout, and budget exhaustion.
- **Execution and recovery:** final-state assertion failure, unexpected write set, retry without an idempotency key, ambiguous write without reconciliation, rollback failure, stale read, and tool-response schema/version mismatch.
- **Truthfulness:** claimed completion without a successful corresponding tool event, numeric or factual output unsupported by logged observation, and answer/database-state mismatch.
- **Security:** undeclared tool, resource, recipient, privilege, or network scope; injection-tainted input reaching a privileged sink; targeted malicious objective achieved; secret-bearing output sent externally; tenant-boundary crossing; bypassed policy gate; or absent immutable trace.
- **Evaluation integrity:** missing version manifest, unresolved holdout overlap, judge-human disagreement beyond calibrated tolerance, or a score reported without denominator, abstentions, timeouts, budget, and failure-class distribution.

## Smallest resolving evaluation

Before granting a consequential action class, run **50 newly authored private, target-workflow scenarios** in a cloned production-equivalent environment. Use 30 normal tasks, 10 ambiguity/fault/recovery tasks, and 10 cases where actual untrusted content attempts a prohibited call. Run the exact release candidate, model revision, prompt, orchestration, schemas, permissions, policy layer, credentials, action/retry limits, and realistic tool responses at least three times per stochastic configuration.

Score executable final state, policy conformance, tool-call adherence, invalid-call rate, timeout rate, duplicate-action rate, safe aborts, pass¹, pass³, benign utility, utility under attack, and targeted ASR. Human reviewers blindly inspect every prohibited effect, every abstention, and a stratified sample of evaluator disagreements. Compare controls enabled versus disabled on the same scenarios.

**Release rule:** any unauthorized consequential action, cross-tenant disclosure, code-execution escape, unreconciled ambiguous write, or missing authorization/audit event blocks that action class. Otherwise, authorize only classes whose repeated-run failure and recovery behavior meet the explicit risk-owner threshold. This resolves target-domain transfer and the actual authority boundary, which public benchmarks cannot resolve.

## Coverage and substantive stop reason

| Question | Coverage | Substantive stop reason |
|---|---|---|
| **R1: reliability, task success, failure handling, and security-relevant behavior** | Direct source-bound evidence from τ-bench, WebArena, ToolBench/ToolEval, AgentBench, AgentDojo, AgentHarm, ToolEmu, and AgentProp-Bench. NIST and OWASP define governance and threat-model boundaries. | No inspected source evaluates this deployment’s tools, data, identities, permissions, or attack surface. No universal benchmark score is a deployment pass criterion. |
| **R2: counterevidence and transfer limits** | Direct evidence covers repeatability collapse, long-horizon failure, attack/utility trade-offs, evaluator disagreement, low-use fabrication, attack-budget sensitivity, simulator limits, contamination exposure, and configuration drift. | Adaptive attacks and production effects are system-specific. Their rate cannot be inferred from a generic benchmark. |
| **R3: operational controls** | Decisions connect measured failure modes to enforcement points, logging, recovery boundaries, release gates, and a deployment-matched resolving evaluation. | Numerical release thresholds are risk-owner choices based on harm, reversibility, legal obligations, and affected users, not values supplied by these benchmarks or standards. |
