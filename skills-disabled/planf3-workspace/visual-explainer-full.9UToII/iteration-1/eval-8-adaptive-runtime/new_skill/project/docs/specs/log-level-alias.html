01 · Goal

Goal and scope

In scope

  • Accept LOG_LEVEL_ALIAS as a secondary environment name.
  • Keep LOG_LEVEL authoritative when both names are truthy.
  • Keep info as the fallback when neither supplies a value.
  • Document and test the precedence contract.

Explicitly out of scope

  • Log-level validation or normalization.
  • Changing the exported function signature.
  • Adding dependencies or a generalized configuration framework.
  • Changing logger output or runtime wiring outside this fixture.

02 · Evidence

Current state

Resolver

src/config.js returns env.LOG_LEVEL || 'info'. Callers may inject an environment-like object; otherwise it reads process.env.

Coverage

test/config.test.js proves a truthy LOG_LEVEL and the empty-object fallback. It does not cover aliases or competing values.

Public guidance

README.md promises that existing LOG_LEVEL behavior remains compatible and identifies Node's built-in test runner.

Constraint

Use the existing truthiness semantics rather than introducing validation or distinguishing missing, empty, and other falsy values.

03 · Design

Primary, alias, fallback

The relationship is linear and is clearer as a compact CSS pipeline than a Mermaid diagram.

1 · Primaryenv.LOG_LEVELFirst truthy value wins.
2 · Aliasenv.LOG_LEVEL_ALIASConsulted only after a falsy primary.
3 · Default'info'Used when both names are falsy.
src/config.js · intended resolver expression
return env.LOG_LEVEL || env.LOG_LEVEL_ALIAS || 'info';
Compatibility boundary. Existing truthy LOG_LEVEL values still win, existing calls and exports stay unchanged, and the existing info result remains when neither variable is provided. A configured alias intentionally fills the previously unsupported secondary-name path.
