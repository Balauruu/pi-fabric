Goal and scope

Change shape, not product behavior

Outcome

Evolve the existing SQLite table through three ordered, restartable stages while preserving readable rows and bounded write locks.

  • Columns begin nullable.
  • Backfill commits every 500 rows.
  • Constraints wait for a zero-null gate.

Boundaries

  • No online dual-write framework.
  • No generalized migration platform.
  • No unrelated schema or application changes.
  • Use the existing Node test runner.

Evidence-led current state

Forward path

Three gates, each independently safe

01Add nullable

Transactional DDL. Existing rows stay valid.

→
02Backfill

Primary-key cursor, 500 rows, commit, checkpoint, repeat.

→
03Enforce

Verify zero nulls, rebuild table, validate, swap.

Each stage writes its completion only after its transaction commits; rerunning skips completed work and resumes the cursor.

The restartable seam

while (true) {
  const rows = selectNextBatch(db, checkpoint, batchSize);
  if (rows.length === 0) break;
  db.transaction(() => {
    backfillRows(db, rows);
    saveCheckpoint(db, rows.at(-1).id);
  })();
}
assertNoNullTargets(db);

The cursor and row updates commit atomically. A crash before commit repeats the batch; a crash after commit resumes after it.

Risk falls when gates are observable

Lock duration

Medium → bounded transactions and WAL-friendly pauses.

Partial progress

Medium → atomic cursor + data commit.

Constraint loss

High → preflight, transactional rebuild, row-count validation.

[] Phase 1: Add nullable columns

[] Implement introspected, transactional DDL

  • [] Read table metadata before ALTER operations.
  • [] Add each requested column only when absent.
  • [] Record Stage 1 completion after DDL commit.

[] Testing Strategy

  • [] Run node --test --test-name-pattern="nullable".
  • [] Rerun Stage 1 and assert schema is unchanged.
  • [] Force DDL failure and assert no completion marker.

[] Phase 2: Backfill in batches

[] Implement cursor-bounded data updates

  • [] Select stable primary keys greater than the checkpoint.
  • [] Update no more than 500 rows per transaction.
  • [] Persist cursor with the same commit as row changes.

[] Testing Strategy

  • [] Run node --test --test-name-pattern="backfill|resume".
  • [] Inject failure inside batch N and verify only N rolls back.
  • [] Restart and verify every row is updated exactly once.

[] Phase 3: Enforce constraints

[] Gate and rebuild the SQLite table

  • [] Abort unless target null count is zero.
  • [] Create constrained copy with indexes and defaults preserved.
  • [] Copy, compare counts, swap, then record completion.

[] Testing Strategy

  • [] Run node --test --test-name-pattern="constraint|rollback".
  • [] Seed one null and assert original table remains authoritative.
  • [] Complete the rebuild and inspect constraints with PRAGMA table_info.

Acceptance is observable

Global validation

  • [] npm test passes all existing and new migration tests.
  • [] A fresh temporary database reaches the constrained schema.
  • [] A killed backfill resumes from the last committed checkpoint.
  • [] No transaction updates more than 500 rows.
  • [] Residual nulls block constraint enforcement without schema loss.
  • [] A second full run is a no-op and preserves row counts.

Manual operational check

  1. Copy a representative local database.
  2. Run through Stage 2, terminate, restart.
  3. Inspect checkpoint, null count, row count, indexes, and constraints.
  4. Retain the untouched copy as rollback evidence.

Implementation notes

SQLite-specific

  • Constraint enforcement uses table rebuild, not unsupported ALTER COLUMN.
  • Recreate existing indexes and triggers from inspected schema.
  • Use a stable, indexed primary-key cursor rather than OFFSET.

Preconditions

  • The caller supplies the target table, column definitions, and deterministic backfill expressions.
  • Backfill values must not depend on mutable row order.
  • Run on a disposable copy before touching the working database.
