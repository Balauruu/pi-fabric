Goal and Scope

Implement the shortest safe path for a schema change whose target table and column definitions are supplied by the concrete migration specification. Stage 1 must be immediately backward-compatible, stage 2 must be restartable after any committed batch, and stage 3 must enforce the declared NOT NULL and related constraints without losing rows.

Out of scope

  • Changing the public three-stage ordering or the observed batch size of 500.
  • Supporting another database engine, concurrent migration runners, or an application deployment protocol.
  • Inventing target column names or backfill values not present in this fixture; those belong in the concrete migration specification.

Current State

The repository currently exposes only migration intent. src/migration.js exports the ordered labels add-nullable-columns, backfill-batches, and enforce-constraints, plus batchSize = 500. The existing Node test asserts those two facts. No SQL executor, checkpoint table, target schema, failure handling, or end-to-end SQLite test exists.

Planning boundary: preserve the observed exports while adding execution behind them. A concrete caller must provide table, column definitions, a stable integer cursor, and deterministic backfill expressions.

Proposed Design

Extend the existing module with a synchronous runMigration(db, spec) entry point. Use the repository runtime's built-in SQLite adapter in tests, avoiding a new package. Record only completed stages and the last committed cursor in a migration-local checkpoint row. Every schema stage and every backfill batch gets its own explicit transaction.

Stage mechanics

  1. Add nullable columns: inspect PRAGMA table_info, add only absent columns without NOT NULL, and mark stage 1 complete in the same transaction.
  2. Backfill batches: select cursor values greater than the checkpoint in ascending order with LIMIT 500; update exactly that key range and persist the final cursor atomically. Empty selection marks stage 2 complete.
  3. Enforce constraints: assert no target value is null, create the strict replacement table, copy explicit columns, compare counts, swap names, recreate supplied indexes/triggers, run PRAGMA foreign_key_check, and mark stage 3 complete in one transaction.

SQL safety boundaries

Values use bound parameters. SQLite identifiers cannot be parameters, so validate specification identifiers against the existing schema and a strict identifier grammar before quoting. Do not accept untrusted runtime input as migration SQL.

Implementation Phases

Execute in order. Each phase leaves a durable, independently testable boundary.

[] Phase 1: Nullable schema and checkpoint

Establish restart metadata and backward-compatible columns only.

[] 1.1 Implement stage 1

  • [] Validate the concrete spec and create the checkpoint table idempotently.
  • [] Add missing columns as nullable and checkpoint completion in one transaction.

[] 1.2 Testing Strategy

  • [] node --test --test-name-pattern="nullable|stage order" proves add and rerun behavior.

[] Phase 2: Bounded resumable backfill

Make each batch its own atomic data-and-cursor unit.

[] 2.1 Implement cursor loop

  • [] Select stable keys in ascending batches capped by exported batchSize.
  • [] Commit updates and last cursor together; mark complete only after an empty next selection.

[] 2.2 Testing Strategy

  • [] node --test --test-name-pattern="batch|resume" injects a post-batch failure and proves the restart neither skips nor repeats rows.

[] Phase 3: Constraint enforcement

Rebuild only after data preconditions hold.

[] 3.1 Implement strict rebuild

  • [] Preflight null count, perform explicit create/copy/count/swap/recreate operations, and checkpoint atomically.
  • [] Run foreign-key validation before commit and preserve the original table on failure.

[] 3.2 Testing Strategy

  • [] node --test --test-name-pattern="constraint|rollback" proves null rejection, row preservation, dependent object recreation, and stage-local rollback.
