# Build Plan

Unit status markers are `[]`, `[wip]`, `[x]`, and `[f]`. Completion means executable units and global validations are resolved, observed evidence/blockers are recorded beside their owner, lifecycle history is appended, and `--complete` validates.

1. Resolve the target plan. If inference leaves more than one plausible file, confirm before mutation.
2. Run a thin semantic preflight and `node "$VALIDATOR" "$PLAN_FILE"` from the repository root. Reject legacy/unmarked plans, `approach` plans, and answer-seeking chat outputs. Approach approval must first route through Create to a code or knowledge plan.
3. Require readiness `approved` before execution. Read semantic indexes and metadata only at plan level; do not load the full decorative HTML as execution context.
4. Determine unit dependency order only from `data-planf3-dependencies`, respecting phase gates. Re-derive phase/unit waves and work modes and reject drift from the visible Execution order fields or ordering projection. Parallel means units are permitted, not required, to run concurrently. For each ready unit run:
   `node "$SKILL_DIRECTORY/scripts/context-slice.mjs" "$PLAN_FILE" UNT-ID`
   Use that bounded slice as the execution packet. It includes goal/profile/readiness, owning phase, cited requirements/decisions/evidence, dependency units, target fields/checks/File Impact or resources, source/illustrative snippets, and global validations/DoD, while excluding presentation runtime/CSS and unrelated units. Revalidate source snippets before use. Treat illustrative snippets as subordinate design intent, not current source or a replacement for unit goals, contracts, and File Impact.
5. Set document, phase, and current unit execution markers to in-progress/`[wip]` before work. Code units execute File Impact in dependency order. Keep `data-planf3-path-state="existing|new"` as baseline state; use `data-planf3-path-result="deleted"` only for an intended deletion of a baseline-existing path. That path must exist through preflight and remain absent once document execution becomes `complete`; every unmarked baseline-existing path must still exist. Knowledge units execute actionable input/output-resource packets without assuming files or code tests.
6. Run each unit's scenario checks and observable verification. Record observed command/manual evidence or a concrete blocker immediately beside the relevant `UNT-*`/`CHK-*`, then set checks and owners to `[x]` or `[f]`. Preserve historical decision intent; execution observations may cite or trigger a decision revisit but never silently rewrite it.
7. Resolve a phase only after all owned units resolve; continue past failure only when dependencies permit and record the block. Execute every global validation and record evidence beside its `VAL-*`. After all units resolve, update Key metrics observations and evidence from measured results and set metrics state to `observed`; pending or not-measured values cannot complete. Set document execution to `complete` only when all executable statuses pass, otherwise `failed` when any fail.
8. Append timestamp, available agent/session, actual commit SHAs only, and a lifecycle amendment summarizing execution evidence/blockers and metric updates.
9. Run `node "$VALIDATOR" --complete "$PLAN_FILE"`. Report per-unit context command, implementation/evidence, final markers, and blockers.
