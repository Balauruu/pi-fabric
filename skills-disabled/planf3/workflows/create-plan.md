# Create Plan

Completion is either an answer delivered in chat with no lifecycle artifact, or one validated current HTML plan at `PLAN_FILE`.

1. **Classify intent before composition.** Route to exactly one outcome:
   - **Code implementation**: a persistent `code` + `implementation` plan.
   - **Knowledge-work plan**: a persistent `knowledge` + `execution` plan whose units produce concrete outputs.
   - **Answer-seeking**: use a disposable internal plan-of-attack, answer in chat, and create no HTML lifecycle artifact.
   - **Approach altitude**: for explicit requests to plan the approach, decide methodology, or determine how to tackle work before committing, and for materially uncertain deliverables. Persist an `approach` + `decision` plan and stop at its decision checkpoint.
2. **Inspect before asking.** Read local repository/input evidence first. Software always gets focused source, architecture, instruction, interface, and test inspection. Synthesize scope, assumptions, and settled decisions before Standard/Deep or material-decision composition. Ask only unresolved user-owned decisions and never re-ask a decision already settled in the prompt, session, or durable records.
3. **Research selectively.** External research is warranted only when explicitly requested, high-risk, recently changing, locally thin, or when an unsettled external option materially shapes the plan. Consolidate only load-bearing findings into `EVD-*`; every evidence record must link to an owned `DEC-*`, `REQ-*`, or `UNT-*`. Carry session choices, rejected alternatives, rationale, and provenance into `DEC-*` records, not a transcript.
4. **For approach plans**, perform cheap input-specific reconnaissance, compare at least two concrete evidence-grounded options, and state criteria, risks, evidence, recommendation, and the exact user decision checkpoint. The routes are exact: approve invokes Create again for the selected code or knowledge profile; revise remains in the approach workflow and amends the comparison; reject stops. Do not add phases, units, or File Impact.
5. Read both PlanF3 contracts, `references/information-design.md`, `references/report-patterns.md` when composing a report, retained Visual Explainer references needed by the presentation contract, `assets/plan-template.html`, `assets/presentation/v1/themes.css`, and `assets/presentation/v1/runtime.js`.
6. **Compose the semantic plan.** Executable phase and unit packets follow the complete content contract. Treat `data-planf3-dependencies` as ordering authority. Derive deterministic topological execution waves: phase dependencies include owner phases contributed by dependency units; unit waves use same-phase unit dependencies. Mark a same-scope wave of one sequential and two or more parallel, meaning permitted rather than guaranteed concurrent work. Emit matching wave/work-mode attributes and visible Execution order fields. Put exactly one SVG branching ordering figure first in `#phases`: normalize Mermaid aliases from semantic IDs without collisions, declare every phase/unit once with its exact ID/wave/mode label, and after exact `flowchart TD` emit only one simple dependency-derived `-->` edge per nonempty line (phase to first-wave units, same-phase unit dependency to unit, cross-phase dependency to dependent phase, each terminal unit to both Key metrics and Validation), and add no unrelated nodes or edges. Include the labelled focusable viewport and exact grouped HTML fallback with phase/unit ID set, matching wave/mode, labelled unit-wave bands, and links. Code units own contextual Before/After File Impact deltas, named scenario tests, observable verification, and checks. Derive the actionable File impact index solely from unique unit File Impact paths, including state, seam, intent, every owning-unit backlink, and validation relation. Knowledge units instead own explicit input/output resource locators. One phase and one unit are sufficient for small work; never add filler. When code materially clarifies a unit, use the shared code snippet figure. Use the source variant only for fragile or contract-sensitive current seams: include every guard plus whole-file SHA-256 and wrap each escaped source line in the exact numbered line span required by its declared range. Use the visibly labelled illustrative variant for proposed code, pseudocode, or commands that do not yet exist, without source guards or line numbers and without treating it as authority.
7. **Set readiness independently of execution:** `draft` when the content is intentionally incomplete but no explicit blocker owns the next step; `blocked` when an unresolved blocking question prevents a complete or executable contract; `review-ready` when the semantic contract is complete and awaits review/decision; `approved` only after explicit approval. Executable plans begin execution `not-started` with `[]`; approach execution is `not-applicable`.
8. Compose once from the template. Use the full-width phase owner/detail ledger and visibly owned unit lanes. Add the single global `#key-metrics.key-metrics-overview` immediately after the hero and before `#purpose`, with 3-6 unique scorecards and visible label, baseline, target, observed, and evidence parts. The overview component is reusable, but only this top instance is semantic authority. Executable plans start planned and may use `Not measured - execution not started`; approach plans use planned decision metrics. For a report, inventory source items and select documented projections; remove the authoring exemplar, keep projections source-visible, link review/decision material to semantic authority, and derive File Map actionable paths exactly from File Impact. Emit ordinals, symbols/type labels, permalinks, observability inventory, metadata, stable IDs, and fallbacks. Replace every placeholder.
9. Run `node "$VALIDATOR" "$PLAN_FILE"`. For Standard/Deep, high-risk, or decision-heavy plans, immediately route through `workflows/deepen-plan.md`, then validate again. Report the route, readiness basis, path, and exact deterministic checks.
