# PlanF3 current content contract

PlanF3 plans are source-visible HTML editorial ledgers. Hidden JSON never duplicates semantic authority.

## Document and records

`<html>` carries `data-planf3-contract="current"`, profile `code|knowledge|approach`, kind `implementation|execution|decision`, execution `not-started|in-progress|complete|failed|not-applicable`, readiness `draft|review-ready|blocked|approved`, and the current presentation/runtime markers. Every `REQ`, `DEC`, `EVD`, `PHS`, `UNT`, `CHK`, and `VAL` has a stable matching DOM ID, two-digit type ordinal, fixed symbol/type label, and permalink. Space-separated semantic links resolve. Lifecycle status remains exactly `[]`, `[wip]`, `[x]`, or `[f]` and is independent of readiness.

Decision fields are Choice, Status, Rejected alternatives, Rationale, Provenance, Evidence links, Affected links, and Revisit. Evidence fields are Source, Finding, Confidence, and Changes. Phase fields are Outcome, Dependencies, Execution order, Entry evidence, Owned units, Exit evidence, and Handoff. Unit fields are Goal, Trace links, Dependencies, Execution order, Approach, Tests, and Verification. Fields are visible owned definition-ledger rows. Resolved checks and validations own observed evidence; failed records also own a blocker.

## Execution ordering

`data-planf3-dependencies` is the sole ordering authority. Every executable phase and unit carries `data-planf3-execution-wave="01..."` and `data-planf3-work-mode="sequential|parallel"`, with the same values stated in its owned visible Execution order field.

Derive phase waves topologically from phase dependencies and from cross-phase unit dependencies declared by units the phase owns. Any dependency unit contributes its owner phase, without requiring authors to duplicate that dependency on the phase. Derive unit waves from dependencies on units in the same owner phase. Roots are wave 01 and each record is one plus the maximum contributing dependency wave. Within the same scope and wave, one record is sequential and two or more are parallel. Parallel means permitted, not guaranteed concurrent execution.

Every executable plan has exactly one `figure.execution-order-map.diagram-shell[data-planf3-execution-order]` as the first content in `#phases`. It owns one labelled, focusable `.diagram-viewport.execution-order-viewport` containing the single `data-planf3-execution-svg` canvas, plus one nonempty `script.diagram-source[type="text/plain"]` using `flowchart TD`. Use collision-free normalized Mermaid aliases by replacing every non-alphanumeric ID character with `_`; aliases for distinct authority IDs must remain unique. Declare every phase/unit exactly once with label `ID · Wave NN · mode`, and declare only `METRICS["Update Key metrics"]` and `VALIDATION["Validation"]` beyond those authorities. After the exact first line `flowchart TD`, every nonempty line is exactly one simple `-->` edge with optional quoted endpoint declarations. Comments, directives, styles, chains, other edge operators, and every unparsed statement are invalid. The exact derived edges are phase to each first-wave owned unit, same-phase dependency unit to dependent unit, each cross-phase dependency unit/phase to the dependent phase, and every terminal unit to both closeout nodes. No extra or missing node or edge is valid. Mermaid is presentation only, never ordering authority.

One direct source-visible `.execution-order-phases[data-planf3-execution-fallback]` remains the resilient exact projection. It owns one direct `.execution-order-phase[data-planf3-execution-phase]` group per phase. Each phase group directly owns its phase node and one direct `.execution-order-wave[data-planf3-execution-wave-group][data-planf3-work-mode]` per unit wave; each wave directly owns its unit nodes. The fallback contains one linked `.execution-order-node[data-planf3-execution-node]` for every phase and unit, with the exact ID set, owner group, wave/mode, and no duplicates. Every node visibly states its ID, `Wave NN`, and sequential/parallel text; every wave has a visible `.execution-order-wave-label`. It remains visible if SVG rendering is unavailable and canonical export restores it. Approach plans have no phases, units, or ordering projection.

## Profiles and File Impact

Code/implementation units own File Impact. Each authority is `.file-impact-delta[data-planf3-file-impact]` with repo-relative path, baseline `data-planf3-path-state="existing|new"`, and `data-planf3-anchor`. An authority that intends to delete a baseline-existing path additionally carries `data-planf3-path-result="deleted"`; no other value, baseline state, or context may carry this marker. Before document execution is complete, every baseline-existing path must still exist. When document execution is `complete`, a marked deleted path must be absent, while every unmarked baseline-existing path must still exist. It contains one direct visible matching path header marked `data-planf3-impact-path` and one direct `.file-impact-sides` wrapper. That wrapper directly owns exactly one Before and one After side. Each side has an exact visible `data-planf3-impact-label` (`Before` or `After`) and one nonempty `data-planf3-impact-body`. Bodies differ and describe the concrete delta. Duplicate normalized Before+After body pairs across authorities are invalid, preventing repeated generic intent prose.

The File impact index remains an exact unique-path table projection with path, state, seam, intent, owner backlinks, validation relation, local filter, and result count. Tests name a same-unit impacted test path. Only explicitly `data-planf3-work-class="non-behavioral"` work may instead carry a concrete no-test reason; behavioral work cannot bypass testing.

Knowledge/execution units use explicit input/output resource locators instead of File Impact. Approach/decision plans contain at least two evidence-linked options plus criterion, recommendation, risk, decision checkpoint, and post-selection route.

## Code snippets

Optional unit-owned code uses one shared `figure.code-snippet[data-planf3-code-snippet="source|illustrative"]`. Every figure has a nonempty `data-planf3-code-purpose`, one direct visible `figcaption.code-snippet-header`, one direct `pre.code-snippet-body` with a nonempty accessible label and `tabindex="0"` containing exactly one direct `code`, and one direct visible `data-planf3-code-caption`. Preserve code whitespace, escape HTML-significant characters, and keep the code body at most 2,000 characters.

A `source` figure is source-authentic evidence. Its `code` is the existing `data-planf3-snippet` guard with repo-relative path, matching same-unit existing File Impact and anchor, ordered line range, revision, whole-file SHA-256, purpose, and required revalidation. Wrap every source line in one direct `span[data-planf3-code-line="N"]`; numbers exactly cover the declared range in order while the combined code text remains byte-for-byte equal to the source lines. The figure's source and line metadata and visible header labels exactly match the guarded path and `Lines N-N`. The figure purpose matches the guard purpose. The `code-excerpt` report pattern uses this source variant.

An `illustrative` figure expresses proposed code, pseudocode, or a command that does not yet exist. It carries `data-planf3-code-kind="proposed|pseudocode|command"` and one matching visible kind label (`Proposed`, `Pseudocode`, or `Command`). It carries no source path, line, revision, hash, revalidation, or snippet guard metadata. Its caption explicitly states that it is illustrative design intent, not current source, and not independent semantic authority. Build receives both variants in the unit slice: revalidate source evidence before use, and treat illustrative code as subordinate to the unit goal, contracts, and File Impact.

## Key metrics

Every profile has exactly one global `section#key-metrics.key-metrics-overview[data-planf3-key-metrics="planned|observed"]` immediately after the hero and before `#purpose`. The location-independent `key-metrics-overview` component is reusable wherever a metrics overview fits, but only this top instance carries semantic authority; do not duplicate metric authorities. It owns one direct `.key-metrics-ledger` with 3-6 direct `.key-metric[data-planf3-key-metric]` scorecards and one direct visible housekeeping status row. Every metric has a `positive|negative|warning|info|neutral` semantic tone and exactly one visible part for label, baseline, target, observed, and evidence. Baseline is a visible `was ...` trend. Before execution, observed may say `Not measured - execution not started`. Approach plans use planned decision metrics. Hero observability remains record inventory and is not a substitute.

After all executable units resolve, Build updates metric observations/evidence and changes metrics state to observed. `--complete` rejects planned, pending, or not-measured metrics.

## Lifecycle

Execution derives from owned statuses. Under `--complete`, all statuses resolve, parent phase/unit status agrees with descendants, modified metadata is non-None, and amendments contain execution evidence. Preserve immutable created metadata, append-only lifecycle lists, stable IDs, settled decision history, and load-bearing evidence links.
